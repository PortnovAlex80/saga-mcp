## Все баги (8 исправлено)

### БАГА #1 [BLOCKER] — readExecutionWrites: execution-level query возвращает stale версию

**Слой:** kernel validation (formalization-installation.ts)
**Симптом:** `ledger artifact N does not match its canonical row` после recovery
**Причина:** `readExecutionWrites` искал managed productions по execution_id. Artifacts переживают несколько executions (создан в exec#1, отредактирован в exec#5), но query по execution_id возвращал устаревшую версию (exec#1 hash), а live artifact имел актуальный hash (exec#5).
**Фикс:** Query переделан на node-level (`listArtifactsForNodeInProcessRun`): process_run + module + node. `latestArtifactWrites` берёт последнюю версию. execution_id остаётся только как durability fence (worker вообще работал), не как query filter.

### БАГА #2 [BLOCKER] — matchesFenceRelaxed: проверял intent+task

**Слой:** kernel validation (formalization-installation.ts)
**Симптом:** Recovery создавал новый intent/task → `matchesFenceRelaxed` не пропускал artifacts
**Причина:** Fence проверял process+module+node+intent+task, но recovery меняет intent+task для того же node.
**Фикс:** `matchesFenceRelaxed` проверяет только process+module+node (граница listArtifactsForNodeInProcessRun). `matchesExecutionFence` удалён как dead code.

### БАГА #3 [BLOCKER] — trace_delete отсутствовал в COMMON_WRITE_TOOLS

**Слой:** authority scope (formalization-process-module.ts)
**Симптом:** Бесконечный review loop — модель создавала лишние traces (UC→UC-1), reviewer просил удалить, но developer не имел `trace_delete` в allowed_tools.
**Причина:** COMMON_WRITE_TOOLS содержал `trace_add` но не `trace_delete`. Recovery specs имели `trace_delete` в requiredTools, но обычные review-loop раунды — нет.
**Фикс:** `trace_delete` добавлен в COMMON_WRITE_TOOLS для всех formalization producer nodes.

### БАГА #4 [BLOCKER] — reset-saga-db не чистил 4 таблицы

**Слой:** persistence cleanup (reset-saga-db.mjs)
**Симптом:** Stale данные между прогонами вызывали acceptance-blocked
**Причина:** reset пропускал таблицы с immutable triggers:
- `saga3_exact_candidate_acceptance_items` (277 stale rows)
- `saga3_exact_candidate_acceptance_decisions`
- `saga3_managed_node_submissions`
- `command_receipts` (85837 stale rows)
**Фикс:** reset дропает immutable triggers (`DROP TRIGGER IF EXISTS`), удаляет все таблицы, триггеры пересоздаются при следующем `getDb()` через `CREATE TRIGGER IF NOT EXISTS`. Также добавлена очистка `saga3_module_installations`.

### БАГА #5 [BLOCKER] — findContractGap возвращал первый gap

**Слой:** flow logic (formalization-installation.ts)
**Симптом:** Formalization падала при 3+ missing AC traces. Recovery чинил по одному AC за attempt, max_attempts=2 → exhausted.
**Причина:** `findContractGap` использовал `return` на первом найденном gap, вместо сбора всех. Kernel сообщал recovery один finding; модель могла починить все за один заход, но не видела полного списка.
**Фикс:** `findContractGap` собирает ВСЕ gaps в массив (`gaps.push`), возвращает `gaps.join('; ')`. Структурные проверки (must contain one PRD) остались early-return.

### БАГА #6 [BLOCKER] — accept CAS: execution-level query

**Слой:** persistence CAS (sqlite-exact-candidate-acceptance.ts)
**Симптом:** `EXACT_ACCEPTANCE_CANDIDATE_NOT_PRODUCED` — та же fence проблема что #1, но в accept()
**Причина:** `accept()` искал managed production по `intent_id + task_id + execution_id + artifact_id`. Recovery менял intent/task → не находил producer'а → CAS reject.
**Фикс:** Query переделан на node-level: `process_run_id + module_ref + node_id + artifact_id`, `ORDER BY id DESC LIMIT 1`. Тот же паттерн что #1.

### БАГА #7 [BLOCKER] — ghost skill saga-planning-reviewer

**Слой:** infrastructure (development module package)
**Симптом:** Planning review workers умирали (`state=lost`). Planner работал, но reviewer spawn падал.
**Причина:** `saga-planning-reviewer` — skill, на который ссылается development execution profile (`reviewSkill`), но SKILL.md **никогда не существовал** на диске. Manifest комментировал это как "If a real planning-reviewer skill ships later, add it here."
**Фикс:** Skill создан (274 строки, по образцу saga-requirements-reviewer) + скопирован в development package/resources/skills/ + добавлен в manifest resourceIndex с kind='reviewer-skill'.

### БАГА #8 [MEDIUM] — module_installations блокируют reinstall

**Слой:** persistence (package installer)
**Симптом:** `cannot install module@version: installation id=N already holds the active slot with a different package_digest`
**Причина:** После изменения module definition (manifest/skill) package_digest меняется, но старая installation блокирует новую.
**Фикс:** reset-saga-db очищает saga3_module_installations. Для partial-reset — вручную `DELETE FROM saga3_module_installations WHERE name='<module>'`.

## Resume (доказано работающим)

### Что работает

| Механизм | Как | Статус |
|---|---|---|
| **Stale lease recovery** | Процесс убит → lease протухает (~5 мин) → `--resume` забирает | ✅ Доказано |
| **Partial-reset + resume** | `saga-reset-stage.mjs` сбрасывает один stage → `--resume` продолжает | ✅ Доказано (Development перезапущен без повтора Formalization) |
| **Checkpoint-resume внутри ProcessRun** | GenericFlowExecutor помнит последний completed node_run → перепрыгивает done узлы | ✅ Работает |

### Чего НЕТ (gap)

**Нет явной ручной паузы (graceful shutdown):**
- Нет `--pause` флага
- Нет обработки SIGTERM/SIGINT — kill прерывает worker на середине MCP call
- `pauseStage` вызывается только при ошибке (`kind:'paused'`), не по запросу

**Риск:** kill на середине MCP call может оставить half-written artifact. `--resume` восстанавливает, но это не идеально.

**Рекомендация:** добавить graceful shutdown — при SIGTERM:
1. Дождаться завершения текущего worker (не убивать на середине MCP call)
2. Вызвать `pauseStage` явно
3. Сохранить lease для resume

Это критично для **смены модели в runtime** (нужно остановить worker между MCP calls, сменить `episode_workflows.metadata.active_provider`, resume).

## Фундаментальная проблема: модули НЕ универсальные блоки

### Ожидание

Process Module — подключаемый блок с единым контрактом:
вход → flow → выход. Runtime единообразно исполняет любой модуль.

### Реальность (доказано кодом)

**Три разные инфраструктуры связи LM→kernel:**

| Модуль | LM подаёт output через | Kernel читает через | БД таблица |
|---|---|---|---|
| **Discovery** | `proposal_submit`, `readiness_submit`, `normalization_submit`, `diagnosis_submit` (domain-specific) | Domain-specific readers | `saga3_proposals`, `saga3_readiness_assessments`, ... |
| **Formalization** | `artifact_create` + `trace_add` (generic tracker) | `readExecutionWrites` → scan managed productions | `saga3_managed_artifact_productions` |
| **Development** | `process_node_submit` (kernel gate) | `plannerSubmissions.readExact` | `saga3_managed_node_submissions` |

**Подтверждение в коде:**
- `process_node_submit` существует как единый tool (`src/tools/process-node-submissions.ts`)
- Но formalization **не использует его** — kernel сам сканирует БД через `readExecutionWrites`
- Development **использует** — kernel читает `saga3_managed_node_submissions` через `readExact`
- Discovery использует **свой** набор domain-specific tools (`proposal_submit` ≠ `process_node_submit`)

### Почему это критично

1. **Модель путается.** Formalization: "создай artifacts → worker_done" (kernel сам найдёт).
   Development: "создай tasks → process_node_submit → worker_done" (явный шаг).
   Discovery: "заполни template → proposal_submit → worker_done" (domain tool).
   Три разных паттерна — модель не переключается между ними.

2. **Единый process_node_submit ЕСТЬ, но используется только development.**
   Formalization должен тоже через него — но не делает. Discovery использует
   устаревшие domain-specific tools вместо единого.

3. **Нет runtime gate.** worker_done не проверяет что output подан.
   В formalization — artifacts в БД, kernel найдёт. В development — модель
   должна сама помнить вызвать process_node_submit. Нет принуждения.

4. **Reviewer-ы разные.** Formalization reviewer проверяет artifacts.
   Development reviewer проверяет submission. Разные контракты.

### Что нужно (унификация)

**process_node_submit — единый output контракт для ВСЕХ модулей:**
- Discovery: `process_node_submit` с proposal payload (вместо proposal_submit)
- Formalization: `process_node_submit` с artifact refs (вместо artifact_create как output)
- Development: `process_node_submit` (уже так)
- Kernel всегда читает `saga3_managed_node_submissions`, не сканирует БД

**Runtime gate:** worker_done проверяет что process_node_submit вызван
для output_schema профиля. Без submit → reject.

## Уроки (критично для будущих прогонов)

| Урок | Что делать |
|---|---|
| **НЕ гонять формализацию заново ради бага в development** | partial-reset только проблемного stage + resume |
| **Cache кеширует документы, но не artifacts/traces в БД** | После reset модель перерегистрирует через MCP (~5-10 мин на этап). Для оптимизации — Trace Replay Guide |
| **execution_id не должен быть query filter** | Артефакты переживают executions. Query только по node (process+module+node) |
| **Ghost skills молча убивают workers** | Skill должен быть в package/resources/ И в manifest resourceIndex. Регрессионный тест |
| **findContractGap должен собирать ВСЕ gaps** | Один issue = все findings → один recovery attempt чинит всё |
| **reset должен чистить ВСЕ таблицы с "памятью"** | receipts, acceptance items, installations, node submissions |
