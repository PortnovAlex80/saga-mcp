# SAGA5 — план полной перестройки движка

- **База:** коммит `f1355390` (17.08.2026, «mis-key workItemKey») — тег `rollback-point`, ветка `saga5`.
- **Статус:** план на обсуждение/реализацию. Не является ADR; после принятия первого milestone превратить в ADR-001 saga5.
- **Дата:** 2026-08-30

## 0. Зачем перестройка (диагноз одним абзацем)

Идея конвейера (CONVEYOR-MENTAL-MODEL v5.2) нормативно верна, но реализация
saga4 зашла в тупик, который ADR-053 диагностировал точно: **двойная модель
собственности на материал** (Workplace vs WorkerExecution). Вся антифриз-серия
после 17.08 (supervisor-слои A/B1–B4/C, ADR-074/075, watchdog, park-reasons,
recovery-epochs, transition-obligations) — это патчи симптомов: не материал
получил единого владельца, а каждая машина из девяти получила собственный
надзиратель за синхронизацию с остальными восемью.

Цена вопроса на точке отката:

| Метрика | saga5-база (f1355390) | upstream-доска (spranab/saga-mcp) |
|---|---|---|
| LOC в src | ~127 000 TS | ~2 800 TS |
| Таблиц в схеме | 107 | 12 |
| Машин состояний | 9+ (Launch, Lifecycle, Stage, Process, Node, Workplace, Reservation/Execution, CandidateSet, Gate, Effect) | 1 (task status) |
| Зависимостей рантайма | тяжёлый набор | 2 (MCP SDK, better-sqlite3) |

**Решение оператора:** не продолжать патчи, а восстановиться на `f1355390` и
перестроить движок заново — проще, взяв лучшее из трёх систем: **saga
(конвейерный смысл), n8n (декларативный граф и исполнение), Temporal
(долговечность через историю событий)**.

## 1. Что берём из каждого движка

### 1.1 Из saga — конвейерный смысл (нормативная идея, не её код)

1. **Один производственный интерфейс**: воркер (LLM, скрипт, replay) получает
   неизменяемый контекст, читает точные входы, сдаёт материал через один
   протокол. Физика замены воркера не протекает в физику конвейера.
2. **Рабочий стол — владелец материала** (урок ADR-053, доведённый до
   фундамента): принятый материал — это запечатанная **ревизия стола**
   (множество content-addressed продуктов), а не «выход последнего исполнения».
   Исполнение — только provenance. Это не cutover-миграция, как в saga4, а
   исходное устройство с первого коммита.
3. **Production Cell** как универсальный цикл качества: автор → gate →
   (опц. рецензент) → accepted / repair / human_required / failed.
4. **Проверки ≠ эффекты**: check читает неизменяемый материал; effect меняет
   внешний мир и возвращает typed receipt. Компенсация — всегда явный эффект.
5. **Капсула/replay** — отложенная оптимизация (фаза 3), не режим рантайма.

### 1.2 Из n8n — форма движения

1. **Декларативный JSON-граф**: `nodes` + `connections` (map «узел → выход →
   список целей»), у каждого узла `type` + `typeVersion`. Исполнение — чистая
   интерпретация данных. Все цеха saga4 (`src/modules/*`,
   `src/process-modules/modules/*` — десятки тысяч строк ветвлений) заменяются
   декларативными графами.
2. **Items — универсальная валюта потока**: каждое ребро несёт массив
   `{json, binary?, pairedItem?}`; `pairedItem` даёт per-item provenance
   (аналог точных ProductRef, но встроенный в движение, а не надстроенный).
3. **Плагинный контракт узла**: `execute(ctx) → INodeExecutionData[][]`
   (массив на каждый выход). Ядро не знает семантики узлов: дисковери,
   формализация, разработка — это типы узлов в реестре, не модули ядра.
4. **Персистентный возобновляемый рекорд исполнения**: шапка
   (`status: new|running|waiting|success|error|canceled|crashed`, `waitTill`)
   отдельно от payload. Ключевое различие n8n: `crashed` ставится только
   статусам `new|running|unknown`, а легитимная пауза `waiting` никогда не
   считается крахом — это ровно та честность, которую saga4 добывала
   супервайзер-слоями.
5. **Декларативные политики отказа на узле**: `retryOnFail`, `maxTries`,
   `waitBetweenTries`, `onError: continueErrorOutput | stopWorkflow` — ретраи
   и обработка ошибок конфигурируются, а не программируются в движке.

### 1.3 Из Temporal — долговечность

1. **Event sourcing как единственный авторитет**: «истории событий достаточно,
   чтобы восстановить всё остальное состояние». Один append-only журнал на
   прогон вместо 107 таблиц-машин.
2. **Ядро (workflow) vs активность (activity)**: детерминированный интерпретатор
   выдаёт команды (`ScheduleActivity`, `StartTimer`, `CompleteNode`…), вся
   недетерминированность (LLM-вызовы, внешние системы) изолирована в
   активностях. Для LLM-завода это идеальная граница: модель не обязана быть
   детерминированной — обязано ядро.
3. **Типизированные таймауты на активность**: `schedule-to-start` (ожидание в
   очереди), `start-to-close` (бюджет самого вызова), `heartbeat`
   (прогресс живого воркера). Это заменяет supervisor/heartbeat-маркеры/
   watchdog saga4: зависший воркер = истёкший heartbeat, диагностируемый
   тем же ядром из той же истории.
4. **RetryPolicy с типами неповторяемых ошибок** и экспоненциальным backoff —
   единая политика вместо разбросанных `onExhausted`/бюджетов/эпох.
5. **Транзакционный append**: события + проекция + порождённые задачи
   фиксируются **одним** SQL-транзактом («decide then log») — класс
   «потерянных синхронизационных рёбер» между машинами saga4 исчезает
   структурно, потому что машин больше нет.
6. **Single-writer + fencing** на прогон: один токен записи на run-агрегат.

## 2. Целевая архитектура saga5

### 2.1 Три опоры

```text
ДЕКЛАРАЦИЯ            ЯДРО                          МАТЕРИАЛ
workflow-граф   →     детерминированный      →      content-addressed стол
(n8n-стиль)           интерпретатор-командер        (saga-053: ревизия стола)
                      событийная история
                      (Temporal-стиль)
```

### 2.2 Схема ядра (~10 таблиц вместо 107)

| Таблица | Роль |
|---|---|
| `workflows` | декларативные графы: `id, version, graph_json` (nodes/connections/узловые политики) |
| `runs` | прогон: `id, workflow_ref, root_run_id?, status, wait_till, next_seq, writer_token` — шапка-проекция, восстановима из событий |
| `events` | **единственный авторитет**: `run_id, seq, type, payload_json, ts`, append-only |
| `materials` | content-addressed продукты: `digest PK, schema_ref, content, ts` — неизменяемые |
| `executions` | активности: `id, run_id, node_id, attempt, status, timeouts, retry_policy, worker_kind, lease, heartbeat_at` |
| `effects` | внешние эффекты: `idempotency_key, desired_digest, receipt_json, status` |
| `timers` | отложенные пробуждения: `run_id, due_at, kind, payload` (ретраи, waitTill) |
| `projects` / `epics` / `tasks` | доска оператора (как у upstream): статусы `todo|in_progress|review|done|blocked`, автоблок по зависимостям — **проекция**, не авторитет |
| `activity_log` | человеко-читаемый журнал (проекция событий) |

Правило дисциплины: **новая таблица допустима только если её нельзя выразить
как событие или проекцию событий.**

### 2.3 Исполнение

```text
factory_start(order)
  → ядро: создан run, события RunStarted → NodeScheduled(roots)
  → диспетчер: eligible executions → очередь → воркер (LLM-процесс)
  → воркер: desk_read(exact refs) … desk_submit(schema, content)
       → материалы записаны (content-addressed), ExecutionCompleted событие
  → ядро (одна транзакция): свёртка → gate-узел → GateDecided
       | accepted → NodeCompleted → следующая NodeScheduled
       | repair_required → NodeScheduled(attempt+1) в бюджете политики
       | human_required → run.waiting + задача на доске (blocked)
  → таймауты/сердцебиение: TimerDue события → RetryScheduled / Failed(typed)
```

Статусы исполнения наследуют честную семантику n8n: `waiting` (человек, таймер,
зависимость) никогда не превращается в `crashed`; crashed — только
`new|running` c истёкшим lease/heartbeat.

### 2.4 Граница авторитета материала (053 с первого дня)

- `desk_submit` пишет материалы по дайджесту и добавляет событие
  `MaterialSubmitted(digest, node, execution)` — execution **не** входит в
  идентичность материала.
- Gate запечатывает `DeskRevision = отсортированный список дайджестов` и
  решает по нему; последующие потребители (reviewer, effects, следующие узлы)
  читают **только дайджесты ревизии**.
- Fitness-тест с первого milestone: ни один потребитель не выбирает материал по
  `execution_id`, `task_id`, `latest` — иначе CI красный (критерии завершения
  cutover из ADR-053, пункты 1–5, становятся архитектурными тестами saga5).

### 2.5 Человек и доска

Доска возвращается к простоте upstream: задачи со статусами
`todo|in_progress|review|done|blocked`, автоблок по зависимостям, dashboard.
`human_required` гейт = задача `blocked` + запись в activity_log; возобновление
— операторская команда, порождающая обычное событие. Двуканальность
«Kanban vs loop state» saga4 исчезает: канбан — проекция одного журнала.

### 2.6 MCP-поверхность (~15 тулов вместо 30 файлов)

Доска (из upstream): `project_*`, `epic_*`, `task_*`, `dashboard`, поиск/экспорт.
Конвейер: `factory_start`, `factory_status`, `desk_read`, `desk_submit`,
`execution_complete`, `operator_resolve`, `effect_run`, `event_tail`.
Всё остальное (settlement-debug, нормализация, readiness, approvals…) —
узлы графа и проекции, не отдельные протоколы.

## 3. Чего сознательно НЕ переносим из saga4

| Артефакт saga4 | Почему нет в saga5 |
|---|---|
| 5-уровневая иерархия Launch/Lifecycle/Stage/Process/NodeRun | стадии — подграфы одного графа; одна машина `runs` |
| Supervisor-слои A/B1–B4/C, watchdog, heartbeat-файлы движка | детерминированное ядро + таймауты активностей + replay истории = единый recovery-путь |
| `factory_workplace_park_reasons`, `recovery_epochs`, `operator_holds`, `transition_obligations`, `accepted_authority_head`… (~40 таблиц) | выражаются событиями и проекциями |
| Двуканальность Kanban/loop-state с mapping-правилами | один журнал, доска — проекция |
| Newest-wins капсульный биндер; resume-compatibility по `handlerLogicalIds` | не переносится вовсе; вместо resume-политики — пин `workflow version` на прогон |
| Замороженные пакеты/CheckPlans с rehydrate-пиннингом | узел графа версионируется `typeVersion`+дайджест в `workflows`; прогон пиннится на версию |

Сохраняются без изменений нормативные запреты модели: воркер не выбирает
работу; ядро не ветвится по имени цеха; `worker_done` без сданного материала
не является завершением; digest считает ядро, не модель; проверки не меняют
внешний мир; компенсации только явные.

## 4. Этапы (milestones)

Каждый milestone — зелёный, демонстрируемый, коммителен; без «временно
сломанного HEAD».

- **M0 — каркас.** Ветка `saga5`: удалить `src/process-modules`,
  `src/modules/*` (цеха), фабричные таблицы; новая `schema.ts` (~10 таблиц по
  §2.2); MCP-каркас + тулы доски (перенос из upstream-стиля).
  DoD: сервер поднимается, доска работает, `npm test` зелёный.
- **M1 — ядро-интерпретатор.** Граф + items + стек исполнения; события
  `RunStarted/NodeScheduled/NodeCompleted`; **scripted-воркер**
  (детерминированный исполнитель вместо LLM). DoD: сквозной прогон
  демонстрационного графа (например, mini-discovery) без LLM, восстановление
  после kill -9 в любой точке (replay истории).
- **M2 — LLM-активности.** Реальный воркер-процесс: spawn, `desk_read/
  desk_submit`, таймауты `schedule-to-start/start-to-close/heartbeat`,
  RetryPolicy с nonRetryable-типами. DoD: один узел выполняется реальной
  моделью; зависший воркер честно ловится heartbeat-таймаутом.
- **M3 — цикл качества.** Gate-узлы, DeskRevision-запечатывание, repair-бюджет
  из декларативной политики, `human_required` → доска. DoD: property-тест
  partition-invariance (сценарий Run 011 из ADR-053 как общий тест: материал
  собран двумя исполнениями — ревизия целостна).
- **M4 — эффекты.** Git-интеграция как effect с idempotency-key и typed
  receipt; компенсация — явная. DoD: конфликт интеграции — типизированный
  исход, не стирание принятого материала.
- **M5 — канарейка.** Реальный прогон одного проекта end-to-end; затем
  перенос 20-проектного по-цехового плана из `docs/testing/`.
- **Фаза 3 (опционально) — replay-капсулы.** Семантический ключ = дайджест
  входов узла (уже есть в items-провенанс); сертификация только от принятой
  ревизии. Делать только после стабильного M5.

## 5. Бюджеты и fitness-тесты

- **LOC-бюджет ядра** (kernel + schema + MCP-поверхность, без цехов-графов):
  ≤ 10 000 строк. Превышение — повод для ADR, а не для исключения из правила.
- Обязательные архитектурные тесты (красный CI при нарушении):
  1. ни один потребитель не читает материал по execution/latest (053);
  2. `waiting` никогда не превращается в `crashed` при recovery;
  3. события + проекция + порождённые задачи фиксируются атомарно;
  4. recovery после kill в любой точке не создаёт дублей материалов/эффектов;
  5. ядро не содержит ветвлений по имени цеха/типу проекта;
  6. scripted-прогон проходит через тот же протокол, что и LLM-прогон.
- Ручной критерий дрейфа (из модели, §29): «после сдачи материала ядро
  выполняется одинаково, не зная источника байт?» — если нет, в ядро протёк
  воркер.

## 6. Риски и контрмеры

| Риск | Контрмера |
|---|---|
| Event sourcing: эволюция схемы событий | versioned event types + upcast-функции; проекции перестраиваемы |
| SQLite как журнал событий | WAL, `next_seq` в транзакции append, single-writer на run; объёмы завода (сотни прогонов) заведомо посильны |
| Потеря жёстких гарантий saga4 при упрощении | §5 fitness-тесты = обязательные; инварианты сохранены, механизмы заменены |
| Соблазн тащить старые модули «по частям» | правило: цех = декларативный граф + узлы-плагины; перенос кода saga4 возможен только как узел-плагин |
| Матрица «трёх двигателей» расползается | каждый новый механизм обязан назвать источник (saga/n8n/Temporal) и причину, почему нельзя событием/проекцией |

## 7. Definition of Done (всего плана)

1. Сквозной scripted-прогон Discovery→Formalization→Development без LLM на
   новой схеме — зелёный в CI.
2. Один реальный canary-прогон проекта до terminal-состояния.
3. Ни одного потребителя материала по `execution_id`/`latest` (тест 1 из §5).
4. Ядро ≤ LOC-бюджета; схема ≤ 12 таблиц.
5. Доска оператора в простоте upstream: 5 статусов, автоблок зависимостей,
   dashboard.
