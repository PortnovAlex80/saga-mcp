# HUMAN-GATE-CONSOLE — консоль оператора для human_required гейтов

Дата: 2026-08-24. Статус: реализовано (saga4).

## Проблема (наблюдено на Elite 2, 2026-08-25)

Гейт `development.readiness-certification` вынес вердикт `human_required`:
провайдер `factory.local-runnability.v1` выдал типизированный `unknown`
`warrant-blocked-environment` (докер-среда машины недоступна — завод не может
сам запустить продукт и посмотреть на него). Воркспейс ушёл в `blocked/paused`
с park-причиной `GATE_HUMAN_REQUIRED`. Дальше — тупик:

- у трекера **не было ни одного UI-элемента**, который показал бы оператору,
  что завод просит человека;
- единственная операция `unpark` перезапускает воркера, но НЕ отвечает на гейт:
  чек повторно исполняется, снова выдаёт `unknown`, воркспейс снова паркуется
  (наблюдено: park-reason id 1 → unpark → id 2, 19:37 → 20:09);
- ответ человека нигде не фиксировался — «я посмотрел игру, всё ок» оставался
  вне аудиторского следа завода.

Класс дефекта: **backend спроектирован (CONVEYOR §17 граница человека,
REG-22 durable resume), механизм взаимодействия оператора не построен.**
Тот же пробел у `human_requests` (worker_ask_need/worker_ask_done): MCC-часть
есть, UI нет.

## Контракт

Когда гейт останавливает линию вердиктом `human_required`, завод ждёт
**явного решения оператора** по конкретному воркспейсу:

| Решение     | Семантика                                        | Механика после ответа                                                        |
|-------------|--------------------------------------------------|------------------------------------------------------------------------------|
| `accept`    | «Человек посмотрел продукт — всё ок»             | Резюм воркспейса (`repair-requeued`); при следующем прогоне чека runnability `unknown` конвертируется в `passed` с доказательством-ссылкой на решение человека; гейт принимает, ячейка терминализируется `verified` |
| `reject`    | «Человек посмотрел — НЕ ок» + обязательный текст | Резюм воркспейса; чек конвертируется в `failed` с диагностикой, несущей текст оператора; `failureOwnership:'upstream'` → вердикт `failed` → settle-development X3 переправляет дефект производящему цеху |

Оба пути идут **через существующий машинный конвейер** — новых переходов,
новых видов решений, подделки рецептов нет. Ответ человека входит в систему
как доказательство чека (check evidence) с точным провенансом: кто, когда,
какой bytes-субъект смотрел, что сказал.

## Механика

### 1. Парковка (существующее)

`human_required` → `human-required` → `blocked/paused` + append-only строка
`factory_workplace_park_reasons` (code=`GATE_HUMAN_REQUIRED`, сообщение
содержит `decision decision:gate-run:<sha>`).

### 2. Консоль (новое)

- `GET /api/human-gates` — список припаркованных `GATE_HUMAN_REQUIRED`
  воркспейсов с контекстом: проект, ячейка, сообщение парковки, рецепты чека
  (провайдер → outcome), subject binding, пути к репозиторию продукта.
- `POST /api/human-gates/resolve` — `{ workplace_ref, decision: accept|reject,
  feedback?, actor_id }`. Reject без feedback — отказ (400).
- UI: баннер вверху борда «⚠ ЗАВОД ПРОСИТ ЧЕЛОВЕКА — N гейтов ждут решения»,
  карточка гейта с кнопками **«✅ Всё ок — принять»** и **«❌ Не ок — на
  доработку»** + поле «что не понравилось» (обязательно при отказе).
  Вторая секция — открытые `human_requests` (вопросы воркеров) с полем ответа.

### 3. Запись решения (новое)

Append-only таблица `factory_human_gate_resolutions` (BEFORE UPDATE/DELETE →
ABORT, как у прочих immutable-таблиц):

```
id, workplace_ref, process_run_id, park_reason_id,
gate_decision_key,        -- отвечаемый human_required-вердикт
subject_binding,          -- local-readiness-subject:<hash>:<commit>:<tree> — страж bytes
provider_id,              -- чей unknown конвертируется этим решением
resolution,               -- 'accept' | 'reject'
feedback,                 -- текст оператора (обязателен при reject)
actor_id, created_at
```

Резюм — канонический CAS-переход `repair-requeued` (paused → queued, фаза
возвращается в активную по next_role, revision+1), в одной транзакции с
записью решения и строкой activity_log. Идемпотентность: повторный resolve
по уже отвеченному воркспейсу — no-op (CAS не сходится).

### 4. Пробуждение чека (новое, провайдер 1.16.0)

`factory.local-runnability.v1` 1.16.0 (новая политика
`humanGateResolutionPolicy` в дайджест-объекте, план
`development.readiness-certification.final.v4` пинит новый дайджест):

при исходе `unknown` провайдер консультирует таблицу решений по
`workplace_ref + provider_id`:

- **страж bytes**: решение применяется только если subject binding текущего
  субъекта совпадает с записанным в решении. Оператор принял конкретные байты
  замороженного кандидата; новый/другой кандидат — снова честный `unknown`,
  снова парковка, снова консоль. Цикл «принял один раз — всё далее зелёное»
  невозможен;
- `accept` → `passed`, evidence = исходный unknown-диагностик (аудит сохранён)
  + ссылка `human-gate-resolution:<id>` (actor, время);
- `reject` → `failed`, диагностик несёт текст оператора; далее штатный
  upstream-маршрут дефекта производителя;
- нет строки / таблицы / страж не сошёлся → поведение 1.15 без изменений
  (fail-closed).

Монотонность (`readiness-profile-monotonicity`) НЕ конвертируется решением
человека — это anty-gaming ratchet (CERTIFICATION-GAMING-REMEDY): сужение
декларации должно оставаться эскалацией. Такие парковки видны в консоли,
но операторский accept их не закрывает — воркспейс перепаркуется. Это
сознательная граница v1.

## Границы и безопасность

- Решение пишет только операторский API трекера (localhost-привязка трекера);
  actor_id фиксируется в каждой строке и в каждом proof-evidence.
- Решение immutable: append-only, изменения/удаления запрещены триггерами.
- Подделка рецептов невозможна: человек не пишет в `factory_check_receipts`;
  конвертацию выполняет сам провайдер при исполнении, recipe несёт digest
  провайдера 1.16.0 и ссылку на строку решения.
- Elite-2 кейс: `warrant-blocked-environment` на Windows-машине без докера —
  ровно тот класс, для которого граница создана: «завод не может посмотреть
  на продукт — человек может».

## Соответствие EK (новое ядро)

Это же будет нативно в EK-4 (WP-07 typed waits): парковка = типизированное
ожидание `factoryRun.observeWatchdog` с wake-source «operator command»;
консоль = проекция очереди ожиданий; resolve = команда оператора. Контракт
(accept/reject/feedback + bytes-страж + immutable-аудит) переносится как есть.

## Руководство оператора

1. Баннер на борде проекта красный — «ЗАВОД ПРОСИТ ЧЕЛОВЕКА».
2. Откройте карточку: прочитайте сообщение парковки (почему завод не решил сам).
3. Посмотрите продукт (карточка показывает путь к репозиторию; для served-
   продуктов — запустите локально и откройте в браузере).
4. Продукт ок → «✅ Всё ок — принять». Не ок → «❌ Не ок», заполните поле
   «что не понравилось» (обязательно), отправьте.
5. Завод продолжит сам: accept → certify → verified; reject → дефект уйдёт
   производящему цеху с вашим текстом.
