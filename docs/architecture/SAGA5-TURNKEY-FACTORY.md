# Завод под ключ: от идеи до запускающейся программы

- **Статус:** реализовано и проверено живым прогоном, 2026-08-31.
- **Цех:** `factory` — `WORKSHOP_SPECS.factory`, семь столов.
- **Модель прогона:** `zai-coding-plan/glm-5.3-flash`, два воркера одновременно.

---

## 1. Что значит «под ключ»

Единственная честная формулировка приёмки: **программа запускается**. Не
«модель написала код», не «ревьюер одобрил», а исполнимый критерий.

```
идея → бриф → SRS → план задач → веер реализации → ревью → сборка → ЗАПУСК
```

| Стол | Кто работает | Приёмка |
|---|---|---|
| `brief` | аналитик | пять разделов брифа (критерии навыка) |
| `srs` | системный аналитик | FR-/UC-/AC- нумерация |
| `plan` | техлид | JSON-массив ≥2 независимых задач |
| `implement` | **веер**: по воркеру на задачу | JSON-массив файлов |
| `review` | ревьюер | вердикт вынесен |
| `assemble` | сборщик | **запуск кандидата** (`command_ok`) |
| `smoke` | никто (только команда) | **запуск опубликованного** |

Публикация в репозиторий стоит между `assemble` и `smoke`: **в репозиторий
попадает только то, что уже запускалось** во временном каталоге.

## 2. Живой прогон

Идея: «одностраничный таймер-помидорка: 25 минут работы и 5 минут отдыха,
кнопки старт/пауза/сброс, звуковой сигнал и счётчик за день».

Результат — `success`. Репозиторий продукта:

```
index.html   css/styles.css   js/timer.js   js/sound.js   js/storage.js
discovery/brief.md   formalization/srs.md
```

Проверено в браузере: страница открывается, таймер идёт (25:00 → 24:49),
кнопки работают, счётчик на месте. Дымовая проверка опубликованного
репозитория: `OK: приложение собрано и запускается. Проверено файлов: 5`.

Замеры смены: планировщик выдал 4 задачи; четыре воркера отработали по
2 минуты; ревью — 51 с (7219 входных / 625 выходных токенов); сборка — одна
попытка.

## 3. Три дефекта, которые нашёл сам завод

Это ценнее, чем сам факт успеха: каждый дефект был пойман исполнимой
приёмкой, а не рассуждением.

### 3.1 Ссылка на несуществующий файл

Первый прогон: `index.html` подключал `js/app.js`, которого не создала ни
одна задача. Классика параллельной работы — исполнители не знали друг о друге.

**Исправление:** узел `siblings` кладёт каждому воркеру веера сводку о
соседних задачах и их файлах. Рабочий на конвейере обязан видеть соседние
рабочие места.

### 3.2 Переписывание всего набора не укладывается в бюджет

Первая версия сборщика возвращала ПОЛНЫЙ набор файлов. Замер: попытка
оборвалась по `start_to_close_s = 300`, потом повторилась и снова оборвалась.

**Исправление:** сборщик возвращает только изменённые и добавленные файлы, а
узел `overlay` детерминированно кладёт заплатку на исходный набор (поздний
item побеждает по ключу `path`). Модель делает малую работу, склейку делает
код. Это же снимает риск, что модель молча сократит содержимое файла.

### 3.3 Гейт судил не то, что произвёл воркер

Команда заменяет содержимое стола доказательством (`ok/exit_code/output`),
поэтому критерий навыка «ответ — это JSON-массив» проверять стало не на чем
и он падал структурно.

**Исправление:** при наличии команды гейт читает СОЮЗ — что воркер произвёл
и что показал запуск.

## 4. Почему ревью больше не блокирует

Приёмка ревью требует, чтобы вердикт был **вынесен**, а не чтобы он был
положительным. Причина прагматична и проверяема: повторный запуск того же
ревьюера на тех же файлах — лотерея, а не доработка (чинить код он не умеет,
а бюджет доработок он сжигает). Замечания ревьюера уезжают сборщику как
контекст, а решающей приёмкой становится запуск.

Это осознанный размен: субъективное суждение перестаёт быть воротами,
исполнимый критерий ими становится.

## 4b. Что показала вторая ночь (Elite, каркасный 3D в браузере)

Второй продукт — космический симулятор с векторной графикой — оказался
сильно тяжелее счётчика и вскрыл шесть дефектов. Все, кроме одного, были
дефектами МЕХАНИЗМА, а не модели.

| Симптом | Настоящая причина | Где починено |
|---|---|---|
| воркер записал файл продукта в репозиторий завода | у агента есть инструменты записи, а рабочим каталогом был каталог воркера | песочница на попытку |
| «fetch failed» ровно на 305-й секунде | `fetch` в Node сдаётся по headersTimeout undici (300 с) | длинный вызов на `node:http` |
| разбор JSON уронил весь прогон | приёмка веера требовала «хоть один член», а ниже разбирается каждый | допускной критерий `each_json_array` |
| страница собралась, но HUD не появился | два воркера договорились по-разному: конструктор против объекта с `init` | приёмка в настоящем Chrome |
| повтор упавшего ребёнка никто не заметил | соединение и приёмка остались со старым содержимым | устаревшее соединение пересобирается; гейт судит изменившийся стол |
| ответ модели обрезан на середине | задача не умещается в лимит вывода (`finish=length`) | страж обрыва + дробление задач в навыке планировщика |

Два вывода стоят отдельно.

**Приёмка «запускается» слабее, чем кажется.** Статическая проверка видит
битые ссылки и синтаксис, но расхождение контрактов между параллельными
воркерами — нет: оба файла корректны, а на экране пусто. Поэтому добавлена
проверка в настоящем Chrome (headless, разговор по CDP, ни одной новой
зависимости). Общее правило вместо настройки под продукт: если КОД
обращается к контейнеру по id, а контейнер после загрузки пуст — модуль не
подключился.

**Накопление стола — не универсальный закон.** Оно придумано для
взаимодополняющих попыток (Run 011). Для брака оно вредно: забракованный
материал лежит рядом с новым и продолжает валить приёмку. Поэтому у
операторского повтора теперь смысл «переделай», а не «добавь ещё одну
попытку»: старый материал уходит со стола явным событием.

## 5. Что этот прогон НЕ доказывает

- Дымовая проверка ловит битые ссылки, синтаксис JS и отсутствие корня
  документа. Она **не** проверяет логику: в готовом приложении две кнопки
  оказались подписаны «Пауза» (первая переключает надпись, вторая осталась
  отдельной). Такой дефект поймал бы только тест поведения.
- Проверено на статическом веб-приложении. Для другого типа продукта нужен
  свой стол приёмки — но это данные (`{kind:'command', run: '…'}`), а не код.
- Один прогон — не статистика. Первые два прогона нашли по дефекту; третий
  прошёл. Устойчивость измеряется серией, а не одним успехом.

## 6. Безопасность команды

Команда берётся из ДЕКЛАРАЦИИ цеха (оператор), никогда из вывода модели.
Воркер может описать желаемое состояние, но не может выдать себе право на
эффект. `workdir: 'items'` выполняет команду во временном каталоге над
кандидатом; обычный режим — в продуктовом репозитории. Ни то, ни другое не
даёт модели канала для произвольного исполнения.
