# saga5: монитор смены и операторский лимит найма

- **Статус:** принято, реализовано.
- **Дата:** 2026-08-30.
- **Область:** `src/kernel/workers.ts`, `src/limits.ts`, `src/runtime/worker.ts`,
  `src/kernel/executions.ts`, `src/bridge.ts`, `desk/src/Workers.tsx`.

---

## 1. Задача

В saga4 был фронт-мониторинг воркеров (tracker-view): видно, сколько агентов
нанято и что они «думают», плюс настраиваемый лимит параллельности. В saga5
это отсутствовало: `executions` знали всё, но наружу отдавали только счётчики
по статусам.

## 2. Что честно можно показать (измерено, а не предположено)

Прежде чем строить «поток мыслей», я измерил, что вообще отдаёт наш провайдер.
`opencode run` **не стримит токены**: при вызове на `glm-5.3-flash` весь ответ
пришёл одним куском (2943 байта) через 20.8 с, ровно один chunk.

С `--format json` картина другая — приходят события:

```
[+8.2s]  step_start
[+19.0s] text        ← весь ответ целиком, не дельтами
[+19.0s] step_finish ← tokens {input, output, reasoning}, cost
```

Вывод: «мысли по токенам» на этом маршруте невозможны, и рисовать их было бы
враньём. Зато честно доступны **фазы** и **расход**. Разница между «модель
думает 40 секунд» и «звонок повис, не дойдя до первого шага» — это ровно то,
ради чего оператор смотрит в монитор.

Поэтому воркер переведён на `--format json` и ведёт фазовый журнал:

```
[+0.0s]  запрос отправлен · zai-coding-plan/glm-5.3-flash · 406 симв.
[+8.9s]  модель начала шаг
[+21.5s] получен ответ · 1691 симв.
[+21.8s] шаг завершён · 500 токенов ответа
```

Побочная выгода: ответ теперь берётся из событий `text`, а не из
декорированного вывода CLI — разбор устойчивее. Если события не распознались
(другой провайдер, другая версия), воркер молча возвращается к сырому stdout:
монитор не имеет права быть причиной отказа.

## 3. Где живёт живой текст и почему не в журнале

| Что | Где | Почему |
|---|---|---|
| «сколько символов пришло к этому удару сердца» | событие `execution.heartbeat` | **факт**, воспроизводимый реплеем |
| сам текст фазового журнала | колонка `executions.progress` | **окно** в недетерминированный процесс: перезаписывается каждым ударом, ни одно решение его не читает |
| расход попытки (`usage`) | событие `execution.completed` | провенанс **попытки**, не материала |

Ключевое разграничение: **материал — это то, что воркер СДАЁТ**. Живой текст
материалом не является и не должен становиться дайджестом. По той же причине
`usage` не кладётся в item: два одинаковых ответа обязаны остаться
контентно-идентичными, сколько бы они ни стоили.

Финальные фазы приходят уже после последнего удара сердца, поэтому воркер
делает один явный flush перед расчётом — и карточка завершённой попытки
показывает историю целиком, включая причину отказа.

## 4. Лимит найма — не состояние ядра

Сколько воркеров нанимать и как часто — свойство машины и тарифа провайдера,
а не продукта, который строится. Поэтому лимиты живут **рядом с базой** в
`<DB_PATH>.limits.json`: ни таблицы, ни события, нечего реплеить.

```json
{ "max_workers": 2, "min_spawn_interval_ms": 1500 }
```

- `max_workers` — одновременно нанятых (1–64). Планы GLM троттлят выше ~2–3.
- `min_spawn_interval_ms` — минимальная пауза между двумя наймами. Это именно
  **рейт-лимит**, а не ограничение параллельности: при глубокой очереди он
  удерживает частоту запросов под потолком тарифа.

Файл — источник истины, поэтому UI, MCP-тул `limits_set` и человек с
редактором не спорят между собой; мост перечитывает файл, когда меняется
mtime, то есть перенастройка применяется к живому заводу без перезапуска.
Чтение никогда не создаёт файл, значения клампятся, битый файл — это дефолты
(fail-open: неверная настройка не имеет права остановить завод).

## 5. Поверхность

- `GET /api/workers` → `{limits, hired, stats, live[], recent[]}`
- `GET|POST /api/limits`
- MCP: `workers_view`, `limits_set`
- Стол: вкладка **Воркеры** — «нанято N из M», бюджет каждой попытки полосой
  (видно, что воркер вот-вот упрётся в таймаут), пульс, фазовый журнал,
  завершённые попытки с расходом и раскрывающимся разбором.

## 6. Fitness-тесты

`tests/workers.test.mjs`:

- очередь показывает модель и задание из объявленного графа;
- удар сердца несёт **число символов** в журнал, а текст — только в колонку;
  проверяется, что живой текст не протёк в авторитет;
- завершённая попытка отдаёт свою **длительность**, а не «время с конца»;
- лимиты клампятся, переживают перечитывание, чтение не создаёт файла.

`tests/bridge.test.mjs`: при `max_workers: 1` две готовые активности дают
ровно одного нанятого и одного в очереди — это потолок, а не потеря; после
снятия потолка очередь дорабатывается до `success`.
