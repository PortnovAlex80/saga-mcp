# saga5: канбан и мини-вики как проекции одного журнала

- **Статус:** принято, реализовано (фаза A из `docs/plans/SAGA5-REBUILD-PLAN.md` §2.7).
- **Дата:** 2026-08-30.
- **Область:** `src/kernel/projection.ts`, `src/kernel/board.ts`,
  `src/kernel/artifacts.ts`, `src/operator.ts`, `src/workshops.ts`,
  `desk/src/{Board,Wiki}.tsx`.

---

## 1. Задача

После M5 у saga5 были ядро, цеха-графы и стол-канвас, но не было двух вещей,
ради которых конвейер вообще нужен человеку:

1. **канбан** — «где сейчас работа и что от меня требуется»;
2. **мини-вики** — «покажи артефакт-спецификацию, дай его прочитать и
   поправить».

В saga4 они были, но ценой двуканальности: доска Kanban и loop-state были
двумя машинами состояний, которые сшивались правилами маппинга. Это одна из
причин мегасложности, из-за которой saga4 стала неработоспособной.

## 2. Диагноз: не хватало не механизма, а существительного

Карточка доски и страница вики должны быть *о чём-то*. В saga4 этим
существительным был Workplace (плюс ~40 таблиц вокруг). В n8n такого
существительного нет вовсе — есть только исполнения. saga5 унаследовала эту
дыру: единственными долговечными сущностями были `runs` (безымянные, по одному
на цех) и `tasks` (создавались только для человеческого гейта).

Соблазн был очевиден: завести таблицу карточек и таблицу артефактов. Это и
есть первый шаг обратно в saga4.

## 3. Решение

**Ни одной новой таблицы. Новое существительное выводится, а не хранится.**

| Понятие | Определение | Идентичность |
|---|---|---|
| **Карточка** | стол одного узла одного прогона | `run_id::node_id` |
| **Артефакт** | один item одного материала на этом столе | `digest` + индекс |

Обе сущности — свёртка `events` (`src/kernel/projection.ts`), той же природы,
что и свёртка самого ядра в `runner.ts`. Правило дисциплины из плана §2.2
(«новая таблица допустима только если её нельзя выразить событием или
проекцией») соблюдено буквально.

### 3.1 Канбан

Колонки — словарь upstream-доски: `todo | in_progress | review | blocked |
done | failed`. Колонка **выводится** из журнала:

```
node.scheduled / execution.scheduled      → todo
node.started   / execution.started        → in_progress
execution.failed / timed_out              → todo  (решение о ретрае — за свипом)
gate.decided repair_required              → review (+ цель ремонта → review)
gate.decided human_required               → blocked
node.completed                            → done
node.failed / retry_exhausted             → failed
```

Отсюда главное свойство: **карточку нельзя перетащить в «принято»**, потому
что «принято» не хранится. Двуканальность saga4 исчезает не по соглашению, а
структурно. Единственная запись, которую карточка может нести, — решение
оператора на человеческом гейте (`action: 'operator_decision'`), и это обычное
событие ядра `operator.resolved`.

Динамический fan-out даёт по карточке на каждого порождённого ребёнка
(`nodes.spawned`), с заголовком из его item. Параллельные воркеры Development
видны как реальные карточки без единой новой строки в схеме.

### 3.2 Мини-вики

Артефакт — это материал, а не отдельная сущность:

- **путь** артефакта берётся из декларации ближайшего downstream-эффекта
  (`files: [{path, field}]` / `files_from: 'items'`). Гейты прозрачны —
  принятый материал публикуется под тем же путём; обычные узлы **нет**: идея
  не является брифом, который из неё вырос;
- **`publishedFiles()`** зеркалит `desiredFiles()` воркера, поэтому вики
  показывает содержимое файла байт в байт, не читая файловую систему;
- **принят** = дайджест входит в ревизию, принятую гейтом;
- узлы-транзиты (`gate`, `join`, `split`) в списке скрыты: их стол — это
  повтор материала автора под новым дайджестом.

### 3.3 Правка артефакта = сдача материала

Ключевое упрощение: **человек, пишущий материал, — это воркер, сдающий
материал.** `submitOperatorMaterial()` в одной транзакции пишет
`material.submitted` + `node.completed` с `author: 'operator'`. Дальше — тот
же стол, то же накопление, тот же гейт, тот же журнал.

Следствия, которые пришлось довести до конца:

1. гейт в состоянии `human_required` теперь пересматривает решение, если
   целевой узел получил **новый материал** после его вердикта. Иначе правка
   оператора не имела бы никакого эффекта — гейт ждал бы только кнопки;
2. успешный прогон запечатан: `RUN_SEALED`. Принятый материал не переписывают,
   для него запускают новый прогон;
3. терминальный (`error`) прогон переоткрывается **явно**, событием
   `operator.reopened`, а не молча.

Так «управление через артефакты-спецификации» стоит одной функции и не
заводит второго авторитета.

## 4. Побочная находка: допускные критерии против накапливающегося стола

`not_contains` вычислялся как `!items.some(...)` по **всему накопленному
столу**. Стол по ADR-053 накапливает, значит один испорченный материал
(например, мохибейк `U+FFFD`) проваливал гейт вечно и сжигал весь бюджет
доработок. Починить такой стол было невозможно в принципе — ни моделью, ни
руками.

Разделение (`src/kernel/gate.ts`, `evaluateDesk`):

- **приёмочные критерии** (`nonempty`, `contains`, `regex`, `json_array`) —
  позитивные: достаточно, чтобы их удовлетворил *какой-то* выживший член. Тут
  накопление помогает (Run 011: две попытки в сумме дают полный материал);
- **допускной критерий** (`not_contains`) — обязан держаться для *каждого*
  члена. Нарушивший член уходит со стола событием `material.superseded` с
  явной причиной; ревизия запечатывается только из выживших.

Инвариант ADR-053 сохранён: идентичность ревизии по-прежнему зависит только
от множества дайджестов её членов, а исполнение остаётся provenance.

## 5. Один вход в цех

Побочно закрыт начавшийся рецидив saga4: `discovery_start`,
`formalization_start`, `product_start`, `development_start` — четыре функции,
четыре MCP-тула и четыре HTTP-ручки, растущие линейно по числу цехов.

Теперь: `startWorkshop(db, name, input)` — один тул `workshop_start`, одна
ручка `POST /api/workshops/:name/start`. Цех декларирует свою форму ввода
(`inputs: WorkshopInput[]`), и стол рисует её сам. **Новый цех = новый граф;
ни тула, ни ручки, ни ветки в UI.**

Материал между цехами передаётся принятым артефактом из хранилища материалов
(`latestPublished`), а не `readFileSync` по продуктовому репозиторию; поиск
ограничен репозиторием продукта, чтобы материал не утекал между продуктами.
Файл остался запасным путём для материала, произведённого вне ядра.

## 6. Поверхность

MCP: `workshop_start`, `workshops_list`, `board_view`, `artifact_list`,
`artifact_read`, `artifact_submit`, `operator_resolve`, `factory_start`,
`factory_status`, `event_tail` — плюс тулы доски upstream.

HTTP (мост): `POST /api/workshops/:name/start`, `GET /api/board`,
`GET /api/artifacts`, `GET /api/artifact`,
`POST /api/runs/:id/nodes/:node/submit`, `POST /api/runs/:id/resolve`,
`POST /api/graph`, `GET /api/runs/:id[/events]`, `GET /api/state`.

Стол (`desk/`): три вкладки — **Доска** (канбан + запуск цеха), **Стол**
(граф), **Артефакты** (вики с чтением и правкой).

## 7. Fitness-тесты

- `tests/board-projection.test.mjs` — колонки выводятся из журнала; fan-out
  даёт карточку на ребёнка; человеческий гейт несёт единственное действие;
  ни одна карточка не имеет статуса вне словаря.
- `tests/artifacts.test.mjs` — артефакт несёт путь/дайджест/принятость;
  правка оператора пересматривается гейтом; испорченный материал вытесняется,
  и после этого починка возможна; успешный прогон запечатан.
- `tests/bridge.test.mjs` — доска, артефакты и операторская запись живут на
  одном origin; единственный вход в цех валидирует объявленные входы.
