# SEAM ARCHITECT — итоговый архитектор в цехе? Три независимых анализа

**Вопрос оператора:** нужен ли в Development итоговый архитектор-полировщик?
Или последняя задача цепи должна получить права чинить весь скоуп?

## Вердикт трёх архитекторов — единогласный по главному

**Оба предложения отвергнуты в исходной форме.** Права записи от ТОПОЛОГИИ
(«последний в цепи») или от РОЛИ («полировщик») ломают модель авторитета.
Права приходят только от КОНТРАКТА (planner-frozen scope + check plan).

## Почему (B) «последняя задача = полные права» — худший вариант

При width-1 цепи sink = automated-test, зависящий от всех семи задач.
Вариант (B) даёт автору тестов право чинить код, который его тесты судят:
**самосертификация**. Модуль уже запрещает это на settlement-уровне
(verification = read_only_evidence); (B) реинтродуцирует на уровне задачи
то, что запретлено уровнем выше. CODEOWNERS-параллель: права на пути +
ревью, никогда на позицию в цепи.

## Почему (A) «полировщик-роль» — слишком дорого

1. **K13-спайн ломается молча**: голова авторитета byte-identical per-cell;
   полировщик, правящий physics-core после принятия ячейки, создаёт
   head-says-X/tree-says-Y расхождение, которое НЕ МОЖЕТ быть легально
   разрешено (final_acceptances immutable по trigger'у).
2. **Гейт не может проверить глобальную задачу**: чек-планы per-contract;
   глобальный план = непиннованный blob, который §27 отвергает.
3. **Каскад инвалидации**: правка полировщика обнуляет ВСЕ ревью,
   касающиеся этих файлов; «пере-ревью» = новые repair-ячейки с новым
   digest — полный цикл на каждую правку.
4. **Экономика**: бюджет траектории уже сделал распределённый ремонт
   бесплатным до 20 при сходимости; полировщик не экономит токены,
   а переносит их в один жирный контекст.

## Решение — три слоя

### Слой 1: чинить декомпозицию на этапе планирования (корень)

Изменение: `development-settlement-policy.ts` — при оверлапе scope'ов
ТРЕБОВАТЬ извлечения общей поверхности (base-item / scaffolding item),
а не упорядочивания. Механически = расширение существующего
requiredChangeScopes bootstrap.

Триггер: телеметрия из `factory_gate_finding_set_chain` — частота
`path-outside-authority` по паре (задача, чужой-scope). Выше порога →
планировщик обязан пересмотреть нарезку на следующем цикле.

### Слой 2: интеграционная верификация (недостающий генератор улик)

Расширение verification-continuation: **гонять собранное целое** (полный
тесьют + docker compose + acceptance-тест) ДО settlement'а. Сегодня
git-интеграция текстуальна (merge-tree ловит только CONFLICT-строки) —
семантические разрывы швов проходят молча, и ничто не доказывает, что
собранный продукт работает.

Выход: типизированные repair-issues с точной локализацией — какой шов,
какие задачи вовлечены, что нарушено.

### Слой 3: ремонт через владельца (паттерн reconciliation)

Интерegration-верификация НЕ пишет сама. Она маршрутизирует repair-issue
**владеющей ячейке** (scope-провайдер определяет по пути). Ячейка
открывается в repair-режиме со СВОИМ check plan, чинит в СВОИХ границах,
проходит СВОЙ ревью. Для真正的 межшовных дефектов (не принадлежащих
никому) — reconciliation-паттерн: ограниченные записи + типизированный
отчёт (repairs[]/remaining_gaps[]/rationale) + независимый ревьюер + гейт.

## Контраргументы (сохранены честно)

- **A1:** планировщик не может предвидеть швы заранее; collision-after-physics
  всплыл в рантайме — planner-frozen scope может промахнуться, воссоздав
  4-раундовое горение на стадию раньше. Ответ: рантайм-эскалация хуже,
  потому что превращает случайный mis-scope в постоянную дыру.
- **A2:** бюджет траектории может сделать весь вопрос moot — чинить ничего,
  пока телеметрия не потребует. Дешевейший архитектор — тот, кто ничего
  не строит и ждёт данных.
- **A3:** freeze делает ограниченные записи само-обесценивающими (любая
  правка обнуляет upstream-эвиденс через candidateHash). Ответ: кто-то
  должен владеть и локализовать отказ; сегодня эвиденс складируется
  мёртвым грузом.

## Рекомендация

Внедрять в порядке: Слой 2 (integration-верификация — генерирует данные,
которых сегодня нет) → Слой 1 (пересмотр нарезки по телеметрии) →
Слой 3 (reconciliation-выход для безхозных швов — только если Слой 2
покажет, что такие швы реально случаются).
