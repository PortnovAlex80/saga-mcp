# FINDING-TRAJECTORY BUDGET — сходимосте-осведомлённый ремонтный бюджет

**Автор идеи:** оператор (2026-08-19): «если завод видит по recovery-feedback.json,
что количество замечаний меняется — это не зацикливание, не штрафовать; до 20 раз».
**Статус:** дизайн-исследование; к реализации после терминала stage-11 (кандидат в
очередь кампании PREVENTIVE-HUNT).

## Вердикт исследования

Инстинкт верен по данным (stage-11 планировщик: попытка 1 = 15 замечаний, попытка 2 =
**5, строгое подмножество** — 10 снято, 0 новых — учебниковая §15-сходимость, которую
счётный бюджет не отличает от спина). Но **честный сигнал — отношение строгого
подмножества на множествах ключей замечаний, не счётчик**: чистый счёт (15→5)
проигрывает косметическому churn (15→14 с одним НОВЫМ ключом при живом ядре —
счёт упал, сходимость ложная).

## Рекомендуемый вариант (d) — гибрид

- **Предикат:** попытка сходящаяся ⟺ множество ключей — строгое подмножество
  предыдущего (снято ≥1 И новых 0) И fatal-подмножество не растёт.
  `spinning` = байт-идентичное множество; `churning` = всё остальное.
- Сходящиеся попытки **не расходуют epoch-бюджет** (максуется только вклад
  rejectedSets — крахи терминальных исполнений и effect-ремонты ВСЁ РАВНО
  списываются: сходящаяся ячейка с умирающими воркерами не крутится бесплатно).
- Поток сходимости ограничен `convergenceChainAttempts ?? 20`; абсолютный
  `totalAttempts=30` неприкосновенен (§15 правило 4). Арифметика самозамыкающая:
  строгое подмножество ≥1 снятия за шаг ⇒ ≤ начального числа замечаний шагов.
- Расширение **только для `onExhausted:'requeue'`** ячеек; pause-ячейки
  (Delivery/infra, ADR-075) остаются human-gated.

## Точки касания (для реализации)

1. Чистый модуль `finding-trajectory.ts`: `findingKey` = code + нормализованное
   сообщение (стриппинг semver/hex ≥16); `findingSet` (digest, keys, fatalKeys);
   `trajectory(prev,next)`. Цепочка сбрасывается при смене `check_plan_digest`.
2. Append-only таблица `factory_gate_finding_set_chain` — пишется в транзакции
   `driveGateRun` при `verdict='repair_required'`; декодирование через общий
   `decodeFindingsForDecision` (экстракт из projection-persistence:700-733) —
   писатель фидебека и бюджет не могут разойтись.
3. Сравнение — в `repair_wait`-ветке executor'а (production-cell-node-executor:
   569-659), ГДЕ бюджет сравнивается сегодня: гейт НЕ отказывает в планировании —
   гейты судят материал, планирование — плоскость executor'а, и решение раньше
   mint'а попытки N+1.
4. `CellRecoveryPolicy.convergenceChainAttempts?: number` (production-cell-
   definition.ts:61).
5. Проекция оператору рендерит `CONVERGING n→m keys` — цепочку, не голый счёт.

## Почему не другие варианты

- (a) чистый счёт: побеждён cosmetic-churn (см. выше); 5→6→5 осцилляция невидима.
- (b) только identity-множества: не отличает сходимость от churn (оба «новый
  digest = работа = не налог»).
- (c) пороги/монотонность: %-пороги бессмысленны на малых N, non-increase
  легализует чистый спин.

## Ключевые ограничения (честно)

- **b004-клапан не видит repair-петель** (обязательства минтятся на accept, не на
  repair_required) — плоскости разные; семантика зеркалится, код не связывается.
- **Review-путь исключён**: ревьюерские findings — ординальные коды + свободная
  проза, ключи нестабильны между попытками. Сравнение — только check-diagnostic
  findings. Корневое лечение (follow-up): структурные поля subject в
  CheckDiagnostic — заодно фиксирует review-путь у источника.
- Детерминизм шаблонов сообщений — предусловие; дрейф проверок → ложный churn
  (переналог, никогда недоналог — fail-safe направление).
- Стоимость: 20 сходящихся попыток ≈ 2.5-5 часов одной станции; downstream в
  pendingOutcome (живы, стагнируют) — потому потолок 20 + абсолют 30 + рендер
  цепочки оператору.

## Анти-гейминг

Удаление-токена-за-попытку: чистые удаления — строгое подмножество, НО ограничены
начальным числом ключей и потолком, а терминальный диагноз называет выжившие
ключи. Severity-рост (5 fatal вместо 15 error): fatal-неубывание ⇒ churn ⇒ налог.
Крах-отмывание: сходящимся списывается только rejectedSets. Косметика (новый
ключ при живом ядре): новый ключ ⇒ churn ⇒ налог. Направление отказа —
переналог, не вечный цикл.
