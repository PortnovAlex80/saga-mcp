## 2. Гипотезы о причинах фейлов (TB-6, TB-8)

### 2.1 TB-6 — P02 stopwatch, HASH_DRIFT (гонка repair-редактирования против гейта)

**Где возникла гипотеза.** Лог `testbed P02/W2` показал terminal-фейл в 09:34:58 при
`workers={exited:7…}`; единственный failed node_run в БД — id 574 `model-use-cases`
(09:34:50). Хронология `activity_log` + `artifacts` по epic 4:

```
09:31:01–09:32:06  ревьюер: changes_requested → UC-задача обратно автору
09:32:12           первый final-гейт ACCEPTED (кандидат-сет №1)
09:33:02           artifact 38 (UC-2) updated — repair-автор правит общий файл
09:33:57           автор: done (кандидат-сет №2 запечатан ≤09:34:01, author-гейт accepted)
09:34:16           artifact 37 (UC-1) мутирован upsert'ом (draft, новый content_hash)
09:34:50           final-гейт ACCEPTED сет №2 → post-acceptance effect сверяет живую
                   строку artifacts с запечатанным хэшем → HASH_DRIFT (throw)
```

**Гипотеза (механика).** Два разнесённых хранилища: запечатанный (sealed) кандидат-сет,
который смотрит гейт, и мутируемая строка `artifacts`, которую сверяет post-acceptance
effect. Ремонт-автор отредактировал draft-артефакт **между запечатыванием сета и вторым
accept-гейтом** (~49 сек окно). Effect — первый и последний компаратор, и он бросает
исключение, хотя реестр эффектов поддерживает `repair_required`.

**Где мог возникнуть дефект (по чтению кода):** upsert draft-артефакта, уже входящего в
запечатанный кандидат-сет, не ограждён (`src/tools/artifacts.ts`, upsert-ветка); эффект
`formalization-accept-products-effect.ts` возвращает void и кидает throw вместо
`repair_required`. Гипотеза о вкладе: движок ~60%, протокол воркера (правка после
submission) ~35%, ревью ~5%. **Фиксы 4f6c9190 этот шов, по нашей оценке, не закрыли** —
они ограждают transition-obligations, а не строки artifacts.

**Почему прошёл только P02:** он единственный получил changes_requested на
формализационных артефактах в этом окне. Его слабейший в пятёрке proposal (18/25) коррелирует
с ремонтной активностью (workplace revision 15 против 4 у «чистых» проходов, 150 node_runs
с attempt до 59) — слабый материал → больше repair → больше экспозиция к окну гонки.
Repair сам по себе не фатален: themes имел repair_required и прошёл.

### 2.2 TB-8 — P07 snake, silent terminal fail на freeze-acceptance-baseline

**Где возникла гипотеза.** Внешне — «идеальный» прогон (proposal 23/25, 0 repair, 0 lost,
все 10/10 карточек done, все артефакты accepted, все workplace'ы terminal/accepted), но
lifecycle завершился `terminalStatus:"failed"`, `lastError:null`. Единственная зацепка —
`production_envelope` node_run 2460 (`freeze-acceptance-baseline`, event `domain.failed`):
`"atomic acceptance artifact 'AC-NFR-1.1' has no matching document heading"`.

**Важная коррекция собственной первой версии.** Изначально я записал в BUGS, что в
документе нет заголовка с кодом. Это НЕВЕРНО: заголовок в
`repos/snake/docs/requirements/REQ-001-snake/03-acceptance-criteria.md:399` есть и
корректен (`## AC-NFR-1.1: Offline Operation — Local Filesystem`). Запись в BUGS исправлена.

**Гипотеза (механика).** Регулярка парсера заголовков AC-документа
(`src/modules/formalization/domain/acceptance-criterion-document.ts:9`):

```
/^(#{2,3})\s+(AC-[A-Za-z0-9]+(?:\.[A-Za-z0-9]+)*):\s+(.+?)\s*$/gm
```

допускает в сегментах кода только буквы/цифры/точки — **дефис не входит**. Код `AC-NFR-1.1`
не матчится регуляркой вообще; при этом 34 плоских `AC-N` матчатся → parsed непуст →
fallback «использовать artifact.code как атомарный критерий» не срабатывает → throw →
kernel-узел (без repair-цикла) терминит стадию. Ошибка попадает только в bindings
production-конверта — в `stage_runs.error`/`lastError`/логи не попадает (silent).

**Где мог возникнуть дефект:** грамматика кода при `artifact_create` свободная (любая
строка), грамматика парсера — уже́е; первый строгий чекер — терминальный kernel-узел.
Та же узкая regex, по нашей оценке, продублирована в development-стадии
(`src/modules/development/infrastructure/sqlite-development-verification-adoption.ts:486`) —
проект мог бы пройти formalization и упасть позже в W3. Вклад: движок ~75%, протокол
воркера (самовольная иерархическая нумерация) ~20%, ревью ~5%.

**Почему упал только snake:** единственный проект партии, где модель завела
иерархические коды `AC-NFR-x.y` (8 из 42 AC). Все 5 прошедших использовали плоские `AC-N`.

### 2.3 Почему большинство прошло (сводно)

Оба механизма требуют редкого совпадения: TB-6 — правка draft строго в ~49-сек окне между
seal и final-гейтом; TB-8 — дефисная схема нумерации AC. Ни один фейл не объясняется
«плохим проектом» в целом: P02 был слабейшим по proposal, но P07 — одним из лучших.

### 2.4 Прогноз и ранние признаки (для мониторинга)

Прогноз до фиксов: ещё ~2–4 фейла на P08–P20. Повышенный риск: **P11 markdown** (proposal
16/25 — по обоим механизам), крупные AC-деревья L/XL/XXL (mars, sudoku, tetris, sheets,
elite, mario3d, interp) — по TB-8.

Ранние признаки (наблюдаемы read-only из БД):
1. workplace revision ≥ 10 (P02: 15; чистые: 4);
2. node_run attempt > 20 на одном node_id (P02: до 59);
3. draft-артефакт с `updated_at` позже последнего accept-гейта своего эпика;
4. AC ≥ 30 и/или NFR-AC ≥ 2 перед freeze; иерархические (`AC-XXX-n.m`) коды AC;
5. `freeze-acceptance-baseline` в factory_node_runs со статусом failed — смотреть
   production_envelope (единственное место, где видна причина).
