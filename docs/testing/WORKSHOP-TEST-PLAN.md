# По-цеховое E2E-тестирование конвейера saga4 — мастер-план

Статус: план согласуется. Дата: 2026-08-15. Ветка: saga4.

## 1. Цель

Измерить **стабильность и качество каждого цеха отдельно** на 20 проектах
возрастающей сложности, прогнав их каскадом в **одной общей БД**
(наблюдение через один фронт `localhost:4321`):

```
Раунд W1: 20 × Discovery            → анализ (границы в общей БД)
Раунд W2: 20 × resume → Formalization → анализ
Раунд W3: 20 × resume → Development   → финальный отчёт
```

Между раундами restore не нужен: состояние всех проектов накапливается
в одной БД (§4.2); снапшоты — защита и перезапуски.

Окружение фиксировано: модель `qwen/qwen3.6-35b-a3b` (LM Studio, :1234),
**параллелизм строго 1 везде**, локальный запуск, БД-на-прогон.

## 2. Почему по-цехово (точечно)

1. **Атрибуция отказов.** При сквозном прогоне сбой в цехе 2 может быть
   следствием мусора из цеха 1. Изолированный раунд с замороженным входом
   даёт однозначный ответ: дефект принадлежит этому цеху.
2. **Статистика по цеху.** 20 запусков на одну и ту же границу входа/выхода —
   это pass-rate, время, число repair-циклов и lost-воркеров **в пересчёте на
   цех**, а не «в среднем по конвейеру».
3. **Стоимость.** Discovery — минуты, Development — часы. Гонять 20 сквозных
   прогонов, чтобы узнать, что Discovery сыплется, — потеря десятков часов
   GPU/времени. Cascade: дешёвые цехи сначала.
4. **Воспроизводимость.** Капсула на входе = байт-в-байт одинаковый вход для
   отладки: баг-репорт цеха N содержит точный входной снапшот БД.
5. **Каскадные эффекты качества.** Семантический дефект артефакта (пример из
   mars-ballistic: FR-2 «высота орбиты», не потребляемая формулами RULE-2)
   виден как дефект цеха 2, а не «где-то потом сломалось».

## 3. Почему порядок 1 → 2 → 3

1. **Контрактная цепочка.** Цех N потребляет immutable-сертификат цеха N-1
   (ProductRef + hash). Тестировать цех 2 без капсул цеха 1 невозможно —
   вход был бы фиктивным.
2. **Мусор не должен течь вперёд.** Если цех 1 нестабилен, метрики цеха 2 —
   шум. Сначала фиксируем/принимаем цех 1, потом сигнал цеха 2 чист.
3. **Капсулы — это тестовые ассеты.** Выход каждого раунда — 20
   воспроизводимых входов для следующего; ассеты накапливаются, их можно
   реиспользовать для регрессий, A/B моделей, replay.
4. **Экономика с ранним выходом.** Go/No-Go гейт после каждого раунда:
   нестабильность ниже порога → чиним, не запуская следующий раунд.

## 4. Одна БД, один фронт, механика капсул (главное)

### 4.0 Архитектура пространства

Все 20 проектов живут в **одной БД** `.factory-testbed/factory.sqlite`;
**один трекер** на порту 4321 обслуживает её всю сессию. Доска проекта:
`http://localhost:4321/?project=<id>`. Никаких песочниц-на-прогон.

Следствия:
- Проекты стартуют/останавливаются/возобновляются **по одному** (rate=1),
  строго последовательно — движок на эпик, через API трекера.
- `factory.mjs resume` НЕ используется: он резолвит project 1 (песочница).
  Resume в общей БД — `POST /api/factory/start {"project_id": N}`
  (форма «Возобновить заказ завода» в /admin) или Start на доске проекта.
- Модель пишется per-epic (`lifecycle_execution_controls`, каждый проект —
  свой epic) → у каждого проекта своя строка контроля.

### 4.1 Каталоги

```
.factory-testbed/
  factory.sqlite                    — ЕДИНАЯ БД всех 20 проектов
  snapshots/                        — снапшоты всей БД (перед раундами)
    W1-round-start.sqlite           — до начала раунда W1
    W2-round-start.sqlite           — до начала раунда W2 (внутри все 20 прошли W1)
    reruns/<PID>-<round>-<date>.sqlite — для перезапусков отдельных проектов
  runs/<PID>/journal.md             — детальный журнал проекта
  docs/testing/projects.json        — список проектов (в git)
```

### 4.2 Капсула = сама долговременная БД

При последовательных раундах **восстановление между цехами не нужно**:

```
Раунд W1: P1..P20 по очереди: старт → граница Discovery → стоп.
          БД накапливает 20 lifecycle-ов с завершённым Discovery.
Раунд W2: тот же трекер, resume каждого проекта (project_id) →
          движок продолжает с Formalization. Никаких restore.
Раунд W3: аналогично из состояния после W2.
```

Снапшоты — только защита и перезапуски:
- **перед каждым раундом**: `wal_checkpoint(TRUNCATE)` + копия всей БД в
  `snapshots/<round>-start.sqlite` (бесплатно: артефакты — текст, БД лёгкая);
- **перезапуск одного проекта в цехе N** (после фикса): копия
  `snapshots/<N>-round-start.sqlite` → `reruns/<PID>-...sqlite`, в копии
  resume ТОЛЬКО этого проекта (lifecycle-и независимы), при необходимости
  `restore-from-checkpoint.mjs --reset-stage <stage>` в копии.

### 4.3 Старт проекта (harness, Phase 0)

Публичный gateway `/api/factory/start {idea_url}` требует **публичный
HTTPS** (private-адреса запрещены — проверено, `product-idea-source.mjs`).
Локальные идеи идут через app-слой напрямую (как factory.mjs, но per-project):

1. INSERT project + repository + epic (идея текстом, как в admin new-flow);
2. `configureFactoryControl(db, epicId, {provider:'lmstudio', model:'qwen/qwen3.6-35b-a3b', effort:null, limit:1}, concurrency=1)` —
   **до** первого claim: это полностью убирает гонку KI-3;
3. `startProductLifecycleFromIdea({projectId, epicId, idea, ...})` →
   background-движок эпика;
4. далее — поллинг границы (§4.4).

### 4.4 Остановка на границе цеха

Встроенного «stop-after-stage» нет. Harness обязан:

1. поллить каждые ~5с: terminal-статус stage цеха N + создание следующего
   stage_run (в scope текущего lifecycle);
2. при переходе — `POST /api/factory/stop {"epic_id": N}` (трекер жив);
3. **известная гонка:** движок мог успеть заклеймить первую карточку
   следующего цеха. Штатно: stop убивает воркера; следующий resume стартует
   с `--resume-worker-loss`-эквивалентом через supervision; если workplace
   завис в repair-budget pause — `factory.mjs continue`/app-layer эквивалент
   `resumeWorkerLossWorkplace` (harness вызывает его напрямую по БД — тот же
   приём, что и resume, но per-project);
4. капсульной точкой считается **чистая граница**: следующий stage_run
   существует, его workplaces пусты/не клеймятся.

### 4.5 Что считается «выходом из цеха» (критерий границы)

| Цех | Terminal-условие stage | Артефакты на выходе |
|---|---|---|
| W1 Discovery | stage `initial-discovery` completed; создан stage `solution-formalization` | discovery certificate (outcome=go), accepted proposal, readiness |
| W2 Formalization | stage `solution-formalization` completed | Solution Contract: accepted brief/PRD/FR/NFR/RULE/UC/AC/SRS, 100% trace, frozen baseline hash |
| W3 Development | stage `solution-development` completed | verified integration bundle, код в product-repo, verification evidence |

## 7. Метрики раунда

### Стабильность (авто, на каждый прогон)
- outcome: pass / fail(код) / stuck; wall time
- worker-executions: всего, lost, repairs, spawn-failures
- engine restarts (включая spin-зависания — known issue KI-1)
- восстановимости: сработал ли plain resume / `--resume-worker-loss`

### Качество (рубрика)
- **W1**: proposal — покрытие идеи, измеримость гипотезы, schema-валидность (1–5)
- **W2**: counts (PRD≥1, FR≥3, UC≥2, AC≥FR-покрытия); trace-покрытие AC→{FR|NFR|RULE} и AC→UC = 100%;
  baseline hash заморожен; **семантический спот-чек**: выборочно 1 из 5 проектов — полный ручной
  ревью на классы дефектов (внутренние противоречия, входы без потребителей, непроверяемые NFR)
- **W3**: репо билдится/открывается; каждая AC имеет evidence; все projected tasks terminal;
  integration merged; settlement verified

### Пороги Go/No-Go
- W1 → W2: ≥16/20 (80%) pass и нет критических багов движка на границе
- W2 → W3: ≥16/20 pass И trace-покрытие 100% у ≥17 проектов; семантический спот-чек ≤1 фатального дефекта/проект
- Ниже порога: стоп, фикс, повтор раунда только упавших проектов из капсул предыдущего раунда

## 9. Фазы работ

- **Phase 0 — harness (до первого раунда).** Скрипт `scripts/testbed-run.mjs`:
  1) провиженинг проекта в общую БД (project+repo+epic+control `lmstudio/qwen/limit 1`
     ДО первого claim — убивает гонку KI-3) + `startProductLifecycleFromIdea`;
  2) поллинг границы цеха → `POST /api/factory/stop {epic_id}`;
  3) чистка грязной границы (`resumeWorkerLossWorkplace` per-project);
  4) снапшот БД перед раундом; 5) запись в журнал. Плюс watchdog KI-1
  (лог движка молчит >3 мин при живом процессе → рестарт эпика).
  Обкатка: сквозной smoke на P01 (W1→W2→W3 подряд).
- **Phase 1 — раунд W1 (20 прогонов).** После каждого — журнал; после всех — сводка
  стабильности + выборочный семантический ревью, No-Go гейт.
- **Phase 2 — раунд W2.** Вход из C1-капсул. Дольше (9–11 карточек/проект).
- **Phase 3 — раунд W3.** Самый долгий; допускается ночными батчами (rate=1 сохраняется).
- **Phase 4 — итоговый отчёт**: стабильность по цехам, порог сложности модели,
  топ багов, рекомендации (модель/промпты/профили).

## 10. Known issues на старте (базовая линия, из mars-ballistic)

- **KI-1**: движок может уйти в 100% CPU спин в синхронной секции (инцидент
  19:38 2026-08-13, лог замер на polls=200). Лечение — kill+resume; для harness:
  watchdog «нет строк лога > 3 мин при живом процессе» → авто-рестарт.
- **KI-2**: qwen галлюцинирует о своём toolset («no Write tool» при наличии) —
  сжигает время, но обходит через MCP-путь. Метрика: доля лишних ходов.
- **KI-3**: гонка первого claim при старте (облачный профиль до флипа) — в тестбеде
  закрывается порядком: модель/set ставится СРАЗУ после provisioning до первого
  claim, при проигрыше — kill+resume (процедура §4b quickstart).
- **KI-4**: LM Studio Jinja-патч обязателен (см. CLAUDE.md); перед каждым раундом — смоук.
