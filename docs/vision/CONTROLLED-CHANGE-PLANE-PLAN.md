# Controlled Change Plane — план инкрементальной реализации (C0–C13)

План-разбор концепции «Controlled Change Plane» v0.1 (2026-08-17) на
последовательность узких производственных релизов. Концепция ставит
целью управляемую плоскость изменений над принятым состоянием продукта;
этот документ переводит её в исполняемую лестницу задач с инвариантами,
тестами и exit-гейтами.

- **Дата:** 2026-08-17
- **Источник:** концепт «Controlled Change Plane. General Concept,
  Target Architecture, and Incremental Delivery Roadmap», v0.1.
- **Статус:** план к реализации; очередность C0→C13 обязательна.
- **Привязка к репо:** C0 = завершение программы ADR-053/073
  (точный presentation cutover: epic-scoped readers, newest-wins биндер,
  resume без implementation-дайджестов — см.
  `ideas/2026-08-17-verdict-reconciliation.md` §1 п.4).
- **Уточнение от 2026-08-17:** ядровая часть C0 разложена в отдельную
  программу Saga Core Renewal K0–K20 — см.
  `SAGA-CORE-RENEWAL-PLAN.md`. K0–K20 — нормативный путь до Core 3.0 GA;
  после него C0 становится коротким integration-acceptance-релизом и
  больше не владеет core-очисткой (см. §12 этого плана).

---

## 1. Тезис и целевая архитектура

**Тезис:** завод исполняет не генерацию артефактов, а управляемые,
тестируемые переходы от одного принятого базлайна продукта к следующему.

Целевой поток:

```
Change Request → Change Desk → Change Compiler
  → Baseline Resolver + Policy/Authority
  → Impact & Closure Engine
  → Versioned Change Package
  → Selective Production Graph
  → Workcells / Agents / Solvers / Humans
  → Candidate Configuration + Evidence
  → Reconciliation & Assurance
  → Atomic Baseline Commit → Baseline N+1
```

Граница авторитета: **AI предлагает — ядро распоряжается.** Агенты
интерпретируют намерение, предлагают цели/зависимости, объясняют
последствия. Детерминированное ядро владеет идентичностью, переходами
состояний, свежестью доказательств, правилами замыкания, авторитетом и
коммитом базлайна.

**Принцип доставки:** ни один релиз не вводит AI в
correctness-critical путь, пока тот же путь не работает на явном
структурированном вводе и детерминированной валидации.

Финальное правило замыкания (справочно, достигается к C8–C9):

```
ChangeClosed = ImpactClosureComplete
  AND NoStaleAcceptedArtifacts
  AND NoDanglingActiveReferences
  AND RequiredEvidenceComplete
  AND RequiredAuthoritySatisfied
  AND AtomicBaselineCommitSucceeded
```

## 2. Незыблемые правила плана

### 2.1 Монотонная лестница гарантий

Каждый релиз добавляет ровно одну новую гарантию и сохраняет все
предыдущие. Автоматизация позже может снижать труд оператора, но не
имеет права ослаблять семантику идентичности, доказательств, замыкания
и авторитета.

```
Точная идентичность → Иммутабельные базлайны → Запись изменений
  → Явный scope → Атомарный successor → Генерируемая трассируемость
  → Свежесть доказательств → Детерминированный импакт
  → Замыкание → Селективное исполнение → AI-помощь → Domain packs
```

### 2.2 Одна сложная проблема на релиз

- Не вводить новую модель базлайна и NL-агента в одном релизе.
- Не вводить хранение трасс и транзитивное замыкание в одном релизе.
- Не вводить enforcement замыкания и селективное планирование в одном
  релизе.
- Не вводить generic domain SDK и первый инженерный домен в одном
  релизе.
- Не совмещать correctness-фичу с широким рефакторингом/переименованием.
- Если новый инвариант нельзя протестировать без мокания самого
  инварианта — релиз слишком широк.

### 2.3 Прогрессия режимов эксплуатации

Record-only → read-only projection → shadow analysis → manual
enforcement → deterministic automation → AI-assisted → domain-extensible.
Каждый релиз в таблице ниже закреплён в одном режиме.

### 2.4 Канонический сценарий (общий фиксстур для всех релизов)

> **Вывести из эксплуатации принятую legacy-функцию экспорта, сохранив
> новый путь экспорта и историческую трассируемость.**

Стартовый базлайн N: требование REQ-LEGACY-EXPORT, архитектурное решение
ADR-LEGACY-EXPORT, backend-модуль `legacy-export.ts`, экшен UI
«Export legacy format», флаг `legacyExportEnabled`, регрессионный тест
`legacy-export.spec.ts`, раздел user guide «Legacy export», CheckReceipt
старой реализации. Каждый релиз добавляет к фикстуре только новое
поддержанное поведение. Фикстура остаётся минимальной — это не
мини-репозиторий, а доказательство переходов состояний.

## 4. Детальные карты релизов

Формат карты един для всех релизов. **Exit gate копируется в задачу
агента-исполнителя дословно** (правило §8.3 концепта).

---

### C0 — Authority Ratchet

- **Гарантия:** принятая ссылка на материал разрешается в одну и только
  одну lifecycle-scoped ревизию. Ambiguity идентичности исключена до
  появления любых change-фич.
- **Режим:** internal hardening, включён везде после миграции.
- **Сущности:** `AcceptedAuthorityHead`, `ResumeCompatibilityFingerprint`.
- **Бэклог в репо:** это финиш программы ADR-053/073.

Задачи:

- [ ] Accepted-чтения только по точным ссылкам (lifecycle, workplace,
      accepted revision).
- [ ] Убрать newest-wins и epic-scoped выборку принятого материала из
      correctness-critical путей.
- [ ] Resume-совместимость включает дайджесты: реализации хендлера,
      схемы, check-плана.
- [ ] Идемпотентность accepted authority head: та же ревизия не может
      указывать на разные output refs / решения.
- [ ] Factory-only architecture ratchet-тест: падает при появлении
      legacy acceptance-путей.

Инварианты:

1. Ссылка на принятый материал → ровно одна lifecycle-scoped ревизия.
2. Resume отвергается при изменившейся реализации/контракте, даже при
   совпадающих логических именах хендлеров.
3. Повторный accepted commit: либо побитово идентичен и идемпотентен,
   либо отвергнут как нарушение инварианта.

Тесты: 3+ lifecycle (N не может взять материал N-1/N-2); resume при
неизменном logicalId и изменившемся дайджесте; дубль-коммиты
(идентичный/конфликтный); crash/replay вокруг acceptance и
post-acceptance effects; статический тест отсутствия epic-scoped
accepted readers в production path.

Не-цели: нет Baseline, ChangeIntent, impact-графа, UI change-flow,
рефакторинга оркестрации.

**Exit gate:**
- Все acceptance paths используют точную lifecycle-scoped идентичность.
- Third-lifecycle regression постоянно покрыта тестами.
- CI исполняет ratchet-тест на точном коммите.
- Существующие сценарии завода зелёные без compatibility fallbacks в
  authority path.

---

### C1 — Baseline Registry

- **Гарантия:** иммутабельный, восстанавливаемый снапшот принятого
  состояния продукта; исполнение работ не меняется.
- **Режим:** read-only production.
- **Сущности:** `Baseline`, `BaselineManifest`.

Задачи:

- [ ] Минимальный агрегат Baseline: `baselineId`, `parentBaselineId`,
      ссылки на принятые артефакты, ссылка на lifecycle, content digest,
      ссылка на решение о создании.
- [ ] Автосоздание Baseline при final acceptance существующего lifecycle.
- [ ] list / show / export через минимальный существующий API/CLI.
- [ ] Детерминированный упорядоченный manifest (то же состояние → тот
      же дайджест).
- [ ] Compatibility-адаптер: текущие accepted outputs → записи Baseline.

Инварианты: Baseline иммутабелен после создания; каждый артефакт —
точная принятая ревизия; дайджест детерминирован и не зависит от порядка
в storage; Baseline восстанавливается без обращения к newest state.

Тесты: детерминированность дайджеста при перемешанной вставке;
иммутабельность (update/delete отклоняются); реконструкция после
рестарта процесса; миграция текущего принятого lifecycle; export/re-import
round-trip.

Не-цели: нет change-семантики parent→child (только опциональная ссылка),
графа зависимостей, редактирования/ветвления базлайнов, автоматического
diff сверх added/removed/changed.

**Exit gate:**
- Каждый новый принятый lifecycle даёт ровно один Baseline.
- Инженер поддержки может инспектировать, какие точные артефакты
  образуют поставленное состояние.
- Создание Baseline идемпотентно при retry/replay.
- Фича отключаема без влияния на исполнение.

---

### C2 — Change Ledger

- **Гарантия:** change requests — первоклассные версионируемые записи
  до какого-либо влияния на исполнение.
- **Режим:** record-only.
- **Сущности:** `ChangeIntent`, `ChangeIntentRevision`.

Задачи:

- [ ] ChangeIntent: `changeId`, `baseBaselineRef`, title, rationale,
      requestedBy, acceptance criteria, state.
- [ ] Только структурированный ввод (API/CLI), **без LLM**.
- [ ] Стейт-машина: draft → submitted → approved | rejected | cancelled.
- [ ] После approval `baseBaselineRef` и операции заморожены; поправки =
      новая ревизия ChangeIntent.
- [ ] Все переходы — события с actor и reason.

Инварианты: approved change привязан ровно к одному точному базлайну;
approved intent не редактируется молча; reject/cancel сохраняют историю;
запись изменения сама не мутирует артефакты.

Тесты: таблица переходов; неавторизованные переходы; иммутабельность
после approval; event replay восстанавливает состояние; валидация
(нет базлайна / rationale / AC).

Не-цели: нет списка целей, плана исполнения, импакта, NL-интерпретации.

**Exit gate:**
- Изменения создаются, ревьюятся, одобряются/отклоняются/отменяются в
  production.
- Каждый approved change имеет валидный иммутабельный базовый Baseline.
- Исполнение approved change невозможно (поддержка исполнения ещё не
  существует — намеренно).
- Ledger полностью восстанавливается из событий.

### C3 — Explicit Scope

- **Гарантия:** человек перечисляет точные артефакты для
  add/modify/replace/retire/recheck; автоматического discovery нет.
- **Режим:** manual planning + approval.
- **Сущности:** `ChangeOperation`, `ExplicitTarget`, `ProposedDisposition`.

Задачи:

- [ ] Типы операций: add, modify, replace, retire, recheck.
- [ ] Явные цели (ArtifactRefs / стабильные semantic IDs) в approved
      ревизии ChangeIntent.
- [ ] По одному proposed disposition на каждую цель.
- [ ] Plan-preview projection: базовый Baseline, операции, ожидаемое
      целевое состояние, acceptance criteria.
- [ ] Отклонение дублирующих/противоречивых операций на одной цели.

Инварианты: scope явен и ревьюится до работ; у каждой цели ровно одна
активная операция и один disposition; retire убирает элемент только из
successor Baseline, никогда из исторических; система не заявляет
полноту явного scope.

Тесты: валидация всех операций; противоречия; семантика retire с
сохранением истории; golden plan-preview; approval — scope не меняется
без новой ревизии ChangeIntent.

Не-цели: нет auto-discovery, trace matrix, исполнения цехов, AI.

**Exit gate:**
- Канонический legacy-export change полностью выражается явными
  операциями.
- Ревьюер понимает целевое successor-состояние до запуска работ.
- Исторические Baselines разрешаются после планирования retire.
- Все тесты планирования используют точные ссылки, не эвристики имён
  файлов.

---

### C4 — Atomic Successor Baseline — первый операционный MVP

- **Гарантия:** ручной scoped change исполняется заводом и коммитит
  иммутабельный successor Baseline.
- **Режим:** manual controlled production.
- **Сущности:** `ChangePackage`, `BaselineTransition`, `TransitionReport`.

Задачи:

- [ ] ChangePackage — контейнер исполнения одной approved ревизии
      ChangeIntent.
- [ ] Узкий адаптер: операции → существующие workplaces и production
      cells Saga4.
- [ ] Неизменённые артефакты переносятся точной ссылкой; изменённые
      заменяются только после acceptance; retired исключаются из
      successor manifest.
- [ ] Baseline N+1 с `parentBaselineRef = N` одним compare-and-swap
      коммитом.
- [ ] Идемпотентный retry: candidate production → gate decision →
      baseline commit → post-commit effects.
- [ ] Минимальный transition report: added / changed / retired /
      unchanged refs.

Инварианты: принятый Baseline не модифицируется на месте; successor
коммитится атомарно или не коммитится вовсе; reuse неизменённого —
только точная принятая ссылка; каждая явная операция разрешена до
коммита; отказ post-commit публикации не стирает успешное решение о
базлайне.

Тесты: e2e-вывод legacy-export из эксплуатации; crash до/во время
коммита и retry-после-коммита; CAS-конфликт при сдвинувшемся head;
partial failure (нет полу-записанного successor); replay даёт тот же
дайджест и report; исторический lookup — retired фича видна в parent.

Не-цели: нет заявлений о полноте scope, графа, инвалидации
доказательств, селективного планирования сверх явного списка, NL-входа.

**Exit gate:**
- Оператор подаёт approved explicit change и получает Baseline N+1.
- Полный переход replay-ится и аудируется.
- Ни один режим отказа не смешивает accepted outputs разных lifecycles.
- MVP применим для малых тщательно scoped внутренних software-изменений.

### C5 — Trace Graph и генерируемая матрица

- **Гарантия:** трассируемость — авторитетные типизированные данные,
  а не ручные документы.
- **Режим:** read-only projection (без enforcement импакта).
- **Сущности:** `ArtifactManifest`, `TraceEdge`, `GraphDelta`,
  `TraceProjection`.

Задачи:

- [ ] ArtifactManifest для принятых артефактов: стабильная семантическая
      идентичность, provides / consumes / satisfies / verifiedBy /
      supersedes / declared dependencies.
- [ ] Типизированные TraceEdge с provenance, source revision, authority
      state.
- [ ] Явные manifests авторятся рядом с текущими software-артефактами.
- [ ] Генерация trace matrix и current-state отчётов из принятого
      Baseline + рёбер.
- [ ] Рёбра версионируются через baseline transitions; принятые
      исторические рёбра не редактируются.

Инварианты: матрица — проекция, не отдельный источник правды; каждое
активное ребро разрешается в точные ревизии; исторические Baselines
хранят действовавшее на момент acceptance состояние графа; изменения
графа входят в candidate layer и принимаются тем же переходом базлайна,
что и артефакты.

Тесты: детерминированная генерация; no-dangling-active-edge;
исторические проекции parent/successor; приём/отклонение GraphDelta;
round-trip manifest → graph → matrix.

Не-цели: нет auto-extraction зависимостей, транзитивного импакта,
генеративной перезаписи нарративных документов, обязательности graph
DB.

**Exit gate:**
- Канонический сценарий выдаёт trace matrix без ручных правок.
- Изменение принятых trace-данных требует управляемого GraphDelta.
- Один и тот же Baseline всегда даёт одну и ту же матрицу.
- Операторы сравнивают проекции Baseline N и N+1.

### C6 — Evidence Freshness

- **Гарантия:** новый Baseline не считает старые проверки валидными,
  если изменился их точный субъект или заявленные входы.
- **Режим:** manual enforcement — ядро блокирует коммит при
  stale/missing обязательных доказательств.
- **Сущности:** `EvidenceBinding`, `EvidenceState`, `EvidenceObligation`.

Задачи:

- [ ] CheckReceipt привязан к: точной ревизии субъекта, ревизиям
      входов, дайджесту check-плана, дайджесту toolchain, результату.
- [ ] Детерминированные правила свежести: смена субъекта / заявленного
      входа / check-плана / реализации инструмента.
- [ ] Состояния: fresh, stale, superseded, waived, not-required.
- [ ] Каждая изменённая или reuse-нутая цель удовлетворяет evidence
      policy до successor-коммита.
- [ ] Отчёт свежести доказательств для перехода.

Инварианты: доказательство не свежее при изменившейся ревизии субъекта;
не свежее при изменившемся обязательном входе или реализации проверки;
waiver — явное решение авторитета, не состояние, молча назначаемое
движком; коммит базлайна падает при неразрешённых доказательствах.

Тесты: truth-table всех правил свежести; same-content-different-reference
и same-reference-different-digest; инвалидация при апгрейде check-плана
и toolchain; авторизация waiver; e2e — код изменён, предъявлен старый
receipt.

Не-цели: нет автопланирования recheck, транзитивного импакта,
AI-оценки достаточности, модели квалификации ревьюеров сверх гейтов.

**Exit gate:**
- Канонический сценарий не коммитится с receipt предыдущей ревизии
  backend.
- Оценка свежести детерминирована и replay-има.
- Отчёты называют точную причину устаревания.
- Legacy receipts либо мигрируются с точными привязками, либо помечены
  unknown — никогда не считаются fresh.

### C7 — Direct Impact Preview

- **Гарантия:** одношаговые последствия считаются из принятых
  заявленных рёбер; execution scope автоматически не меняется.
- **Режим:** shadow analysis, затем advisory production.
- **Сущности:** `ImpactRecord`, `ImpactDecision`.

Задачи:

- [ ] ImpactRecord на каждое прямое исходящее ребро из явной цели
      изменения.
- [ ] Классификация: artifact / evidence / trace / release /
      human-decision impact.
- [ ] Показ пути и правила, породивших каждый finding.
- [ ] Оператор: accept / reject / defer с reason.
- [ ] Scope неизменен, пока новая approved ревизия ChangeIntent не
      включит finding.

Инварианты: каждый finding объясним точной тройкой
target-edge-rule; shadow-находки не расширяют молча активный
ChangePackage; отвергнутый finding — записанное решение, не удаление;
нет заявлений о транзитивной полноте.

Тесты: one-hop обход каждого типа рёбер; golden explanation path;
цикл — preview завершается немедленно; состояния finding; shadow не
влияет на successor Baseline.

Не-цели: нет транзитивного замыкания, авто-disposition, роста scope
во время исполнения, inferred/AI-рёбер.

**Exit gate:**
- Каноническое изменение находит прямо связанные UI, тесты, доку
  и доказательства, когда связи заявлены.
- Каждый finding несёт человекочитаемый путь объяснения.
- Shadow-результаты стабильны при replay.
- Ничто не блокируется только advisory-находкой.

---

### C8 — Transitive Impact Closure и Dispositions

- **Гарантия:** детерминированный fixed-point импакт по принятым рёбрам;
  явная обработка каждого затронутого узла.
- **Режим:** enforced planning до исполнения.
- **Сущности:** `ImpactClosure`, `Disposition`, `ClosureDecision`.

Задачи:

- [ ] Fixed-point обход по малому одобренному набору правил
      распространения рёбер.
- [ ] Dispositions: regenerate, recompute, recheck, rebind, retire,
      reuse-with-proof, human-decision, authorized-waiver.
- [ ] ImpactClosure версионируется внутри ChangePackage.
- [ ] Каждый затронутый узел — ровно один валидный disposition до
      approval исполнения.
- [ ] Change Closure gate: отвергает неразрешённые узлы, stale
      evidence, dangling active references.

Инварианты: обход завершается и даёт одно замыкание для одного
Baseline + change + набора правил; у каждого узла один явный
disposition; reuse — только с детерминированным proof применимости или
авторизованным человеческим решением; неизвестный импакт — obligation,
не «нет импакта»; активное замыкание не меняется без новой ревизии
ChangePackage.

Тесты: fixed-point на chains/diamonds/cycles/disconnected;
property-based (идемпотентность, монотонность, независимость от
порядка обхода); полнота dispositions; fail-closed для unknown;
closure-gate e2e с одним намеренно неразрешённым документом; большой
синтетический граф — базовый perf-бюджет.

Не-цели: нет автопланирования производства, inferred-рёбер,
параллельных change-веток, авто-генерации waiver.

**Exit gate:**
- Каноническое изменение даёт стабильное транзитивное замыкание и не
  идёт дальше с неназначенным узлом.
- Все правила распространения явные, версионируемые, покрыты
  table-driven тестами.
- Замыкание ревьюится до старта любого workcell.
- Выключенный feature flag возвращает поведение C7 без потери данных.

---

### C9 — Selective Re-execution — Change Engine v1

- **Гарантия:** одобренное замыкание компилируется в минимальный
  production graph; результат коммитится одним изменением.
- **Режим:** deterministic automation при человеко-одобренных scope и
  замыкании.
- **Сущности:** `ResolutionBinding`, `SelectiveExecutionPlan`,
  `ReleaseDossier`.

Задачи:

- [ ] Маппинг dispositions на существующие production cells и check
      providers.
- [ ] Селективный граф исполнения: только затронутые работы,
      обязательные координационные join'ы, требуемые гейты.
- [ ] Незатронутые артефакты и свежие доказательства — перенос точной
      ссылкой.
- [ ] Пересчёт/recheck строго по одобренному замыканию.
- [ ] Персистентный маппинг ImpactRecord → разрешивший workcell/решение.
- [ ] Release dossier: intent, замыкание, dispositions, произведённые
      ревизии, доказательства, решения, финальный дайджест Baseline.

Инварианты: workcell вне одобренного замыкания не изменяет successor
Baseline; каждый пункт замыкания разрешён точным артефактом, receipt,
retirement, proof или решением авторитета; неизменённые принятые
артефакты не регенерируются ради удобства оркестрации;
crash/retry/resume не дублируют принятую работу и не смешивают выходы
lifecycles; dossier генерируется из авторитетного состояния, не пишется
вручную постфактум.

Тесты: e2e селективное исполнение канонического изменения; незатронутый
модуль не планируется и его точная ревизия reuse-ится; отказ workcell,
переназначение, resume, финальный коммит; полнота
impact→resolution; детерминированная генерация dossier; мутационный
тест — вне-scope workcell пытается опубликовать accepted artifact.

Не-цели: нет NL-входа, агентных trace-ссылок сверх поддерживаемых
candidate outputs, auto-discovery скрытых зависимостей, не-software
абстракций.

**Exit gate:**
- Каноническое изменение проходит Baseline N → N+1 на детерминированном
  замыкании и селективном исполнении.
- Dossier объясняет каждый изменённый/оставленный/retired объект.
- Fault-injection покрывает отказы до, во время и после коммита.
- Релиз стабилен для повторного внутреннего production-применения на
  ограниченных software-изменениях.

### C10 — Natural-Language Change Desk

- **Гарантия:** снижение стоимости создания структурированных
  ChangeIntent без передачи AI авторитета над scope/коммитом.
- **Режим:** AI-assisted entry, подтверждение человеком обязательно.
- **Сущности:** `ChangeIntentProposal`, `AmbiguityRecord`,
  `ModelObservation`.

Задачи:

- [ ] LLM-фронтенд → кандидат схемы ChangeIntent, список неоднозначностей,
      допущений, предлагаемых acceptance criteria.
- [ ] Цели кандидата разрешаются только в semantic IDs или точные
      refs; неразрешённое — явные вопросы/obligations.
- [ ] Запись наблюдений: модель, дайджест prompt-пакета, вход, выход,
      результат валидации.
- [ ] Человек подтверждает структурированное изменение до входа в
      путь C2–C9.
- [ ] Детерминированный diff между текстом пользователя и итоговыми
      структурированными операциями.

Инварианты: выход модели — всегда кандидат, никогда approved intent;
невалидный/двусмысленный вывод fail-closed; апгрейд модели не меняет
approved ChangeIntent; replay использует сохранённый структурированный
intent, не новый вызов модели.

Тесты: golden corpus для add/modify/replace/retire/recheck;
неоднозначности (нет цели, конфликтующие ограничения, неполные AC);
prompt-injection и контаминация вывода инструментов; timeout, битый
JSON, частичный ответ; approval — в C2–C9 входит именно подтверждённый
кандидат.

Не-цели: нет автономного approval, прямой мутации графа, авто-расширения
scope, заявлений о детерминированности NL-интерпретации.

**Exit gate:**
- Пользователь вводит канонический запрос естественным языком и
  ревьюит корректное структурированное предложение.
- Система раскрывает неопределённость, а не прячет её.
- Отключение AI-фичи не меняет downstream-корректность.
- Сохранённые approved изменения replay-ятся без вызова модели.

### C11 — Guarded Graph Delta и контролируемый рост scope

- **Гарантия:** агенты предлагают пропущенные связи и новый импакт в
  процессе исполнения — без молчащего расширения изменения.
- **Режим:** guarded automation, approval по политике.
- **Сущности:** `NewImpactFinding`, `ChangePackageRevision`,
  `ScopeGrowthDecision`.

Задачи:

- [ ] Production cells и analysis-агенты эмитят кандидаты GraphDelta и
      NewImpactFinding.
- [ ] Валидация каждого ребра: схема, доменные правила, provenance,
      конфликты.
- [ ] Версионирование ChangePackage при расширении замыкания новым
      принятым импактом.
- [ ] Политика авто-приятия низкорискового роста в заданных пределах;
      остальное — human approval.
- [ ] Идемпотентный replan селективного исполнения после одобренного
      роста.
- [ ] Отвергнутые/отложенные inferred-связи сохраняются как findings с
      provenance и rationale.

Инварианты: агент не модифицирует принятый граф напрямую; рост scope
явен, версионируем, атрибутируем; работы по новому импакту не начинаются
до авторизации ревизии ChangePackage; replan не теряет завершённую
валидную работу и не дублирует принятые эффекты; отвергнутые findings
видимы для аудита.

Тесты: отвержение невалидных GraphDelta (схема/доменные правила);
политика низкорискового роста; требование human-approval для
высокорискового; повторное обнаружение и идемпотентный replan;
дедупликация конкурентных находок; e2e — скрытая зависимость
документации обнаружена при имплементации.

Не-цели: нет бесконтрольного автономного обучения графа, статистических
confidence-скоров вместо авторитета, параллельных независимых веток,
универсального семантического анализатора.

**Exit gate:**
- Каноническое изменение обнаруживает одну незаявленную зависимость и
  включает её через новую авторизованную ревизию замыкания.
- Ни один агентный путь не обходит валидацию GraphDelta и
  версионирование ChangePackage.
- Replan replay-им и fault-протестирован.
- Операторы видят, кто/что предложил каждую связь и почему она
  принята или отвергнута.

### C12 — Semantic Adapter SDK

- **Гарантия:** стабильные контракты доменного расширения из
  доказанного software-пути, без редизайна ядра.
- **Режим:** platform release; software остаётся reference-паком.
- **Сущности:** `MaterialAdapter`, `DomainPackManifest`,
  `ConformanceResult`.

Задачи:

- [ ] MaterialAdapter: index, semanticDiff, extractDependencies,
      validate, render, capability-binding.
- [ ] DomainPack manifest: типы артефактов, типы рёбер, правила
      распространения, evidence policies, dispositions, workcells,
      authority hooks.
- [ ] Рефакторинг software-реализации на SDK без изменения наблюдаемого
      поведения.
- [ ] Conformance test kit + генератор маленьких фикстур для авторов
      адаптеров.
- [ ] Версионирование каждого адаптера; дайджест в resume и evidence
      совместимости.

Инварианты: адаптеры расширяют семантику артефактов, но не подменяют
правила коммита базлайна, авторитета, замыкания, свежести; DomainPack
версионируется и пиннится на время жизни ChangePackage; replay не
вызывает адаптер новее записанного для lifecycle; проваливший
conformance пак не включается в production.

Тесты: контракты SDK; эквивалентность software-пака до/после
рефакторинга; дайджест адаптера и resume-несовместимость; conformance
на запрещённые прямые мутации авторитета/базлайна; минимальный
пример-пак вне ядра репозитория.

Не-цели: нет полной инженерной онтологии; CAD/BIM/GIS/solver-интеграций
в самом SDK-релизе; обещаний «один адаптер на все форматы»;
кросс-пакового semantic merge.

**Exit gate:**
- Software-путь полностью работает через контракт адаптера без
  регрессий.
- Минимальный второй фикстурный пак проходит conformance kit.
- Ядро остаётся единственным владельцем авторитета и коммита.
- Смена версии адаптера даёт явный исход по совместимости.

### C13 — First Engineering Domain Pilot

- **Гарантия:** ядро изменений работает за пределами ПО на одном узко
  ограниченном инженерном change package.
- **Режим:** контролируемый пилот с обязательными человеческими
  инженерными гейтами.
- **Сущности:** `EngineeringArtifactIdentity`, `StandardsProfile`,
  `CoordinateProfile`, `SolverEvidence`.

Задачи:

- [ ] Один constrained use case: изменение параметра горизонтального
      ж-д плана в заданном интервале пикетов.
- [ ] Только заземлённый набор: форматы входов/выходов, правила системы
      координат, единицы, расчётные инструменты, evidence checks.
- [ ] Малый граф артефактов: ревизия съёмки, участок плана, переходные
      кривые, расчёт возвышения, проверка габарита, влияние на объёмы,
      экспорт чертежа, release report.
- [ ] Детерминированные солверы и валидаторы для расчётов; AI — только
      кандидатные нарративы и объяснения импакта.
- [ ] Квалифицированный человеческий гейт перед acceptance инженерного
      successor Baseline.
- [ ] Семантика release dossier та же, что в software.

Инварианты: единицы, система координат, эпоха координат, профиль
норм, дайджест toolchain и ревизии источников — часть идентичности
материала; вывод LLM не принимается как детерминированный расчёт; пак
не мутирует правила замыкания/авторитета ядра; поддерживается только
задокументированный класс изменений и форматов; каждый принятый
инженерный вывод трассируется к точным входам, версии солвера, проверкам
и человеческому решению.

Тесты: golden-фикстуры геометрии/расчётов с допусками; несовпадение
единиц/СК/эпохи; импакт по малому инженерному графу; совместимость
версий солвера и политики допусков; e2e пилот N → N+1 с обязательным
human approval; fault-injection вокруг внешних инструментов и экспорта.

Не-цели: нет полной автоматизации ж-д проекта, интерпретации
произвольных CAD/BIM, снятия ответственности с квалифицированного
ревьюера, одновременной поддержки нескольких дисциплин.

**Exit gate:**
- Одно реальное или production-представительное инженерное изменение
  проходит тот же протокол перехода базлайна, что и ПО.
- Каждый расчёт и deliverable имеет точный provenance и доказательства.
- Пилот вскрывает пределы и отвергает неподдерживаемые кейсы, а не
  угадывает.
- Интерфейс DomainPack переживает пилот без изменения семантики
  авторитета ядра.

## 6. Гейты между волнами (стоп-критерии продвижения)

- **После W0:** система идентифицирует и реконструирует принятое
  состояние без lifecycle-неоднозначности? Если нет — не начинать
  ChangeIntent.
- **После W1:** ручное scoped изменение создаёт атомарный successor
  Baseline под crash и replay? Если нет — не добавлять trace-графы.
- **После W2:** трассируемость и свежесть генерируются и enforce-ятся
  без ручных корректировок? Если нет — не заявлять полноту импакта.
- **После W3:** детерминированное замыкание и селективное исполнение
  многократно проходят канонический сценарий? Если нет — не вводить
  NL-вход.
- **После W4:** AI отключается без потери корректности или replay? Если
  нет — границы авторитета нарушены.
- **После W5:** одно инженерное изменение использует то же ядро без
  доменных shortcuts авторитета? Если нет — абстракция SDK неполна.

## 7. Стратегия тестирования

Слои (все накапливаются, релиз-рейтчет):

1. **Pure domain** — переходы состояний, идентичность, правила
   замыкания, dispositions, функции совместимости.
2. **Property-based** — идемпотентность, монотонность, независимость
   от порядка обхода, детерминизм дайджестов, fixed-point графа.
3. **Event replay** — реконструкция агрегатов и финального Baseline из
   событий и наблюдений.
4. **Storage/migration** — апгрейд с предыдущего релиза, открытие
   исторических данных, отсутствие расширения авторитета при миграции.
5. **Contract** — адаптеры production cells, check providers, material
   adapters, границы внешних инструментов.
6. **Golden projection** — trace matrices, impact-отчёты, transition
   reports, release dossiers.
7. **Fault-injection** — crash, timeout, retry, дубль доставки, потеря
   воркера, stale lease, конфликт коммита, отказ post-commit effect.
8. **End-to-end** — канонический переход базлайна точным
   production-путём.
9. **Architecture ratchets** — статические тесты против возврата
   legacy authority-путей и прямой мутации принятого состояния.

Рост канонической фикстуры по одному измерению на релиз: C0 —
множественные lifecycles и точная принятая идентичность; C1 —
иммутабельный снапшот; C2 — approved change record; C3 — явные retire и
modify; C4 — successor-коммит; C5 — генерируемая матрица; C6 — stale
evidence и обязательный recheck; C7 — прямой предпросмотр; C8 —
транзитивное замыкание и dispositions; C9 — селективное исполнение;
C10 — NL-предложение; C11 — обнаруженная зависимость и пересмотренное
замыкание; C12 — конформанс software-адаптера; C13 — эквивалентный
инженерный пилот.

**Правило качества:** релиз завершён не когда работает happy path, а
когда новый инвариант выполняется под retry, replay, миграцией и
частичным отказом. Более поздний релиз не заменяет ранний точный тест
более широким e2e.

## 8. Дисциплина для coding-агентов

### 8.1 Бюджет релиза (отклонение — отдельное архитектурное решение)

- ≤ 1 нового core-агрегата **или** 1 новой стейт-машины.
- ≤ 1 authority-critical миграции storage.
- ≤ 1 нового correctness-алгоритма.
- Один канонический e2e-сценарий — расширяется, не заменяется.
- Никаких побочных реорганизаций пакетов, переименований, UI-редизайнов,
  апгрейдов зависимостей в том же изменении.
- Никакой новой абстракции ядра, пока она не прокачана reference-реализацией
  и второй фикстурой.
- У каждого нового состояния — явные терминальное, retry- и
  cancellation-поведение.
- Каждое внешнее наблюдение для replay записывается, а не
  перезапрашивается.

### 8.2 Обязательный delivery-пакет релиза

1. Один сфокусированный ADR: инвариант, владение данными, переходы,
   явные не-цели.
2. Схема и миграционная записка, включая обращение со старыми данными.
3. Feature flag и путь выключения.
4. Тесты уровня релиза: unit, property, replay, migration,
   fault-injection, e2e.
5. Наблюдаемые счётчики и структурированные логи новых состояний и
   отказов.
6. Production runbook: включение, откат/выключение, диагностика.
7. Короткая демонстрация на канонической фикстуре.
8. Conformance-заявление: все гейты ранних релизов зелёные.

### 8.3 Стоп-условия (прекратить реализацию и сузить scope)

- В релизе два конкурирующих источника авторитета.
- Принятый артефакт или ребро можно обновить на месте.
- Тест проходит только моканием тестируемого механизма
  идентичности/замыкания/коммита.
- Вывод AI обходит структурированную валидацию или human approval.
- Successor Baseline не реконструируется из записанного состояния.
- Trace matrix требует ручной корректировки после генерации.
- Релизу нужна универсальная доменная модель до завершения
  reference-пути ПО.
- Отказ после acceptance может уничтожить принятое решение.

### 8.4 Разделение труда моделей

Большая модель готовит ADR и план имплементации; код-агенты получают
**по одному релизу за раз** с exit gate, скопированным в задачу
дословно; review-агенты проверяют инвариант, а не стиль. Последовательность
задач: архитектура → минимальная схема → чистая доменная реализация →
persistence-адаптер → API/CLI срез → e2e-фикстура → fault-injection →
документация и rollout. Задачи не объединять в один недифференцированный
промпт.

## 9. Миграция с текущего рантайма Saga4

**Рантайм не переписывать.** Production cells, attempts, checks, gates,
accepted authority, recovery, effects остаются; плоскость изменений —
оркестрационный и авторитетный слой поверх:

```
ChangePackage владеет существующими Lifecycles
  → Lifecycle инстанцирует существующие Workplaces и Cells
    → Cells производят CandidateSets и CheckReceipts
      → GateDecision авторизует принятые ревизии
        → BaselineCommitter собирает их в Baseline N+1
```

Прогрессия пакетов: `change-authority` (C0) → `baseline-registry` (C1)
→ `change-ledger` (C2–C4) → `trace-model` (C5) → `evidence-policy`
(C6) → `impact-engine` (C7–C8) → `change-executor` (C9) →
`change-desk` (C10–C11) → `domain-sdk` (C12) → `rail-alignment-pack`
(C13).

Политика совместимости:

- Старые прогоны завода читаемы на протяжении всей миграции.
- Исторические принятые выходы оборачиваются в синтетический genesis
  Baseline только при наличии точных ссылок.
- Неизвестные исторические доказательства маркируются unknown/stale —
  никогда не повышаются до fresh ради удобства миграции.
- Новый change-путь за feature flag до прохождения C4
  fault-injection-гейта.
- После C4 управляемые изменения идут через ChangePackage по умолчанию;
  legacy task-путь временно доступен для неуправляемых экспериментов.
- Legacy-путь никогда не публикует напрямую в управляемый head базлайна.

## 10. Метрики успеха

**Надёжностные (нулевые допуски):** 0 артефактов, разрешённых через
newest-wins; 0 полу-коммиченных successor Baselines под fault
injection; 100% затронутых узлов с явным disposition до approval
исполнения C8+; 100% обязательных CheckReceipt с точными привязками
субъекта и toolchain; replay даёт тот же дайджест принятого Baseline;
все ранние invariant-наборы зелёные на каждом позднем релизе.

**Операционные:** доля change-пакетов без ручной правки trace matrix;
доля reuse по точной ссылке вместо регенерации; число пойманных stale
evidence до релиза; число импакт-находок после старта исполнения;
отказы и восстановления change-пакетов по состояниям; время в
human-decision obligations против производственной работы; доля и
причины отвергнутых AI-предложений (после C10).

**Продуктовые (пилотные гипотезы, не гарантии):** lead time
change-to-release; rework от пропущенных зависимостей; first-pass
acceptance rate; ручные усилия на release dossier; время
реконструкции «почему принятая ревизия существует».

## 11. Ключевые риски и сдерживание

| Риск | Сдерживание |
|---|---|
| Ложная полнота графа зависимостей | Разделение provenance (declared/extracted/inferred/observed); fail-closed obligations для unknown; inferred-рёбра не раньше C11. |
| Преждевременное обобщение | C0–C11 остаются software-специфичными где нужно; SDK только после полного software-пути. |
| Утечка авторитета в AI | Любой результат AI — кандидат; схема-валидация, policy-проверки, версионируемая ревизия ChangePackage, human/deterministic gate. |
| Неоднозначность миграции | Не фабриковать точность; legacy классифицируется как exact/partial/unknown. |
| Взрыв пространства состояний | Минимальные закрытые наборы в каждом релизе; расширения — через table-driven тесты переходов и распространения. |
| Производительность графа | Сначала простое adjacency-хранение и корректность; индексы и инкрементальный пересчёт — после perf-фикстур C8. |
| Перегрузка оператора | Принять стоимость ручных approvals в ранних релизах; автоматизировать только уже представимое и тестируемое решение. |
| Связанность релизов | Доставка через минимальный существующий CLI/API; презентационная работа откладывается. |
| Недетерминизм внешних инструментов | Пиннинг версий, запись наблюдений, классификация детерминизма, привязка evidence к toolchain-дайджестам. |

## 12. Первый шаг

Не AI Change Desk, не универсальный граф зависимостей, не ж-д пак.
Ядровая очистка, ранее входившая в C0, исполняется программой
**Saga Core Renewal K0–K20** (`SAGA-CORE-RENEWAL-PLAN.md`) до Core 3.0 GA.
После GA первый шаг самого change plane — C0 как короткий
integration-acceptance-релиз: потребление сертифицированных
Baseline/Authority API и доказательство, что ни один компонент change
plane их не обходит. Первая продуктовая фича — C1 (иммутабельные
Baseline). Первый операционный MVP — C4 (ручное scoped изменение →
атомарный Baseline N+1). Всё остальное — только после стабилизации
ручного детерминированного пути.
