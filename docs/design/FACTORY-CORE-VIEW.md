# Factory Core View — «Ядро завода»

**Status:** Concept / design proposal (не реализовано)
**Date:** 2026-08-16
**Ограничение:** завод работает — рантайм не трогаем вообще. Только наблюдение.

## 1. Проблема

Сегодня фронт (`tracker-view` :4321) показывает **проекцию канбана**: у карточки
есть статус, у эпика — прогресс-бар, у стадии — степпер. Это отвечает на вопрос
«в каком состоянии работа?», но не отвечает на вопросы:

- **как работа движется?** — что ядро делает прямо сейчас между двумя статусами;
- **почему стоит?** — какая машина из композиции (§23 CONVEYOR-MENTAL-MODEL)
  не отдала синхронизационное ребро, и что ядро «обязано» сделать следующим;
- **какой ценой?** — сколько попыток, ремонтов, повторов, replay-капсул
  стоила каждая принятая ячейка.

Канбан — это витрина. Нужен **рентген**: вид на внутреннюю механику
Production Cell, гейтов, recovery-петель и обязательств переходов — живой,
анимированный, «реакторный».

## 2. Ключевая идея

Конвейер — это композиция авторитетных машин состояний (§23). У них уже есть
**полная дурская трассировка в SQLite** — 120+ таблиц, каждая физика завода
видна без единой правки рантайма. Значит, можно построить **пассивного
наблюдателя**, который читает ту же БД (WAL → конкурентное чтение безопасно)
и хвосты JSONL-логов воркеров, и рисует завод как живой организм.

> Метафора: не «доска с карточками», а **сборочный конвейер под рентгеном** —
> материал течёт по станциям, гейты сканируют пакеты, repair-петли загибаются
> назад, replay-капсулы прилетают с «орбиты памяти», а dispatcher — это
> сердце, качающее очередь.

Три источника истины для картинки — все уже существуют:

| Что видно | Откуда (read-only) |
|---|---|
| Станции и их фазы | `factory_workplaces` (kanban_phase, loop_state, revision, attempt) |
| Живые воркеры + пульс | `worker_executions` (heartbeat_at, pid, log_path, state) + mtime JSONL |
| Запечатанный материал | `factory_candidate_sets` (+ members) |
| Решения QC | `factory_gate_decisions` / `factory_gate_runs` (verdict, repair_target_role) |
| «Что ядро должно следующим» | `factory_transition_obligations` (630 строк live) — материализованный progress-obligation invariant |
| Прогресс по цепочке | `factory_orders → factory_order_runs → factory_lifecycle_runs → factory_stage_runs → factory_process_runs → factory_node_runs` |
| Зависимости станций (DAG) | `factory_workplace_dependencies`, `factory_workplace_graph_items` |
| Recovery-петли | `factory_recovery_cases`, `factory_recovery_attempts` |
| Эффекты наружу (Git и др.) | `factory_external_effect_actions/events`, `factory_cell_effect_receipts` |
| Финальные принятия | `factory_cell_final_acceptances` |
| Replay-память | `factory_replay_capsules` |
| Общая хроника | `activity_log`, `factory_process_transitions`, `lifecycle_events` |

## 3. Зум-уровни (фрактальный вид)

Четыре масштаба, каждый — самостоятельная ценность, собираются поверх одного
snapshot-API.

### L0 «Пульс завода» — обзорная полоса

Сводка всего завода как организма:

- **Кольцо-реактор** активного проекта: текущая стадия lifecycle, доля принятых
  ячеек, число живых воркеров;
- ряд **мини-реакторов** по всем проектам тестбеда (та же сетка 20×3, что в
  WORKSHOP-STATUS.md, но живая из БД, а не ручная);
- спарклайны: gate-решений/час, repair-rate, глубина очереди, свежесть
  heartbeat, replay-hit ratio;
- «лёгкие» LM Studio: последний heartbeat, tok/s активных воркеров.

### L1 «Цепочка» — главный экран

Нормативная цепочка завода как горизонтальный конвейер:

```
FactoryOrder → LifecycleRun → [Discovery → Formalization → Development → …]
                                        │  активная стадия раскрыта:
                                        ▼
   dispatcher ──► станция ──► станция ──► станция ──► transition ──► следующая стадия
   (сердце)        Workplace  Workplace   Workplace     obligation
                    ▣ queued    ◉ busy     ⏳ wait
```

- каждая станция = Workplace-чип: kanban-фаза, loop-state, attempt (кольца
  вокруг чипа), ревизия, свежесть пульса;
- **рельсы зависимостей**: DAG станций натянут на ленту (корни слева,
  зависимые справа, нераскрытые рёбра — серым);
- dispatcher слева: резервации, живой параллелизм против лимита, очередь
  (todo/idle против admitted);
- «материал» — анимированные пакеты, которые движутся по цепочке при реальных
  событиях (new CandidateSet → пакет запечатан; GateDecision accepted →
  пакет прошёл станцию; repair → пакет вернулся по дуге назад).

### L2 «Ячейка под микроскопом» — самое футуристичное

Одна Production Cell как **круговой цикл** (автор → кандидат → гейт →
ревьюер → финал → эффект). Позиция в цикле светится; каждая попытка — орбита
вокруг ядра; история — концентрические кольца. Рядом:

- терминал-панель с живым хвостом лога воркера (JSONL tail, tok/s,
  «спин/стал» детектор по mtime);
- карточка RecoveryIssue как «дефект-ведомость» (термин из глоссария §28);
- EffectReceipt как «шлюз наружу» (Git-иконка, коммит, CAS до/после);
- replay-hit: пакет мгновенно прилетает с «орбиты памяти» — визуально
  отличается (фиолетовый след) от медленного инференса.

### L3 «Хроника» — чёрный ящик

Единая лента событий в одном временном пространстве: `activity_log` +
переходы стадий + гейт-решения + смены состояний обязательств. Цветовая
кодировка по типу источника, фильтры, пауза прокрутки при наведении. Это
flight recorder: когда оператор спрашивает «что было в 15:06?», ответ здесь.

## 4. Честность как принцип (из §23/§27 ментальной модели)

- Каждая nonterminal-станция обязана показывать **класс прогресс-обязательства**:
  `live owner | runnable command | typed wait | transition due` — а если
  никого нет, лампа **STALLED**, если несколько — **INCONSISTENT**. Ядро уже
  вычисляет это в `factory_transition_obligations` — фронт только красит
  лампы. Это превращает invariant в ощущение «здоровья реактора».
- Controller `paused` + живые воркеры = **«воркеры работают»**, не «завод
  стоит» (запрещённое §27 отождествление).
- Постоянная плаха в углу: `PROJECTION — наблюдение, не авторитет`
  (проекции объясняют, но не авторизуют переходы).
- Никаких производных статусов «на глаз»: только то, что durability лежит
  в таблицах.

## 5. Архитектура: sidecar-наблюдатель

Устоявшийся паттерн репо — docs-graph (:4322): отдельный процесс, raw
`node:http`, zero-install, vanilla ESM, без правок рантайма. Новый вид —
`core-view/` на порту **:4323**:

```
core-view/
  server.mjs            # http, статика + JSON API, только GET
  core-snapshot.mjs     # сборка снапшота: better-sqlite3 readonly per request
  core-events.mjs       # дельта-поток хроники (cursor по id)
  log-tail.mjs          # mtime/tok-s по JSONL логам (паттерн /api/workers/active)
  public/
    index.html
    core.js             # рендер L0–L3, canvas-поток частиц
    core.css            # неймспейс .core-*, продолжение GitHub-dark
```

- **Чтение БД**: `better-sqlite3` в `readonly: true`, открытие на запрос
  (существующий `withDb`-паттерн). WAL-режим уже включён — наблюдатель не
  блокирует завод и не видит грязных наполовину транзакций.
- **Обновление**: polling 1 с с курсорами (`/api/core/snapshot?since=`,
  `/api/core/events?since=`), плавность — клиентская интерполяция.
  SSE не вводим: в трекере всюду polling, новую механику не навязываем.
- **Только GET.** Ни одного write-эндпоинта, ни одной кнопки resume/kill.
  Наблюдатель — не оператор. Интервенции остаются в `/admin` и у рабочей
  сессии.
- **Живость**: свежесть пульса (>30 s тишина лога = стал — как `is_stale`
  в `/api/workers/active`), возраст heartbeat, деградация LM Studio.

### Дизайн-язык

Продолжение палитры трекера (`#0d1117` база) с неоновыми акцентами:

| Смысл | Цвет |
|---|---|
| поток материала / вода конвейера | cyan `#22d3ee` |
| принято, QC passed | `#3fb950` (родной зелёный) |
| гейт-скан (момент решения) | лазерный синий `#58a6ff` |
| ожидание / repair | amber `#f39c12` |
| отказ / fail | `#f85149` |
| replay-капсула | violet `#a371f7` |
| эффект наружу (Git) | стальной `#8b949e` |

Анимация — Canvas 2D (частицы-пакеты, свечение станций), без WebGL/THREE:
глаза это читают как «живое ядро», а вес нулевой. Обязательно
`prefers-reduced-motion` (паттерн уже есть в lifecycle-pipeline.css).

## 6. Анти-цели

- ❌ любые записи в БД завода, любое управление процессами;
- ❌ вторая интерпретация физики: вид — проекция над теми же таблицами,
  никаких собственных state-machine выводов «из логов»;
- ❌ «один глобальный статус завода» — завод композиция машин, вид показывает
  композицию, а не синтетический enum;
- ❌ подмена канбана: доска остаётся доской, ядро — рентгеном рядом.

## 7. Фазы (каждая сама по себе полезна)

| Фаза | Что входит | Ценность |
|---|---|---|
| 0 | snapshot-API (read-only запросы) + скелет :4323 | фундамент, ноль риска |
| 1 | L1 «Цепочка» + L3 «Хроника» | главное: движение и причина задержек |
| 2 | L2 «Ячейка» + анимация материала | wow-слой: цикл клетки, repair-петли |
| 3 | L0 «Пульс» + мини-реакторы 20 проектов | ситуационный центр оператора |

## 8. Открытые вопросы (решить перед Фазой 0)

1. Куда монтирует точку входа оператор — отдельный порт :4323 (как docs-graph)
   или будущая ссылка из `/admin` трекера (ссылка — можно, код трекера —
   минимально)? Предложение: отдельный порт, ссылку добавить потом одним
   коммитом в `/admin`.
2. Горячий перезапуск наблюдателя: он должен переживать рестарты завода и
   схлопываться грациозно, если БД исчезла (snapshots/backup-файлы
   `.bak-*` не открывать).
3. Идентификация «активного» проекта на L0: один проект одновременно
   (текущее правило тестбеда) — но API должен уметь N.
