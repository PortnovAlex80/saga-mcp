# Как запускать проекты в Saga (saga-mcp)

> Версия: **saga-mcp @ 2026-07-30**
> GLM-4.7 cloud через z.ai (ANTHROPIC_BASE_URL в ~/.claude/settings.json)
> Pinned Process Module packages, agent assistance, materialized MCP calls
> Test warm-start: epic-scoped draft cache для повторных прогонов

## Что подключено

Все 4 модуля установлены как immutable content-addressed packages:

| Модуль | Версия | LM-задачи | Kernel | Ресурсов |
|---|---|---|---|---|
| **product-discovery** | 3.0.2 | discovery.work, discovery.normalize, discovery.assess, discovery.diagnose | 6 | 18 |
| **solution-formalization** | 1.0.0 | formalization.prd, formalization.uc, formalization.ac, formalization.reconciliation, formalization.srs | 7 | 12 |
| **solution-development** | 1.0.0 | planning.decomposition | 2 | 7 |
| **delivery-release** | 1.0.0 | (kernel-only, без LM) | 5 | 7 |

### Что доказано работает (model-driven на GLM-4.7, прогоны до 2026-07-30)

- ✅ **Discovery** — полный flow: produce-proposal → assess-readiness → settle → certificate. Outcome=**go**, readiness=ready (0.82), все 7 dimensions sufficient, 0 blocking gaps
- ✅ **Discovery → Formalization переход** — lifecycle permissive gate форвардит после Discovery (outcome=go)
- ✅ **Formalization.prd** — PRD + 10 FR + 8 NFR + 8 RULE созданы, приняты ревью, accepted kernel'ом
- ✅ **Formalization.uc** — 9 UC созданы, приняты ревью, accepted kernel'ом
- ✅ **Test warm-start draft-cache** — 5 slots накоплено (discovery, PRD, metrics, UC, AC), все lastOutcome=completed, history-механизм сохраняет предыдущие версии
- ✅ **Recovery pipeline** — kernel находит contract violations (AC trace gaps), даёт structured feedback, worker чинит, re-review. 3 раунда review loop + 2 recovery attempts отработали корректно
- ✅ **Reviewer quality** — модель систематически проверяет traceability matrix, ловит missing UC/FR traces
- ❌ **Formalization.ac settlement** — БАГА: AC artifacts создаются и проходят review, но kernel `resolve-acceptance-contract` не может их accept из-за fence mismatch после recovery (см. Troubleshooting). Formalization завершается `failed` после exhaustion recovery budget
- ⬜ Formalization.reconciliation, srs — не достигнуты (blocked на AC)
- ⬜ Development — не запускался
- ⬜ Delivery — не запускался

## Два режима запуска

### Режим 1: Standalone Discovery (только Discovery модуль)

Быстрый прогон: идея → proposal → readiness → certificate. ~5-7 минут.

```bash
# 1. Создать изолированный sandbox (БД + git workspace + seeds)
node tools/discovery-run.mjs bootstrap --idea="твоя идея продукта"

# 2. Проверить готовность (preflight)
node tools/discovery-run.mjs preflight --run=<путь из вывода>/run.json

# 3. Запустить (заменить пути из вывода bootstrap)
DB_PATH='<saga.db путь>' \
SAGA_REPO_ROOT='D:\Разработка\saga-mcp' \
SAGA_PACKAGE_STORE_DIR='<package-store путь>' \
SAGA_ORCHESTRATION_MODE=saga3-discovery-generic \
node dist/orchestrate-cli.js <project_id> <epic_id> --concurrency=1

# 4. Мониторить (в другом терминале)
node tools/discovery-run.mjs status --run=<путь>/run.json
```

Или через bootstrap скрипт:

```bash
# Сбросить основную БД (если нужен чистый старт)
node reset-saga-db.mjs

# Создать проект в основной saga.db
node bootstrap-autism-buttons.mjs   # (или свой bootstrap скрипт)

# Запустить Discovery
DB_PATH='C:/Users/user/.zcode/saga.db' \
SAGA_REPO_ROOT='D:\Разработка\saga-mcp' \
SAGA_PACKAGE_STORE_DIR='C:\Temp\autism-buttons-pkg' \
SAGA_ORCHESTRATION_MODE=saga3-discovery-generic \
node dist/orchestrate-cli.js 1 1 --concurrency=1
```

### Режим 2: Полный Lifecycle (Discovery → Formalization → Development → Delivery)

Долгий прогон: весь pipeline до released. 30-60+ минут.

**Требуется composition-модуль** — saga3-lifecycle не запустится без
`SAGA_PRODUCT_LIFECYCLE_COMPOSITION` (Delivery preflight/publication/observation
провайдеры не встроены в runtime). Для тестового прогона используй:

- `hex-composition.mjs` — mock delivery ports (всегда `{ok:true}`), позволяет
  дойти до терминала `released`. **Рекомендуется для end-to-end прогона.**
- `product-lifecycle-composition.mjs` — real SqliteDevelopmentRuntime для
  development, delivery ports кидают `NOT_REACHED` (нужно подключать реальные
  адаптеры). Для testing development stages.

```bash
# 1. Сбросить БД + создать проект
node reset-saga-db.mjs
node bootstrap-autism-buttons.mjs

# 2. Создать lifecycle input (policy contentHash должны быть вычислены!)
#    Шаблон: autism-buttons-lifecycle-input.json (projectRepositoryId=65 для epic 1)
#    ВАЖНО: projectRepositoryId = project_repositories.id (НЕ repositories.id)

# 3. Запустить полный lifecycle
DB_PATH='C:/Users/user/.zcode/saga.db' \
SAGA_REPO_ROOT='D:\Разработка\saga-mcp' \
SAGA_PACKAGE_STORE_DIR='C:\Temp\autism-buttons-pkg' \
SAGA_ORCHESTRATION_MODE=saga3-lifecycle \
SAGA_PRODUCT_LIFECYCLE_COMPOSITION='D:\Разработка\saga-mcp\hex-composition.mjs' \
SAGA_TEST_WARM_START=1 \
SAGA_TEST_WARM_START_FIXTURE='D:\Разработка\saga-mcp\test-fixtures\lifecycle\autism-buttons-warm-start.json' \
node dist/orchestrate-cli.js 1 1 \
  --lifecycle-input=D:\Разработка\saga-mcp\autism-buttons-lifecycle-input.json \
  --concurrency=1

# 4. Resume (если прогон был прерван, а definition не менялся)
#    Добавить --resume флаг (SAGA_TEST_WARM_START остаётся!)
node dist/orchestrate-cli.js 1 1 \
  --lifecycle-input=... \
  --resume \
  --concurrency=1
```

⚠️ **policy contentHash** — это `sha256Hex(canonical(policy без contentHash))`.
Не угадывай хэш, вычисли его тем же canonical-json что runtime (см.
`hashWithoutField` в development-settlement-policy.ts). Поле
`operatorAuthorization.releasePolicyHash` должно совпадать с
`delivery.policy.contentHash`.

## Стратегии перезапуска (НЕ ГОНЯЙ ВСЁ ЗАНОВО)

### Главное правило

**Полный `reset-saga-db.mjs` — только для нового проекта или изменения lifecycle definition.**
Для багфикса в одном узле/module — используй partial-reset + resume.

### Что когда использовать

| Ситуация | Инструмент | Что происходит |
|---|---|---|
| **Новый проект / первый прогон** | `reset-saga-db.mjs` + `bootstrap` | Полный wipe, новая БД |
| **Процесс убит (stale lease)** | `--resume` | Continue с места остановки. Discovery/Formalization НЕ повторяются |
| **Баг в одном stage (formalization/dev/delivery)** | `saga-reset-stage.mjs --stage=<stage>` + `--resume` | Сброс только проблемного stage, остальные не трогаются |
| **Изменился lifecycle definition (код stages)** | `reset-saga-db.mjs` (к сожалению) | Definition hash не совпадает → resume невозможен |
| **Изменился только skill/template (не код модуля)** | `saga-reset-stage.mjs --stage=<stage>` + `--resume` | Module digest не изменился → resume работает |

### Partial-reset: сброс одного stage

```bash
# Посмотреть что будет удалено (без выполнения)
node tools/saga-reset-stage.mjs --stage=solution-formalization --dry-run

# Сбросить formalization (Discovery сохранится)
node tools/saga-reset-stage.mjs --stage=solution-formalization

# Сбросить development (Discovery + Formalization сохранятся)
node tools/saga-reset-stage.mjs --stage=solution-development

# После сброса — resume
DB_PATH='C:/Users/user/.zcode/saga.db' \
SAGA_REPO_ROOT='D:\Разработка\saga-mcp' \
SAGA_PACKAGE_STORE_DIR='C:\Temp\autism-buttons-pkg' \
SAGA_ORCHESTRATION_MODE=saga3-lifecycle \
SAGA_PRODUCT_LIFECYCLE_COMPOSITION='D:\Разработка\saga-mcp\hex-composition.mjs' \
SAGA_TEST_WARM_START=1 \
SAGA_TEST_WARM_START_FIXTURE='D:\Разработка\saga-mcp\test-fixtures/lifecycle/autism-buttons-warm-start.json' \
node dist/orchestrate-cli.js 1 1 \
  --lifecycle-input=D:\Разработка\saga-mcp\autism-buttons-lifecycle-input.json \
  --resume \
  --concurrency=1
```

### Resume после убитого процесса

Если процесс убит (Ctrl+C, kill, crash) — lifecycle run остаётся `running` или
`paused`. Stale lease протухает автоматически (~5 мин).

```bash
# Просто добавь --resume — orchestrator подберёт протухший lease и продолжит
node dist/orchestrate-cli.js 1 1 \
  --lifecycle-input=... \
  --resume \
  --concurrency=1
```

### Типичные ошибки (из опыта 11 прогонов)

| Ошибка | Почему | Как избежать |
|---|---|---|
| **Полный reset при багфиксе в одном узле** | Definition hash изменился → resume блокирован → гонял всё заново (потеря 5+ часов, миллионы токенов) | Используй `saga-reset-stage.mjs` для конкретного stage |
| **Гонял Discovery заново ради formalization бага** | Discovery не связан с formalization кодом | Discovery артефакты переживают reset formalization |
| **Не использовал кэш между прогонами** | `SAGA_TEST_WARM_START` забыт в env | Всегда передавай warm-start env vars |
| **Изменил formalization код → formalization digest изменился** | Module definition hash part of lifecycle hash | При partial-reset formalization, reinstall packages автоматически |

### Test warm-start draft-cache (напоминание)

Cache хранит **документы** (markdown), но НЕ **артефакты/трассировки в БД**.
После сброса модель получает готовые документы, но перерегистрирует artifacts через
MCP (~5-10 мин на этап). Для полной оптимизации — см.
`docs/design/TRACE-REPLAY-GUIDE.md` (кеширование трассировок).

## Мониторинг прогресса

### Единый инструмент: `tools/saga-status.mjs`

Покрывает все потребности мониторинга lifecycle-прогона — прогресс, живые мысли
модели, артефакты, draft-cache, сырые логи.

```bash
# Snapshot прогресса (lifecycle, tasks, artifacts, workers)
node tools/saga-status.mjs status
node tools/saga-status.mjs status --epic=1

# Живые мысли активного worker'а (что модель думает прямо сейчас)
node tools/saga-status.mjs thoughts
node tools/saga-status.mjs thoughts --task=5 --tail=5

# Сырой лог worker'а (типы entries)
node tools/saga-status.mjs log --task=5 --tail=10

# Детальный список артефактов
node tools/saga-status.mjs artifacts

# Содержимое test draft-cache
node tools/saga-status.mjs cache

# Live watch: status + thoughts в цикле (Ctrl+C для выхода)
node tools/saga-status.mjs watch --interval=30
```

Опции: `--epic=N` (epic, по умолчанию 1), `--task=N` (конкретный task),
`--tail=N` (сколько entries, по умолчанию 3), `--interval=S` (watch, сек).
Env: `DB_PATH` (путь к saga.db, по умолчанию `C:/Users/user/.zcode/saga.db`).

### Tracker-view фронтенд (веб-канбан)

```bash
# Для discovery-run sandbox
node tools/discovery-run.mjs status --run=<путь>/run.json

# Напрямую из БД (короткий snapshot)
node -e '
const Database = require("better-sqlite3");
const db = new Database("C:/Users/user/.zcode/saga.db", { readonly: true });
const lr = db.prepare("SELECT status, current_stage_id FROM saga3_lifecycle_runs WHERE epic_id=1").get();
const tasks = db.prepare("SELECT id, status, task_kind FROM tasks WHERE epic_id=1 ORDER BY id").all();
const we = db.prepare("SELECT state, pid FROM worker_executions WHERE epic_id=1 ORDER BY started_at DESC LIMIT 1").get();
const arts = db.prepare("SELECT type, status, COUNT(*) n FROM artifacts WHERE epic_id=1 GROUP BY type, status ORDER BY type").all();
console.log("lifecycle:", lr?.status, "| stage:", lr?.current_stage_id);
console.log("tasks:", tasks.map(t=>t.task_kind+":"+t.status).join(", "));
console.log("worker:", we?.state, "pid:"+we?.pid);
if (arts.length) console.log("artifacts:", arts.map(a=>a.type+":"+a.status+"×"+a.n).join(", "));
db.close();
'
```

### Tracker-view фронтенд (веб-канбан)

```bash
# Запустить (если не запущен)
DB_PATH='C:/Users/user/.zcode/saga.db' node tracker-view/tracker-view.mjs

# Открыть в браузере
# http://localhost:4321/
```

Фронт показывает: проекты, эпики, задачи, артефакты, active workers,
live-tail "о чём думает воркер".

### Tracker файлы (на диске)

```
<workspace>/docs/<stage>/projects/<project_id>/executions/task-<id>/<exec-id>/
├── project-<project>-<stage>-stage-<task>.md   ← tracker (program counter, read-only)
├── agent-assistance.json                        ← hook projection (4 events)
├── <call-name>.json                             ← materialized MCP call (machine-filled)
├── discovery-doc.md (или другой output doc)
└── tools/
    ├── <name>-checklist.md                      ← pre-submit checklist
    └── <name>-stage-tracker.md                  ← source template
```

### Артефакты (в БД)

Артефакты (PRD, FR, NFR, UC, AC, SRS и т.д.) хранятся в таблице `artifacts`
БД `saga.db`, а не как файлы на диске. Модель создаёт их через `artifact_create`
MCP tool.

```bash
# Посмотреть артефакты
node -e '
const Database = require("better-sqlite3");
const db = new Database("C:/Users/user/.zcode/saga.db", { readonly: true });
const arts = db.prepare("SELECT id, type, status, substr(title,1,60) title FROM artifacts WHERE epic_id=1 ORDER BY id").all();
for (const a of arts) console.log("#"+a.id, a.type.padEnd(16), a.status.padEnd(10), a.title);
db.close();
'
```

## Test warm-start (epic-scoped draft cache)

Это тестовая инфраструктура (sidecar) для накапливания документов между
прогонами одного epic'а. Она **не трогает** lifecycle definitions, transitions,
модули, resolver, settlement и kernel gates — основная механика в
`src/infrastructure/testing/test-warm-start.ts`. Активируется двумя env vars:

```bash
SAGA_TEST_WARM_START=1
SAGA_TEST_WARM_START_FIXTURE='/abs/path/to/fixture.json'
```

### Как это работает

⚠️ **Cache пишется в GIT WORKSPACE репозитория** (где `local_path` из
`project_repositories`), а НЕ в корень репозитория saga-mcp. Все относительные
пути резолвятся относительно `assignment.repository.local_path`.

```
<git-workspace>/.saga/test-draft-cache/epics/<epicId>/
  product-discovery-3.0.2/produce-proposal/discovery-document.md
  solution-formalization-1.0.0/define-product-contract/product-contract.md
  solution-formalization-1.0.0/define-product-contract/product-metrics.md
  solution-formalization-1.0.0/model-use-cases/use-cases.md
  solution-formalization-1.0.0/define-acceptance-contract/acceptance-contract.md
  solution-formalization-1.0.0/define-architecture-contract/architecture-contract.md
```

Например для эпика 1 c workspace `C:/Temp/autism-buttons-workspace`:
`C:/Temp/autism-buttons-workspace/.saga/test-draft-cache/epics/1/...`

- Node запускается впервые → получает cold-start (или seed из `seedPath`).
- Worker создаёт/исправляет документ.
- При завершении или падении worker → документ сохраняется в свой slot.
- Следующий node добавляет свой slot, не перезаписывая чужие.
- Повторный запуск epic'а восстанавливает каждый draft в актуальный execution-путь.
- Discovery резолвится через `workspaceFile: "discovery-doc.md"` (basename
  match, без glob и привязки к execution ID).
- Два повторных отказа с неизменным содержимым → `force_rewrite` slots
  (сильная переработка, а не минимальная правка).
- Fixture закреплён за epicId; другие epic'и его игнорируют.

### Fixture format (`saga3.test-warm-start-fixture.v1`)

```json
{
  "schemaVersion": "saga3.test-warm-start-fixture.v1",
  "fixtureId": "unique-id",
  "epicId": 1,
  "nodes": [
    {
      "moduleRef": "product-discovery@3.0.2",
      "nodeId": "produce-proposal",
      "mode": "verify-and-submit-existing-draft",
      "drafts": [
        {
          "slot": "discovery-document",
          "workspaceFile": "discovery-doc.md",
          "seedPath": "docs/discovery/projects/1/executions/task-1/.../discovery-doc.md",
          "policy": "learn"
        }
      ]
    }
  ]
}
```

- `path` (project-relative POSIX) ИЛИ `workspaceFile` (basename) — ровно один.
- `path` подходит для стабильных canonical документов (formalization PRD/UC/AC/SRS
  в `docs/requirements/REQ-NNN-<slug>/`).
- `workspaceFile` — для execution-scoped документов (discovery-doc.md, где путь
  содержит `task-<id>/exec-<id>/`).
- `policy`: `"learn"` (накапливать) или `"locked"` (проверять sha256, не менять).
- Файл готов: `test-fixtures/lifecycle/autism-buttons-warm-start.json`.

### Проверить накопление draft-cache

```bash
# WS — это git workspace репозитория (local_path из project_repositories)
WS="C:/Temp/autism-buttons-workspace"

# Структура cache
find "$WS/.saga/test-draft-cache" -type f 2>/dev/null | head -20

# Метаданные одного slot (contentHash, lastOutcome, repeatedFailureCount)
cat "$WS/.saga/test-draft-cache/epics/1/product-discovery-3.0.2/produce-proposal/discovery-document.json"
```

Метаданные содержат: `contentHash` (sha256 документа), `lastOutcome`
(completed/changes_requested/failed), `repeatedFailureCount` (0=последний успех,
растёт при повторных одинаковых отказах → включает force_rewrite).

## Troubleshooting

| Симптом | Причина | Решение |
|---|---|---|
| `worker_executions state=lost, pid=null` | Spawn упал (missing resources, bad pin) | Проверить preflight, package install, agent-assistance path |
| `LIFECYCLE_DEFINITION_CHANGED_FOR_REPLAY` | Definition изменился после kill | Новый чистый прогон (reset + bootstrap), не resume |
| `PINNED_SKILL_NOT_RESOLVED` | Skill не найден в pinned package | Проверить manifest resourceIndex, kind поля |
| `PROCESS_WORKSPACE_ASSET_MISSING` | Template не найден | Проверить что package resources установлены |
| `log_path outside board-runs root` | Фронт не видит лог воркера | Запускать БЕЗ SAGA_ORCHESTRATION_LOG (дефолтный root) |
| `outcome: clarify` | Readiness нашёл пробелы | Это валидный outcome, не ошибка. Permissive gate форвардит |
| `outcome: failed` | Recovery exhausted | Проверить комментарии task, recovery-feedback.json |
| **AC settlement failed** ("persisted no canonical AC artifacts") | **БАГА**: после recovery, `resolve-acceptance-contract` kernel ищет AC managed-productions по execution fence recovery-воркера, но они записаны в исходном execution (task#5). Fallback (`listArtifactsForNodeInProcessRun`) не срабатывает т.к. trace writes есть в новом execution. AC зависают в draft, formalization → failed | Архитектурный фикс: recovery должен либо (a) пере-регистрировать AC artifacts в новом execution, либо (b) fallback в `readExecutionWrites` должен срабатывать когда artifact writes пусты даже при наличии trace writes |

## Структура lifecycle (что за чем идёт)

```
Discovery (product-discovery@3.0.2)
  produce-proposal (LM) → assess-readiness (LM) → settle (kernel) → certificate
  outcome: go | clarify | reject | defer | inconclusive | failed
     ↓ (lifecycle permissive: любой outcome форвардит)
Formalization (solution-formalization@1.0.0)
  define-product-contract (LM: PRD+FR+NFR+RULE)
  → define-use-cases (LM: UC)
  → define-acceptance (LM: AC)
  → reconcile (LM: traceability check)
  → define-architecture (LM: SRS)
  → freeze-baseline (kernel)
  outcome: formalized | clarification_required | inconsistent | infeasible | failed
     ↓
Development (solution-development@1.0.0)
  resolve-task-graph (kernel+LM: planning)
  → execute-implementation (external: worker пишет код)
  → integrate-candidate (external: merge)
  → verify-acceptance (external: verification)
  outcome: verified | failed
     ↓
Delivery (delivery-release@1.0.0)
  preflight-check (kernel)
  → approve-release (human/kernel)
  → publish (external)
  → observe (external)
  → settle-delivery (kernel)
  outcome: released | failed
```
