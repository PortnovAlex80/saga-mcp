⚠️ Три правила, без которых ничего не работает:
1. `SAGA_PRODUCT_LIFECYCLE_COMPOSITION` задаётся при старте tracker-view
2. `lifecycle_input_path` — **только ASCII** (кириллица `Разработка` ломает engine)
3. Движок стартует через tracker-view's `/api/engine/start`, **не** через `node &`
   (harness убьёт child → orphan)

## Что это

Завод = tracker-view (пульт) + orchestrate-cli (движок).
Заказ = идея одной фразой → `/api/project/create-from-idea` →
завод прогоняет 4 цеха: Discovery → Formalization → Development → Delivery.

## Переменные окружения (КРИТИЧНО)

Завод падает молча, если не задать `SAGA_PRODUCT_LIFECYCLE_COMPOSITION`.
Движок наследует окружение tracker-view, поэтому переменные задаются
**при запуске tracker-view**, один раз.

```bash
export DB_PATH='C:/Users/user/.zcode/saga.db'
export SAGA_PRODUCT_LIFECYCLE_COMPOSITION='D:/Разработка/saga-mcp/tracker-view/product-delivery-composition.mjs'
```

Без `SAGA_PRODUCT_LIFECYCLE_COMPOSITION` → `code=1`, `CHILD_EXITED_BEFORE_RECEIPT`,
на доске красный «failed/orphaned». Это главный подводный камень.

## Чистый старт (3 шага)

### Шаг 1 — Полный сброс

Убить всё, почистить логи, БД в ноль:

```bash
cd /d/Разработка/saga-mcp

# Убить все процессы завода
powershell -Command "Get-CimInstance Win32_Process -Filter \"name='node.exe' OR name='claude.exe'\" | Where-Object { \$_.CommandLine -like '*orchestrate-cli*' -or \$_.CommandLine -like '*tracker-view*' -or \$_.CommandLine -like '*claude-board*' -or \$_.CommandLine -like '*project_id=1*' } | ForEach-Object { Stop-Process -Id \$_.ProcessId -Force -ErrorAction SilentlyContinue }"

# Почистить логи
rm -rf ~/.zcode/cli/board-runs/board-*
rm -f ~/.zcode/cli/worker-heartbeat.log

# Очистить «сирот» (иначе reset-транзакция откатится)
node -e "const D=require('better-sqlite3'); const db=new D('C:/Users/user/.zcode/saga.db'); db.pragma('foreign_keys=OFF'); for(const t of ['repository_checkouts','lifecycle_execution_controls','trusted_providers']){try{db.prepare('DELETE FROM '+t).run();}catch{}}"

# Полный reset БД (схема сохраняется, данные — нет)
node reset-saga-db.mjs

# Проверка: должно быть 0/0/0/0
node -e "const D=require('better-sqlite3'); const db=new D('C:/Users/user/.zcode/saga.db'); console.log('projects:', db.prepare('SELECT COUNT(*) c FROM projects').get().c, '| epics:', db.prepare('SELECT COUNT(*) c FROM epics').get().c, '| lifecycle_runs:', db.prepare('SELECT COUNT(*) c FROM saga3_lifecycle_runs').get().c, '| process_runs:', db.prepare('SELECT COUNT(*) c FROM saga3_process_runs').get().c);"
```

#### Вариант 2: существующий проект (engine/start с lifecycle-input)

## Что происходит на доске

Открыть http://localhost:4321/?project=1 :

- **Движок: ▶/⏸** — кнопка старта/остановки (но заказ УЖЕ подан в шаге 3)
- **Lifecycle** — карточка Product Delivery, показывает текущий цех
- **Задачи** — двигаются todo → in_progress → review → done
- **Вкладка «Артефакты»** — PRD/SRS/UC/AC
- **Вкладка «Покрытие»** — какие AC закрыты

### 4 цеха (последовательно)

```
1. Discovery (product-discovery@3.0.2)
   LM-ноды: produce-proposal → normalize-semantic → assess-readiness → settle
   Итог: certificate {go | clarify | reject | ...}

2. Formalization (solution-formalization@1.0.0)
   LM-ноды: PRD → SRS → UC → AC → reconciliation
   Итог: frozen Solution Contract

3. Development (solution-development@1.0.0)
   dev-задачи → ревью → мерж в integration-branch
   Итог: verified integration bundle

4. Delivery (delivery-release@1.0.0)
   preflight → approval → release
   В режиме local-dry-run: завершается approval-required (fail-closed)
```

### Что нормально видеть на канбан (НЕ дубли!)

По мере прохождения цехов завод **создаёт задачи** — это Kanban-история, не дубли.
Каждая задача = одна LM-нода или один dev-step. Пример реального прогона:

```
Цех Discovery:
  Task "Product Discovery: <idea>"          → done   (produce-proposal)
  Task "Discovery: Assess readiness..."     → done   (assess-readiness)

Цех Formalization (после discovery=go):
  Task "Solution Formalization: Create PRD..." → in_progress → done
  Task "...Create SRS..."                      → ...
  Task "...Create UC..."                       → ...
  Task "...Create AC..."                       → ...
  Task "...Reconciliation..."                  → ...

Цех Development (после formalized):
  Task "Implement <feature>"                   → dev → review → done → merged
  Task "AC-verify <AC-N>"                      → verify
  ... и т.д.
```

**«Product Delivery» (родитель) + «Initial Discovery» (стадия) = ОДИН pipeline**,
не две задачи. Стадия внутри родителя меняется по мере продвижения:
`initial-discovery` → `solution-formalization` → `solution-development`
→ `delivery-release`.

Когда видите «задачи поехали» — это значит завод перешёл к следующему цеху и
создал новые задачи для него. **Старые (done) задачи остаются** как audit-trail.

### Прогресс по цехам (SOURCE OF TRUTH = БД, не HTTP-статус)

Один запрос показывает на каком цехе завод и с каким исходом:

```bash
node -e "
const D=require('better-sqlite3');
const db=new D('C:/Users/user/.zcode/saga.db');
console.log('LIFECYCLE:', db.prepare('SELECT id,status,current_stage_id,terminal_status,error FROM saga3_lifecycle_runs').all());
console.log('PROCESS:  ', db.prepare('SELECT id,status,projected_stage,local_outcome FROM saga3_process_runs').all());
console.log('TASKS:    ', db.prepare('SELECT id,status,title FROM tasks').all());
"
```

Как читать вывод:
- `lifecycle.status=running` + `current_stage_id=initial-discovery` → на цехе 1
- `process.local_outcome=go` → Discovery прошёл успешно, завод идёт дальше
- `current_stage_id=solution-formalization` → на цехе 2 (PRD/SRS/UC/AC)
- `current_stage_id=solution-development` → на цехе 3 (код, сборка фронта)
- `terminal_status=released|failed|approval-required` → pipeline завершён

### Движок упал молча? (диагностический рецепт)

Если `LIFECYCLE_START_CHILD_EXITED_BEFORE_RECEIPT: code=1` и непонятно почему —
`stdio:'ignore'` в спавне прячет stderr. Временный diag-патч покажет причину:

1. В `src/infrastructure/engine/legacy-engine-administration.ts`, метод `start()`,
   заменить блок `spawnProcess(...)`:
   ```ts
   // было:
   stdio: 'ignore',
   // стало (временно):
   const diagLog = path.join(os.tmpdir(), `saga-engine-child-${Date.now()}.log`);
   const diagStream = createWriteStream(diagLog, { flags: 'a' });
   // ... spawnProcess('node', cliArgs, { detached:true, stdio:['ignore','pipe','pipe'], env:{...} })
   child.stdout?.pipe(diagStream);
   child.stderr?.pipe(diagStream);
   ```
   (нужны `import os from 'node:os'` и `import { createWriteStream } from 'node:fs'`)

2. `npx tsc` и перезапустить tracker-view

3. Дёрнуть старт, потом прочитать лог:
   ```bash
   cat "$(ls -t /tmp/saga-engine-child-*.log | head -1)"
   ```

4. **После диагноза откатить патч обратно** к `stdio:'ignore'` (не коммитить diag).

Этот рецепт нашёл оба бага текущего прогона (MODULE_NOT_FOUND и ENOENT).

## Известные подводные камни

### 1. `SAGA_PRODUCT_LIFECYCLE_COMPOSITION` обязателен

Без него движок падает с `code=1`, а `stdio:'ignore'` прячет stderr → видно только
`CHILD_EXITED_BEFORE_RECEIPT`. **Задавать при старте tracker-view**, движок
наследует окружение родителя.

### 2. ⚠️ BUG (исправлен): path к orchestrate-cli.js

В `src/app/product-lifecycle-run-starter.ts` и `legacy-engine-administration.ts`
был баг: `path.join(here, '..', '..', 'orchestrate-cli.js')` давал путь в корень
репо (`saga-mcp/orchestrate-cli.js`), но файл реально в `dist/orchestrate-cli.js`.

**Фикс:** spawn-starter теперь использует `path.join(here, '..', 'orchestrate-cli.js')`
(один `..`). legacy-engine-administration — в `dist/infrastructure/engine/`, ему
нужны `..`, `..` → `dist/orchestrate-cli.js` (два `..` корректны для него).
Проверяй: файл должен резолвиться в `<repo>/dist/orchestrate-cli.js`.

### 3. ⚠️ КРИТИЧНО: lifecycle-input путь должен быть ASCII

Windows engine-child получает `--lifecycle-input=<path>` и читает файл через
`readFileSync`. Если путь содержит **кириллицу** (`D:\Разработка\...`), Windows
ANSI codepage ломает её в `??????????` → `ENOENT: no such file or directory`.

**Правило:** клади lifecycle-input **только в ASCII-путь**:
```bash
# ПРАВИЛЬНО:
C:/Users/user/.zcode/blink-input.json
C:/temp/blink-input.json

# НЕПРАВИЛЬНО (кириллица ломает engine):
D:/Разработка/saga-mcp/blink-input.json
```

### 4. `/api/engine/status` врёт на Windows

`alive:false` не значит «движок мёртв» — PowerShell CIM-проверка иногда не находит
процесс в первые секунды. **Источник правды — БД** (`saga3_lifecycle_runs.status`).

### 5. Дубли lifecycle runs

Возникают если запускать несколько раз с разными idempotency-key. Чистый старт =
reset БД. Если нужно удалить один мусорный run, см. SQL-каскад ниже.

### 6. Один lifecycle = одна карточка на доске

«Product Delivery» (родитель) и «Initial Discovery» (вложенная стадия) — это
НЕ две задачи, это один pipeline на двух уровнях детализации.

### 7. НЕ запускай движок через `node ... &` в Bash-tool

Harness убивает child-процессы по завершении tool-call → движок orphan'ится через
пару минут, lease висит. **Запускай только через tracker-view's
`/api/engine/start`** (или веб-форму), который делает настоящий
`child_process.spawn({detached:true})` на уровне ОС — он переживает turn'ы.

## Удаление мусорного lifecycle run (если что-то пошло не так)

```bash
RUN_ID=<id мусорного run'а>  # например 40
node -e "
const D=require('better-sqlite3');
const db=new D('C:/Users/user/.zcode/saga.db');
db.pragma('foreign_keys=OFF');
db.prepare('DELETE FROM saga3_protocol_step_runs WHERE protocol_run_id IN (SELECT id FROM saga3_protocol_runs)').run();
db.prepare('DELETE FROM saga3_protocol_runs').run();
db.prepare('DELETE FROM saga3_process_transitions WHERE lifecycle_run_id=$RUN_ID').run();
db.prepare('DELETE FROM saga3_stage_runs WHERE lifecycle_run_id=$RUN_ID').run();
db.prepare('DELETE FROM saga3_node_runs WHERE process_run_id IN (SELECT id FROM saga3_process_runs WHERE id IN (SELECT process_run_id FROM saga3_stage_runs WHERE lifecycle_run_id=$RUN_ID))').run();
db.prepare('DELETE FROM saga3_stage_runs WHERE lifecycle_run_id=$RUN_ID').run();
db.prepare('DELETE FROM saga3_lifecycle_runs WHERE id=$RUN_ID').run();
db.pragma('foreign_keys=ON');
console.log('run $RUN_ID removed, remaining:', db.prepare('SELECT id,status FROM saga3_lifecycle_runs').all());
"
```

⚠️ Никогда не удаляй run со статусом `running` — это активный pipeline.

## ports и финальный результат

- **Канбан (пульт завода):** http://localhost:4321 — всегда доступен пока жив tracker-view
- **Продукт (Vite dev server):** http://localhost:5173 — поднимется на стадии Development,
  когда dev-воркер соберёт фронт. Не существует до цеха 3.

### Как понять что продукт готов

1. `lifecycle.terminal_status` ∈ `{released, approval-required}` → pipeline завершён
2. В репо продукта появился код (Vite-проект, собранный dev-воркером)
3. Vite dev server отвечает на http://localhost:5173

В режиме `local-dry-run` (composition по умолчанию) Delivery завершается
`approval-required` — это **не ошибка**, а fail-closed: публикация не настроена,
поэтому завод честно говорит «нужна авторизация для релиза». Продукт уже собран
и работает локально, только не опубликован.

### Если нужно перезапустить остановленный движок

```bash
# Остановить
curl -X POST http://localhost:4321/api/engine/stop -H "Content-Type: application/json" -d '{"epic_id":1}'

# Снова запустить (тот же lifecycle продолжится, если не terminal)
curl -X POST http://localhost:4321/api/engine/start \
  -H "Content-Type: application/json" \
  -d '{"epic_id":1,"concurrency":2,"lifecycle_input_path":"C:/Users/user/.zcode/blink-input.json"}'
```

⚠️ Если lifecycle в `terminal_status` (failed/released/...), повторный старт с тем же
idempotency-key вернёт тот же терминальный run. Для нового прогона — новый
idempotency-key или reset БД.
