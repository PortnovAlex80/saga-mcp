# Saga4 Factory — запуск и модель движения работы

Этот документ отвечает на четыре вопроса:

1. Где находится точка старта завода.
2. Что делает кнопка запуска на фронте.
3. Как карточки и рабочие места меняют состояния.
4. Когда завод продолжает работу, приостанавливается или считается завершённым.

Исполняемая модель продукта:

```text
идея на салфетке
  → Discovery
  → Formalization
  → Development
  → Delivery
  → release record
```

Внутренние пользовательские шаги вроде PRD, UC, AC, SRS, planning, implementation, review, integration и verification не являются отдельными lifecycle-цехами. Они являются узлами или рабочими местами внутри четырёх цехов.

## 1. Обязательный выбор режима перед запуском

Если пользователь просит «запустить завод», агент **не должен угадывать режим и
сразу выполнять запуск**. Сначала он показывает следующий нумерованный список и
просит выбрать один вариант:

```text
В каком режиме запустить завод?

1. Resume существующего заказа
   Продолжить тот же production LifecycleRun с последней durable-точки.
   Нужен project_id. Новые Project/Epic/LifecycleRun не создаются.

2. Новый production-заказ
   Создать новый Project и полный live-конвейер из продуктовой идеи.
   Нужна HTTPS-ссылка idea_url. Содержимое ссылки будет заморожено с SHA-256.

3. Тест без LLM — checkpoint replay
   Восстановить diagnostic clone и подставить ранее созданные результаты узлов.
   LLM не вызывается; проверяются runtime, routing, kernel/gate, settlement и
   переходы. Результат никогда не является production-eligible.

4. Тест с реальной LLM — warm start
   Положить ранее созданные документы на рабочий стол как draft и запустить
   настоящего author/reviewer. Проверяются инструкции, инструменты, feedback,
   логи и переходы, но модель не пишет весь материал с нуля. Тестовый check plan
   может не запускать дорогие внешние/NFR-проверки; они отмечаются not_run, а не
   passed. Результат не является production-eligible.
```

После списка агент запрашивает только данные выбранного режима:

| Режим | Что запросить |
|---|---|
| 1. Resume | `project_id` |
| 2. Новый production | `idea_url` |
| 3. Без LLM | checkpoint manifest/ref, diagnostic clone/target и нужную точку replay |
| 4. LLM warm start | `project_id` или diagnostic clone, checkpoint/fixture и проверяемый узел/цикл review |

Если пользователь уже явно назвал один из четырёх режимов и передал все
обязательные данные, повторный вопрос не нужен. Во всех остальных случаях агент
обязан дождаться выбора до любых изменений БД, файлов или запуска процессов.

Режимы 1 и 2 входят через единственный публичный gateway
`POST /api/factory/start`. Режимы 3 и 4 являются диагностическими операциями и
сначала готовят checkpoint clone/adoption или warm-start fixture; они не должны
маскироваться под production-start.

Для нового production-заказа не нужен готовый PRD, список требований или
архитектура. Нужна только HTTPS-ссылка на продуктовую идею. Идея является сырьём
Discovery; оператор не создаёт вручную стартовую task, brief, PRD или SRS.

## 2. Запуск с фронта

### Запустить пульт

```bash
cd /d/Разработка/saga-mcp

DB_PATH='C:/Users/user/.zcode/saga.db' \
SAGA_PRODUCT_LIFECYCLE_COMPOSITION='D:/Разработка/saga-mcp/tracker-view/product-delivery-composition.mjs' \
SAGA_FACTORY_CHECKPOINT_STORE='C:/Users/user/.zcode/factory-checkpoints' \
SAGA_FACTORY_CHECKPOINT_LOGS=1 \
node tracker-view/tracker-view.mjs
```

`SAGA_FACTORY_CHECKPOINT_STORE` включает online-чекпойнты после каждого lifecycle cycle
(backup БД + content-addressing артефактов + manifest digest). Это defense-in-depth для
disaster recovery и cross-machine restore — НЕ единственный механизм resume (resume работает
из lifecycle-state в БД), но обязательный для production reliability. Никогда не запускайте
завод без этого флага.

Открыть:

```text
http://localhost:4321/admin
```

В форме **«Идея на салфетке → запустить завод»** заполнить поля и нажать:

```text
Создать и запустить завод
```

Модель по умолчанию — **GLM 4.7**. Она фиксируется в `lifecycle_execution_controls` до появления первой claimable-карточки. Первый background engine также получает эту модель через собственное окружение, поэтому запуск не зависит от случайного глобального model alias предыдущего проекта.

#### Модельный каталог и лимиты

Единственный каталог облачных маршрутов — `FACTORY_CLOUD_MODELS`
(`src/runtime/factory-model-profiles.ts`, тот же список отдаёт
`GET /api/models`):

| Модель | effort по умолчанию | limit (потолок воркеров) | Примечание |
|---|---|---|---|
| `glm-4.7` | high | 2 | рекомендуемый default (sonnet-уровень) |
| `glm-5-turbo` | high | 5 | flagship |
| `glm-5.2` | high | 10 | operator-approved потолок 10 |
| `glm-5.3` | max | 6 | максимум рассуждений, conscious token cost |

- `effort` — уровни claude CLI `--effort` (`low | medium | high | xhigh | max`).
- `limit` — безопасный потолок параллельных воркеров для аккаунта
  провайдера (не множитель токенов). Эффективный параллелизм =
  `min(concurrency оператора, limit модели)` (`effectiveFactoryConcurrency`);
  некорректная политика падает fail-closed, а не молча развязывает очередь.
- Смена модели на доске: `POST /api/model/set` с
  `{"model":"<id>","epic_id":<N>}` (тот же селектор моделей канбана).
  Маршрут читается из `lifecycle_execution_controls` при каждом назначении
  воркера и замораживается в его execution_context — **уже работающие
  воркеры доигрывают на старой модели**, новая действует с момента claim.
- Параллелизм меняется отдельно: `POST /api/factory/concurrency` с
  `{"epic_id":<N>,"concurrency":<M>}` (1..10, всегда ограничен снизу
  лимитом модели).

#### Наблюдатель core-view

Рядом с пультом можно поднять read-only наблюдатель ядра:

```bash
node core-view/server.mjs   # http://localhost:4323
```

core-view — только GET-проекции над той же БД (snapshot/events/log-tail),
никаких write-эндпоинтов и кнопок: интервенции остаются в `/admin`.
Подробности — `docs/design/FACTORY-CORE-VIEW.md`.

Форма возвращает:

- `project_id`;
- `epic_id`;
- `lifecycle_run_id`;
- фактическую модель;
- фактический параллелизм.

### Что делает кнопка

Кнопка выполняет один согласованный bootstrap:

1. Создаёт Project.
2. Регистрирует control repository и локальный checkout.
3. Инициализирует Git HEAD, если репозиторий пустой.
4. Создаёт Epic.
5. Фиксирует model route и concurrency.
6. Собирает immutable Product Delivery input из идеи и реального Git HEAD.
7. Создаёт durable LifecycleRun.
8. Запускает background orchestrator.

Успешный HTTP-ответ означает не просто spawn процесса, а подтверждение, что LifecycleRun уже записан в БД.

### API-эквивалент

```bash
curl -X POST http://localhost:4321/api/factory/start \
  -H 'Content-Type: application/json' \
  -d '{"idea_url":"https://docs.example.com/sales-assistant-idea"}'
```

### Запуск на локальной модели (LM Studio)

Единственный runtime-переключатель — селектор моделей канбана
(`POST /api/model/set` с `{"model":"<id>","epic_id":<N>}`). Смена действует
с момента claim: маршрут читается из `lifecycle_execution_controls` при каждом
назначении воркера и замораживается в его execution_context. Активные воркеры
дорабатывают на старой модели.

Побочный эффект: переключение на LM Studio перезаписывает
`~/.claude/settings.json` (двухшаблонная схема `settings.cloud.json` ↔
`settings.lmstudio.json`, атомарно + fsync + readback). В claude CLI v2
spawn-env `ANTHROPIC_BASE_URL` больше не перекрывает settings.json, поэтому
на локальную модель переключается **весь claude на машине**, а не только
воркеры эпизода. Обратно на облако — выбрать модель группы «Z.ai (облако)»;
облачный токен заморожен в `settings.cloud.json` и не теряется.

**Гонка нового заказа.** Оба стартовых пути (`factory.mjs start`,
`POST /api/factory/start`) записывают в `lifecycle_execution_controls`
облачный профиль (каталог z.ai — единственный захардкоженный) и сразу
спавнят движок. Первый claim может заморозиться на облаке раньше, чем
оператор переключит селектор. Проверенное восстановление:

1. Убить облачного воркера (`claude ... --bare`) и процесс orchestrate-cli.
2. `node scripts/factory.mjs resume <db>` — **без флагов**: он адоптирует
   активный launch, supervision пометит потерянного воркера `lost`
   (`REAPED ... action=lost`), lifecycle возобновится, и тот же task
   перезаклеймится уже на локальную модель. (CLI-resume спавнит движок с
   `<db>/package-store` — см. оговорку о двойном package-store ниже;
   если остальные движки этой БД пущены панелью, resume лучше делать
   кнопкой Resume / `POST /api/factory/start`.)
3. `--recover-orphaned-launch` НЕ подходит сразу после kill: он требует уже
   детектированного `lost` + `repair_wait`; обычный resume сам доводит
   состояние до этого.

Проверка победы: новый процесс `claude -p --bare --model <локальная-модель>`
и **без** `--effort` — ветка LM Studio опускает effort целиком.

Для resume существующего заказа гонки нет: строка controls уже локальная.

**Двойной package-store root — почему движки пускать через панель.**
`scripts/factory.mjs` задаёт `SAGA_PACKAGE_STORE_DIR=<каталог-БД>/package-store`,
а спавн через панель (`/admin`, `POST /api/factory/start`, resume) не задаёт
его вовсе — движок использует дефолт `<repoRoot>/.saga/package-store`.
Если на одной БД запустить движок из CLI и из панели, они разъедутся по двум
разным package-store: установки задублируются, а resume одного и того же
launch'а увидит «чужие» package bytes. Поэтому рабочий режим — **все движки
пускать через панель** (один и тот же корень по умолчанию); `factory.mjs`
оставлен как аварийный/скриптовый путь и требует явного
`SAGA_PACKAGE_STORE_DIR`, совпадающего с остальными движками этой БД.
Дополнительное отличие: `factory.mjs` спавнит движок с наследуемым stdio
(панель — detached с логом в файл, см. §9), поэтому CLI-движок умирает
вместе с терминалом.

## 3. Кто чем владеет

### LifecycleRun

Владеет маршрутом между цехами:

```text
Discovery → Formalization → Development → Delivery
```

Только lifecycle routing решает, какой цех запускается следующим. Модуль не имеет права сам запускать соседний модуль.

### ProcessRun

Один запуск одного цеха. Цех обязан закончиться локальным outcome и, если outcome допускает передачу дальше, immutable product/certificate.

### Workplace

Стабильное рабочее место внутри ProcessRun. Оно владеет:

- карточкой на доске;
- desk/workspace;
- текущей ролью author/reviewer;
- loop state;
- CandidateSet и gate lineage.

Worker не владеет карточкой. Worker — одноразовый исполнитель, который приходит на Workplace по fenced reservation. При repair приходит новый worker на то же рабочее место.

### Task

`tasks` — человекочитаемая Kanban-проекция Workplace. Это не второй независимый автомат. Источник истины для внутреннего цикла — `v4_workplaces`; task status должен отражать его состояние.

## 4. Состояния карточки и Workplace

Используются только легальные Kanban-статусы:

```text
todo
in_progress
review
review_in_progress
done
blocked
failed
cancelled
```

Внутренний loop state Workplace:

```text
idle
queued
leased
running
verifying
repair_wait
paused
terminal
```

Нормальный author/reviewer-проход:

```text
Workplace queued, next_role=author
  task: todo

worker claim
  Workplace: leased/running
  task: in_progress

worker seals author CandidateSet
  Workplace: verifying или queued, next_role=reviewer
  task: review

reviewer claim
  Workplace: leased/running
  task: review_in_progress

final gate accepted
  Workplace: terminal, terminal_reason=accepted
  task: done
```

Для code-changing task принятие качества и интеграция различаются:

```text
task.status = done
integration_state = pending
  → deterministic integration
integration_state = merged
  → зависимые задачи могут стать claimable
```

`done` без `merged` не открывает зависимую code task.

### Repair

```text
final/author gate: repair_required
  → создаётся RecoveryIssue
  → тот же Workplace сохраняется
  → та же карточка возвращается в todo
  → next_role указывает author или reviewer
  → приходит новый fenced worker
```

Нельзя создавать новую карточку только потому, что сменился worker. Иначе теряются desk, lineage и rejected CandidateSet.

### Исчерпание бюджета ремонта (ADR-075 — без человека в цикле качества)

В клетках качества `onExhausted='requeue'`: при исчерпании `maxAttempts`
бюджет **прокатывается в новую recovery-эпоху** — в immutable-таблицу
`factory_workplace_recovery_epochs` дописывается строка с базовой линией
счётчиков попыток, линия выдерживает экспоненциальный беккофф (1–15 мин) и
продолжает работу автономно. Линия никогда не паркуется «для человека».

Единственный не-человеческий предохранитель: суммарный потолок попыток
(`recovery.totalAttempts`, по умолчанию 30) — при его достижении линия
честно завершается `terminal failed` с диагнозом последнего отказа в логе
(`[recovery-budget] TOTAL-CAP …`). Продолжение — новый Factory Start /
continuation поверх принятого префикса.

### Human required (только Delivery и инфраструктура)

```text
gate: human_required
  → Workplace paused или blocked
  → карточка не claimable
  → создаётся durable human interaction/request
```

Человек требуется только там, где нужна физическая инфраструктура или
внешняя авторизация: approval релиза в Delivery, заблокированные
post-acceptance эффекты (например, git-integration), поломка спавна воркеров.
Клетки качества человека не требуют (см. ADR-075). После решения человека
завод возобновляет тот же Workplace, а не создаёт новый продуктовый поток.

### Failed и cancelled

`failed` и `cancelled` терминальны для конкретного рабочего места. Lifecycle может завершиться соответствующим terminal outcome либо остановиться на уровне текущего цеха. Нельзя превращать failure в `done` ручным SQL.

## 5. Переход между рабочими местами и цехами

Карточка не переезжает из Discovery в Formalization. Между цехами передаётся не task, а immutable handoff:

```text
StageRun A
  → local outcome
  → certificate/product ref + hash
  → atomic lifecycle transition
  → новый StageRun B
  → новые Workplace цеха B
```

Поэтому одновременно истинны два правила:

- внутри repair/review цикла сохраняется то же Workplace;
- при переходе в следующий цех создаются новые Workplace, связанные точными ProductRef/hash предыдущего цеха.

## 6. Что выпускает каждый цех

### Discovery

Вход: сырая идея, контекст, evidence и constraints.

Продукт: discovery certificate с outcome и точной lineage.

Production-сценарий записывает силу идеи и передаёт сертификат в Formalization. Formalization остаётся реальным build gate. Строгий regulated-сценарий может останавливать маршрут раньше.

### Formalization

Внутри производит и согласует:

```text
PRD + FR/NFR/RULE
  → UC
  → AC
  → reconciliation
  → frozen acceptance baseline
  → SRS/decomposition
```

Продукт: immutable Solution Contract certificate.

Только `formalized` передаётся в Development. Clarification, inconsistency и infeasibility завершают маршрут явным terminal status.

### Development

Внутри:

1. Planner предлагает task graph.
2. Kernel проверяет DAG, coverage, repositories и lineage.
3. Kernel материализует implementation/review/integration/verification workplaces.
4. Workers выполняют карточки через общую очередь.
5. Code-changing результаты проходят review и deterministic integration.
6. Verification evidence привязывается к неизменному frozen candidate.
7. Settlement выпускает verified integration bundle.

Критический инвариант:

```text
Development НЕ может settle как verified,
пока все спроецированные задачи не достигли terminal состояния,
все обязательные code changes не integrated,
а evidence не привязана к точному candidate hash.
```

Пока это не выполнено, ProcessRun остаётся paused/awaiting implementation. Conveyor продолжает разбирать доступные карточки и затем повторно запускает тот же settlement node.

### Delivery

Внутри:

```text
preflight
  → human approval, если требует policy
  → publish/deploy desired-state actions
  → authoritative observation
  → settlement
```

Продукт: release record и delivery certificate.

Успешный `git push` или ответ deploy-команды сам по себе не считается release. Нужна authoritative observed state каждого обязательного destination.

## 7. Когда завод должен продолжать работу

Завод работает автоматически, пока выполняется хотя бы одно условие:

- текущий Flow имеет следующий node;
- существует claimable Workplace;
- Development ждёт незавершённые projected tasks;
- активен reviewer/repair loop;
- можно выполнить deterministic integration или verification;
- local outcome текущего цеха маршрутизируется в следующий цех.

Завод не должен завершать background loop только потому, что один worker вышел. Один worker обслуживает одну reservation; orchestrator обязан продолжить с очередью или с текущим ProcessRun.

Законный останов происходит только при:

- lifecycle terminal outcome;
- durable pause (Delivery approval / инфраструктурные границы — ADR-075
  убрал человеческие паузы из цикла качества: исчерпание бюджета ремонта
  продолжается эпохами ретраев до честного terminal failed по потолку);
- human approval required (Delivery);
- exhausted recovery policy (суммарный потолок попыток — terminal failed);
- explicit operator stop/cancel;
- infrastructure failure, зафиксированном как failure, а не замаскированном под success.

Happy path завершён только после:

```text
Discovery certificate
+ Solution Contract
+ verified Development bundle
+ observed Delivery release record
```

## 8. Start, Stop и Resume на доске

На странице проекта доступны:

- выбор модели;
- concurrency;
- кнопка Start;
- Stop;
- Resume для существующего заказа по номеру Project.

Для нового продукта предпочтителен `/admin` → «Идея на салфетке → запустить завод», потому что этот путь создаёт корректный lifecycle input.

Для paused LifecycleRun:

1. Не пересоздавать Project/Epic.
2. Не создавать новую стартовую task.
3. Нажать Resume или вызвать единую стартовую точку:

```bash
curl -X POST http://localhost:4321/api/factory/start \
  -H 'Content-Type: application/json' \
  -d '{"project_id": 1}'
```

Resume обязан использовать уже сохранённые lifecycle input, StageRun, ProcessRun, Workplace и products.

### Пауза и остановка

**Операторский soft-stop (тормоз движка).** Штатная остановка — не `kill -9`
и не закрытие терминала:

```bash
# из UI доски — кнопка Stop, или:
curl -X POST http://localhost:4321/api/factory/stop \
  -H 'Content-Type: application/json' -d '{"epic_id": 1}'

# CLI-эквивалент (тот же операторский протокол):
node scripts/factory.mjs stop <db-path> --project N [--dry-run] [--reason <текст>]
```

Протокол идемпотентный и многофазный (фазы durable в
`factory_worker_stops.phase`): план остановки → тормоз движка
(`brakeEnginesForProject` — убивает только pid, чья command line содержит
`orchestrate-cli.js`; чужой/переиспользованный pid никогда не трогается) →
fence и откат `leased/running` воркеров в точку до найма (карточка
возвращается в очередь, ни один WorkerExecution не теряется — он честно
терминалится) → kill/reap при необходимости → checkpoint. После soft-stop
завод возобновляется обычным Resume — новые Project/Epic/LifecycleRun не
создаются.

**Если остановилась панель.** Движок спавнится detached (`child.unref()`) и
живёт независимо от панели: закрытие/рестарт панели НЕ останавливает завод,
воркеры доигрывают. Обратная сторона — вместе с панелью умирает и engine
supervisor (watchdog, см. ниже): пока панели нет, замёрзший движок никто не
лечит. Перезапустили панель — supervisor подхватил launch'ы по durable-полям
(`factory_launch_requests.engine_log_path/engine_pid`) и продолжает
наблюдение, включая бюджет рестартов (он хранится в
`factory_engine_watchdog_events`, а не в памяти панели).

**Если остановился/умер движок.** Воркеры — отдельные процессы (claude CLI);
они доигрывают свой lease и сдают материал через MCP-сервер, который пишет
БД независимо от движка. Потерянные воркеры (процесс убит, lease истёк)
помечаются supervision как `lost` при следующем resume/adoption и
перезаклеймиваются. Recovery здесь — Resume, а не пересоздание заказа.

**Watchdog: что делает supervisor сам.** Пока панель работает, engine
supervisor (слой C антифриза) сам наблюдает и лечит движки: каждые 30 с
проверяет каждый running launch; живой pid + heartbeat старше 120 с = фриз
главного потока → durable-события `freeze_detected`/`restart_attempted`
пишутся ДО остановки → soft-stop тормозом → рестарт штатным resume-кодом
панели; backoff 1→5→15 минут, бюджет 5 попыток за 2 часа. Мёртвый pid
помечается одной durable-записью `engine_dead`, дубли спавнов
блокируются (`sweepBeforeSpawn` перед каждым спавном панели:
`ok:'already-running'` или guarded-kill замёрзшего трупа). Отключить:
`SAGA_ENGINE_SUPERVISOR=0`; тюнинг: `SAGA_ENGINE_SUPERVISOR_INTERVAL_MS`,
`SAGA_ENGINE_SUPERVISOR_STALE_MS`.

**Когда всё-таки нужен человек.** После исчерпания бюджета (5/2ч) supervisor
не рестартует движок молча: он ставит `engine_state='failed_watchdog'` +
`last_error` — это видно на доске и в `GET /api/factory/status` (поля
`engine_state`/`engine_error`/`watchdog`). Дальше решение оператора:
посмотреть лог движка и phase-маркер (§9), понять причину фриза, починить
окружение и нажать Resume. Это единственная «человеческая» граница движка;
в цикле качества людей нет (ADR-075 — исчерпание бюджета ремонта
прокатывается в recovery-эпохи до честного terminal failed по суммарному
потолку).

## 9. Наблюдение

Пульт:

```text
http://localhost:4321/?project=<PROJECT_ID>
```

Heartbeat:

```bash
curl http://localhost:4321/api/heartbeat
```

Статус engine (включая watchdog-поля):

```bash
curl 'http://localhost:4321/api/factory/status?epic_id=<EPIC_ID>'
```

Ответ кроме `running/pid/concurrency/model/model_limit` несёт
антифриз-поля: `engine_state` (в т.ч. `failed_watchdog` после исчерпания
бюджета supervisor'а), `engine_error` (последняя ошибка) и `watchdog`
(новейшее событие из `factory_engine_watchdog_events`: kind, reason,
engine_pid, heartbeat_age_ms).

Логи и маркеры живости движка. Движок пишет весь свой лог ТОЛЬКО в файл
`$SAGA_ENGINE_LOG` (stdout-пайпа не существует — класс фризов
stdout-backpressure устранён; в файл же дублируется stderr краш-диагностики).
Путь лога durability-привязан к launch'у:

```sql
SELECT engine_log_path, engine_pid, engine_spawned_at
  FROM factory_launch_requests ORDER BY rowid DESC LIMIT 1;
```

Рядом с логом — маркеры живости:

```text
$SAGA_ENGINE_LOG.heartbeat   -- mtime обновляется каждые ≤5 с
$SAGA_ENGINE_LOG.phase       -- последняя фаза главного цикла движка
```

Живой pid + неменяющийся mtime heartbeat = фриз главного потока; это же
условие (старше 120 с) детектирует panel-side supervisor. Человек при
диагностике читает лог+phase; лечением (stop/рестарт/backoff) обычно занят
сам supervisor — вмешиваться нужно только после `failed_watchdog`.

Durable-журнал watchdog (кто/когда/почему останавливал и рестартовал):

```sql
SELECT * FROM factory_engine_watchdog_events ORDER BY rowid DESC LIMIT 20;
```

Ключевые строки в логе движка, которые стоит грепать:

```text
[recovery-budget] ROLLOVER ...    -- бюджет ремонта прокатился в новую
                                    recovery-эпоху (ADR-075, без человека)
[recovery-budget] TOTAL-CAP ...   -- суммарный потолок попыток достигнут:
                                    честный terminal failed
[obligation-reconciler] sweep dispatched=... -- проход метлы обязательств
[obligation-reconciler] DEFER/FAIL ...       -- типизированное ожидание/отказ
                                               (throttled, с номером попытки)
[obligation-reconciler] defer-only streak=... -- серия чистых DEFER: лифт
                                                ждёт постусловий
```

Наблюдатель ядра (read-only, без кнопок): `http://localhost:4323`
(`node core-view/server.mjs`) — цепочка, пульс, хроника.

При диагностике всегда различать:

- lifecycle status;
- current stage;
- ProcessRun status;
- Workplace loop state;
- task Kanban projection;
- worker execution liveness;
- integration state.

## 10. Безопасность оператора

Перед ручным вмешательством сделать snapshot БД.

Нельзя:

- удалять `saga.db`, если нужен прогресс;
- вручную менять accepted artifacts или hashes;
- переводить task в `done` SQL-командой;
- удалять ProcessRun/StageRun для «разблокировки»;
- удалять paused Project — paused lifecycle является живым и resumable;
- повторно отправлять изменённый lifecycle input под тем же idempotency key;
- убивать worker и сразу назначать второго без истечения/release fence.

Проблема решается через resume, recovery, cancel или новый lifecycle run с новым idempotency key — не разрушением audit trail.
