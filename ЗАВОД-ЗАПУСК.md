# Saga4 Factory — запуск и модель движения работы

Этот документ отвечает на четыре вопроса:

1. Где находится точка старта завода.
2. Что делает кнопка запуска на фронте.
3. Как карточки и рабочие места меняют состояния.
4. Когда завод продолжает работу, приостанавливается или считается завершённым.

Исполняемая модель продукта:

```text
идея на салфетке
  → Discovery
  → Formalization
  → Development
  → Delivery
  → release record
```

Внутренние пользовательские шаги вроде PRD, UC, AC, SRS, planning, implementation, review, integration и verification не являются отдельными lifecycle-цехами. Они являются узлами или рабочими местами внутри четырёх цехов.

## 1. Точка старта: идея на салфетке

Для запуска не нужен готовый PRD, список требований или архитектура. Достаточно:

- короткого имени продукта;
- одной-двух фраз о проблеме или желаемом результате;
- локального пути к репозиторию, если путь по умолчанию не подходит;
- модели;
- допустимого параллелизма.

Пример входа:

```text
Имя: sales-assistant
Идея: система помогает маленькой компании не терять заявки и подсказывает менеджеру следующий шаг по каждой продаже.
Модель: glm-4.7
Параллелизм: 4
```

Идея является сырьём Discovery. Оператор не должен вручную создавать стартовую task, brief, PRD или SRS.

## 2. Запуск с фронта

### Запустить пульт

```bash
cd /d/Development/saga-mcp

DB_PATH='C:/Users/user/.zcode/saga.db' \
SAGA_PRODUCT_LIFECYCLE_COMPOSITION='D:/Development/saga-mcp/tracker-view/product-delivery-composition.mjs' \
node tracker-view/tracker-view.mjs
```

Открыть:

```text
http://localhost:4321/admin
```

В форме **«Идея на салфетке → запустить завод»** заполнить поля и нажать:

```text
Создать и запустить завод
```

Модель по умолчанию — **GLM 4.7**. Она фиксируется в `lifecycle_execution_controls` до появления первой claimable-карточки. Первый background engine также получает эту модель через собственное окружение, поэтому запуск не зависит от случайного глобального model alias предыдущего проекта.

Форма возвращает:

- `project_id`;
- `epic_id`;
- `lifecycle_run_id`;
- фактическую модель;
- фактический параллелизм.

### Что делает кнопка

Кнопка выполняет один согласованный bootstrap:

1. Создаёт Project.
2. Регистрирует control repository и локальный checkout.
3. Инициализирует Git HEAD, если репозиторий пустой.
4. Создаёт Epic.
5. Фиксирует model route и concurrency.
6. Собирает immutable Product Delivery input из идеи и реального Git HEAD.
7. Создаёт durable LifecycleRun.
8. Запускает background orchestrator.

Успешный HTTP-ответ означает не просто spawn процесса, а подтверждение, что LifecycleRun уже записан в БД.

### API-эквивалент

```bash
curl -X POST http://localhost:4321/api/factory/start \
  -H 'Content-Type: application/json' \
  -d '{"idea_url":"https://docs.example.com/sales-assistant-idea"}'
```

## 3. Кто чем владеет

### LifecycleRun

Владеет маршрутом между цехами:

```text
Discovery → Formalization → Development → Delivery
```

Только lifecycle routing решает, какой цех запускается следующим. Модуль не имеет права сам запускать соседний модуль.

### ProcessRun

Один запуск одного цеха. Цех обязан закончиться локальным outcome и, если outcome допускает передачу дальше, immutable product/certificate.

### Workplace

Стабильное рабочее место внутри ProcessRun. Оно владеет:

- карточкой на доске;
- desk/workspace;
- текущей ролью author/reviewer;
- loop state;
- CandidateSet и gate lineage.

Worker не владеет карточкой. Worker — одноразовый исполнитель, который приходит на Workplace по fenced reservation. При repair приходит новый worker на то же рабочее место.

### Task

`tasks` — человекочитаемая Kanban-проекция Workplace. Это не второй независимый автомат. Источник истины для внутреннего цикла — `v4_workplaces`; task status должен отражать его состояние.

## 4. Состояния карточки и Workplace

Используются только легальные Kanban-статусы:

```text
todo
in_progress
review
review_in_progress
done
blocked
failed
cancelled
```

Внутренний loop state Workplace:

```text
idle
queued
leased
running
verifying
repair_wait
paused
terminal
```

Нормальный author/reviewer-проход:

```text
Workplace queued, next_role=author
  task: todo

worker claim
  Workplace: leased/running
  task: in_progress

worker seals author CandidateSet
  Workplace: verifying или queued, next_role=reviewer
  task: review

reviewer claim
  Workplace: leased/running
  task: review_in_progress

final gate accepted
  Workplace: terminal, terminal_reason=accepted
  task: done
```

Для code-changing task принятие качества и интеграция различаются:

```text
task.status = done
integration_state = pending
  → deterministic integration
integration_state = merged
  → зависимые задачи могут стать claimable
```

`done` без `merged` не открывает зависимую code task.

### Repair

```text
final/author gate: repair_required
  → создаётся RecoveryIssue
  → тот же Workplace сохраняется
  → та же карточка возвращается в todo
  → next_role указывает author или reviewer
  → приходит новый fenced worker
```

Нельзя создавать новую карточку только потому, что сменился worker. Иначе теряются desk, lineage и rejected CandidateSet.

### Human required

```text
gate: human_required
  → Workplace paused или blocked
  → карточка не claimable
  → создаётся durable human interaction/request
```

После решения человека завод возобновляет тот же Workplace, а не создаёт новый продуктовый поток.

### Failed и cancelled

`failed` и `cancelled` терминальны для конкретного рабочего места. Lifecycle может завершиться соответствующим terminal outcome либо остановиться на уровне текущего цеха. Нельзя превращать failure в `done` ручным SQL.

## 5. Переход между рабочими местами и цехами

Карточка не переезжает из Discovery в Formalization. Между цехами передаётся не task, а immutable handoff:

```text
StageRun A
  → local outcome
  → certificate/product ref + hash
  → atomic lifecycle transition
  → новый StageRun B
  → новые Workplace цеха B
```

Поэтому одновременно истинны два правила:

- внутри repair/review цикла сохраняется то же Workplace;
- при переходе в следующий цех создаются новые Workplace, связанные точными ProductRef/hash предыдущего цеха.

## 6. Что выпускает каждый цех

### Discovery

Вход: сырая идея, контекст, evidence и constraints.

Продукт: discovery certificate с outcome и точной lineage.

Production-сценарий записывает силу идеи и передаёт сертификат в Formalization. Formalization остаётся реальным build gate. Строгий regulated-сценарий может останавливать маршрут раньше.

### Formalization

Внутри производит и согласует:

```text
PRD + FR/NFR/RULE
  → UC
  → AC
  → reconciliation
  → frozen acceptance baseline
  → SRS/decomposition
```

Продукт: immutable Solution Contract certificate.

Только `formalized` передаётся в Development. Clarification, inconsistency и infeasibility завершают маршрут явным terminal status.

### Development

Внутри:

1. Planner предлагает task graph.
2. Kernel проверяет DAG, coverage, repositories и lineage.
3. Kernel материализует implementation/review/integration/verification workplaces.
4. Workers выполняют карточки через общую очередь.
5. Code-changing результаты проходят review и deterministic integration.
6. Verification evidence привязывается к неизменному frozen candidate.
7. Settlement выпускает verified integration bundle.

Критический инвариант:

```text
Development НЕ может settle как verified,
пока все спроецированные задачи не достигли terminal состояния,
все обязательные code changes не integrated,
а evidence не привязана к точному candidate hash.
```

Пока это не выполнено, ProcessRun остаётся paused/awaiting implementation. Conveyor продолжает разбирать доступные карточки и затем повторно запускает тот же settlement node.

### Delivery

Внутри:

```text
preflight
  → human approval, если требует policy
  → publish/deploy desired-state actions
  → authoritative observation
  → settlement
```

Продукт: release record и delivery certificate.

Успешный `git push` или ответ deploy-команды сам по себе не считается release. Нужна authoritative observed state каждого обязательного destination.

## 7. Когда завод должен продолжать работу

Завод работает автоматически, пока выполняется хотя бы одно условие:

- текущий Flow имеет следующий node;
- существует claimable Workplace;
- Development ждёт незавершённые projected tasks;
- активен reviewer/repair loop;
- можно выполнить deterministic integration или verification;
- local outcome текущего цеха маршрутизируется в следующий цех.

Завод не должен завершать background loop только потому, что один worker вышел. Один worker обслуживает одну reservation; orchestrator обязан продолжить с очередью или с текущим ProcessRun.

Законный останов происходит только при:

- lifecycle terminal outcome;
- durable pause;
- human approval required;
- exhausted recovery policy;
- explicit operator stop/cancel;
- infrastructure failure, зафиксированном как failure, а не замаскированном под success.

Happy path завершён только после:

```text
Discovery certificate
+ Solution Contract
+ verified Development bundle
+ observed Delivery release record
```

## 8. Start, Stop и Resume на доске

На странице проекта доступны:

- выбор модели;
- concurrency;
- кнопка Start;
- Stop;
- Resume для существующего заказа по номеру Project.

Для нового продукта предпочтителен `/admin` → «Идея на салфетке → запустить завод», потому что этот путь создаёт корректный lifecycle input.

Для paused LifecycleRun:

1. Не пересоздавать Project/Epic.
2. Не создавать новую стартовую task.
3. Нажать Resume или вызвать единую стартовую точку:

```bash
curl -X POST http://localhost:4321/api/factory/start \
  -H 'Content-Type: application/json' \
  -d '{"project_id": 1}'
```

Resume обязан использовать уже сохранённые lifecycle input, StageRun, ProcessRun, Workplace и products.

## 10. Безопасность оператора

Перед ручным вмешательством сделать snapshot БД.

Нельзя:

- удалять `saga.db`, если нужен прогресс;
- вручную менять accepted artifacts или hashes;
- переводить task в `done` SQL-командой;
- удалять ProcessRun/StageRun для «разблокировки»;
- удалять paused Project — paused lifecycle является живым и resumable;
- повторно отправлять изменённый lifecycle input под тем же idempotency key;
- убивать worker и сразу назначать второго без истечения/release fence.

Проблема решается через resume, recovery, cancel или новый lifecycle run с новым idempotency key — не разрушением audit trail.

## 11. Короткая проверка здорового запуска

После нажатия кнопки должны быть истинны все утверждения:

```text
Project существует
Epic существует
Repository имеет реальный HEAD
lifecycle_execution_controls.model_name = glm-4.7 (по умолчанию)
LifecycleRun существует
current_stage_id = initial-discovery или более поздняя стадия
нет вручную созданной discovery.kickstart task
первая LM-карточка привязана к process_run_id/Workplace
worker claim переводит author в in_progress, reviewer в review_in_progress
```

После полного happy path:

```text
LifecycleRun.status = completed
LifecycleRun.terminal_status = released
все обязательные StageRun completed
Development candidate verified и неизменен
Delivery destinations наблюдены в desired state
```
