# Saga4 Factory — единая инструкция запуска (только opencode)

> **Единственный канонический документ запуска завода.** Слияние бывшего
> `ЗАВОД-ЗАПУСК.md` (панель, режимы, модель движения работы) и бывшего
> `docs/FACTORY-START-QUICKSTART.md` (CLI, preflight, checkpoint-restore,
> мониторинг) от 2026-08-20. Дубликаты убраны; спорные места сверены с кодом:
> каталог моделей — `src/runtime/factory-model-profiles.ts`, порт core-view —
> `core-view/server.mjs`, схема — `src/db.ts` (`SCHEMA_VERSION`).

Этот документ отвечает на вопросы:

1. На чём running воркеры и как это проверить перед запуском.
2. Где находится точка старта завода (панель и CLI).
3. Как карточки и рабочие места меняют состояния.
4. Когда завод продолжает работу, приостанавливается или считается завершённым.
5. Как наблюдать, мониторить и безопасно вмешиваться.

Исполняемая модель продукта:

```text
идея на салфетке
  → Discovery
  → Formalization
  → Development
  → Delivery
  → release record
```

Внутренние пользовательские шаги вроде PRD, UC, AC, SRS, planning, implementation, review, integration и verification не являются отдельными lifecycle-цехами. Они являются узлами или рабочими местами внутри четырёх цехов.

## 1. Бэкенд воркеров — ТОЛЬКО opencode (директива оператора 2026-08-20)

Claude Code CLI отставлен. Все заводские воркеры и весь агентный инструментарий
этого репо идут через opencode. claude CLI никогда не вызывается напрямую,
никаким агентом, ни по какой причине.

**Причина директивы: claude (Anthropic) стал очень дорогим** для заводских
нагрузок — стоимость подписки/токенов Anthropic несоразмерна объёму
конвейерной работы. Завод переехал на opencode через agent-proxy
(`tools/agent-proxy/claude-shim.mjs` → `opencode run`, официальный провайдер
Z.AI Coding Plan); переезд проверен полным производственным прогоном.

**Запрет вшит в код** (`tracker-view/claude-runner.mjs`): `isForbiddenClaudeCli()`
+ fail-closed `resolveExecutorPath()` — любой резолв в claude CLI (дефолтный
`'claude'`, путь к бинарнику, VS Code-расширение) роняет спавн с ошибкой
`FACTORY_CLAUDE_BACKEND_FORBIDDEN`. Никакого тихого фолбэка: забыли env —
первый же воркер громко откажется стартовать, а не спишет деньги Anthropic.

**Обязательно перед любым `factory start/resume`** (и в env панели, если движок
спавнится панелью):

```bash
export SAGA_REAL_CLAUDE_PATH="node D:/Development/saga-mcp/tools/agent-proxy/claude-shim.mjs"
```

Путь без пробелов (spawnClaude режет составные пути по пробелам). Фолбэка на
claude больше нет — без этой переменной завод не запускать.

**Три жёстких правила:**

- НИКОГДА не трогать, не переписывать, не «восстанавливать»
  `~/.claude/settings.json`. Его sha256 — трипвайр: если файл изменился во
  время прогона завода, это условие ABORT — расследовать, а не править назад.
- Держать `SAGA_MODEL_SWITCH_SKIP_CLAUDE_SETTINGS=1` в env трекера/движка,
  чтобы `POST /api/model/set` не мог переписать его тоже.
- Схема LM Studio через перезапись `~/.claude/settings.json`
  (двухшаблонная `settings.cloud.json` ↔ `settings.lmstudio.json`) отставлена
  вместе с claude CLI. В мире opencode локальная модель — это провайдер в
  конфиге opencode; в производственную директиву она не входит.

**Как работает shim** (`tools/agent-proxy/claude-shim.mjs`):

- принимает точный argv + stdin-prompt контракт claude CLI и переводит его в
  официальный `opencode run`;
- модели `glm-*` → `zai-coding-plan/*` (реестр opencode); `glm-5.3` в реестре
  1.18.18 отсутствует — shim добавляет её в built-in провайдер через
  конфиг, ключ берётся из `~/.local/share/opencode/auth.json`; без ключа —
  громкий fallback на `glm-5.2` (тот же план, та же квота);
- `--mcp-config` → `OPENCODE_CONFIG` (MCP-таймаут поднят до 60 c);
- `--output-format stream-json` → `opencode run --format json` с живым
  переводом событий в claude stream-json (детектор циклов, tail-просмотр,
  учёт токенов работают без изменений);
- transient-смерти провайдера (429/5xx/сокеты) ретраятся внутри shim
  (лестница с heartbeat), завод про них не узнаёт; `saga_worker_done`
  помечен как NEVER-retry;
- `--effort` игнорируется (reasoning выбирается моделью);
- воркерам внушается переименование инструментов: saga MCP-инструменты здесь
  называются `saga_worker_done`, `saga_product_submit`, ... — без префикса
  `mcp__saga__`.

**Preflight opencode** (проверено живым вызовом 2026-08-20, opencode 1.18.18):

```bash
# 1) версия (на Windows exe лежит в npm-префиксе, spawn без shell его не видит):
opencode --version    # 1.18.18

# 2) auth: в ~/.local/share/opencode/auth.json есть zai-coding-plan.key

# 3) живой дымовой вызов ровно тем путём, каким завод спавнит воркеров:
echo "Reply with exactly: OK" | \
  node tools/agent-proxy/claude-shim.mjs -p --bare --model glm-4.7
# ожидание: ответ "OK", stderr "... retry summary: 1 attempts, classes seen: clean"
```

## 2. Обязательный выбор режима перед запуском

Если пользователь просит «запустить завод», агент **не должен угадывать режим и
сразу выполнять запуск**. Сначала он показывает следующий нумерованный список и
просит выбрать один вариант:

```text
В каком режиме запустить завод?

1. Resume существующего заказа
   Продолжить тот же production LifecycleRun с последней durable-точки.
   Нужен project_id. Новые Project/Epic/LifecycleRun не создаются.

2. Новый production-заказ
   Создать новый Project и полный live-конвейер из продуктовой идеи.
   Нужна HTTPS-ссылка idea_url. Содержимое ссылки будет заморожено с SHA-256.

3. Тест без LLM — checkpoint replay
   Восстановить diagnostic clone и подставить ранее созданные результаты узлов.
   LLM не вызывается; проверяются runtime, routing, kernel/gate, settlement и
   переходы. Результат никогда не является production-eligible.

4. Тест с реальной LLM — warm start
   Положить ранее созданные документы на рабочий стол как draft и запустить
   настоящего author/reviewer. Проверяются инструкции, инструменты, feedback,
   логи и переходы, но модель не пишет весь материал с нуля. Тестовый check plan
   может не запускать дорогие внешние/NFR-проверки; они отмечаются not_run, а не
   passed. Результат не является production-eligible.
```

После списка агент запрашивает только данные выбранного режима:

| Режим | Что запросить |
|---|---|
| 1. Resume | `project_id` |
| 2. Новый production | `idea_url` |
| 3. Без LLM | checkpoint manifest/ref, diagnostic clone/target и нужную точку replay |
| 4. LLM warm start | `project_id` или diagnostic clone, checkpoint/fixture и проверяемый узел/цикл review |

Если пользователь уже явно назвал один из четырёх режимов и передал все
обязательные данные, повторный вопрос не нужен. Во всех остальных случаях агент
обязан дождаться выбора до любых изменений БД, файлов или запуска процессов.

Режимы 1 и 2 входят через единственный публичный gateway
`POST /api/factory/start`. Режимы 3 и 4 являются диагностическими операциями и
сначала готовят checkpoint clone/adoption или warm-start fixture; они не должны
маскироваться под production-start.

Для нового production-заказа не нужен готовый PRD, список требований или
архитектура. Нужна только HTTPS-ссылка на продуктовую идею. Идея является сырьём
Discovery; оператор не создаёт вручную стартовую task, brief, PRD или SRS.
(CLI-путь §6 для изолированных прогонов принимает идею текстом — это
экспериментальный/скриптовый вход, не production-заказ.)

## 3. Preflight завода (сборка и зависимости)

```bash
npm install && npm run build
cp -r skills/* ~/.zcode/skills/     # синхронизация операторских скиллов
```

`node_modules` НЕ обновляется `git pull`: новая зависимость убивает каждый boot
MCP-сервера с `ERR_MODULE_NOT_FOUND: Cannot find package
'@modelcontextprotocol/sdk'` — воркер молча теряет ВСЕ saga-инструменты, видит
только Bash/Read/Edit и сжигает бюджет, реверс-инжиниря `product_submit`.
Симптом-цепочка для диагностики: в JSONL воркера ноль `mcp__saga__*` tool_use +
thinking вида «у меня только Bash, Read, Edit». Починить зависимости, затем
requeue workplace — не давать воркеру исчерпать попытки против мёртвого
MCP-ребёнка.

Smoke-тест MCP-сервера (должен печатать баннер и жить, без ERR_MODULE_NOT_FOUND):

```bash
DB_PATH=<db> TRACKER_AUTOSTART=0 DOCS_GRAPH_AUTOSTART=0 node dist/index.js
```

**LLM-free TDD-петля** — первичная петля разработки завода. Реальная
инфраструктура (orchestrate-cli, dispatcher, gates, CandidateSets, lifecycle
routing) со скриптовыми воркерами вместо LLM; детерминированно, ~25 с на полный
жизненный цикл:

```bash
npm run test:factory-contract   # 75 тестов (unit + E2E)
npm run test:factory-temporal   # temporal conformance (ADR-048, L5):
                                # fault-schedules на каждом durable-барьере
```

Если продуктовое изменение ломает Factory Contract тесты — чинить до того, как
трогать LLM. Дизайн-документы механизмов — `tests/factory-contract/design/`.

## 4. Рабочий путь: запуск с фронта (панель)

### Запустить пульт

```bash
cd /d/Development/saga-mcp

DB_PATH='<путь к БД прогона>' \
SAGA_PRODUCT_LIFECYCLE_COMPOSITION='D:/Development/saga-mcp/tracker-view/product-delivery-composition.mjs' \
SAGA_FACTORY_CHECKPOINT_STORE='<каталог чекпоинтов>' \
SAGA_FACTORY_CHECKPOINT_LOGS=1 \
SAGA_REAL_CLAUDE_PATH='node D:/Development/saga-mcp/tools/agent-proxy/claude-shim.mjs' \
SAGA_MODEL_SWITCH_SKIP_CLAUDE_SETTINGS=1 \
node tracker-view/tracker-view.mjs
```

`SAGA_FACTORY_CHECKPOINT_STORE` включает online-чекпойнты после каждого
lifecycle cycle (backup БД + content-addressing артефактов + manifest digest).
Это defense-in-depth для disaster recovery — НЕ единственный механизм resume
(resume работает из lifecycle-state в БД), но обязательный для production
reliability. Никогда не запускайте завод без этого флага.

`SAGA_REAL_CLAUDE_PATH` в env панели обязателен: панель спавнит движок, движок
спавнит воркеров — без переменной в этом дереве воркеры пойдут в отставленный
claude CLI.

Открыть:

```text
http://localhost:4321/admin
```

В форме **«Идея на салфетке → запустить завод»** заполнить поля и нажать:

```text
Создать и запустить завод
```

Форма возвращает: `project_id`, `epic_id`, `lifecycle_run_id`, фактическую
модель, фактический параллелизм.

### Модельный каталог и лимиты

Единственный каталог облачных маршрутов — `FACTORY_CLOUD_MODELS`
(`src/runtime/factory-model-profiles.ts`, тот же список отдаёт
`GET /api/models`):

| Модель | effort по умолчанию | limit (потолок воркеров) | Примечание |
|---|---|---|---|
| `glm-4.6` | high | 2 | legacy budget, дешёвые dev-петли |
| `glm-4.7` | high | 2 | рекомендуемый default (sonnet-уровень) |
| `glm-5` | high | 3 | предыдущее поколение flagship |
| `glm-5-turbo` | high | 5 | flagship |
| `glm-5.1` | high | 3 | межгенерационный flagship |
| `glm-5.2` | high | 10 | operator-approved потолок 10 |
| `glm-5.3` | max | 6 | максимум рассуждений, conscious token cost |

- `limit` — безопасный потолок параллельных воркеров для аккаунта провайдера.
  Эффективный параллелизм = `min(concurrency оператора, limit модели)`
  (`effectiveFactoryConcurrency`); некорректная политика падает fail-closed.
- Смена модели на доске: `POST /api/model/set` с
  `{"model":"<id>","epic_id":<N>}`. Маршрут читается из
  `lifecycle_execution_controls` при каждом назначении воркера и замораживается
  в его execution_context — **уже работающие воркеры доигрывают на старой
  модели**, новая действует с момента claim.
- Параллелизм меняется отдельно: `POST /api/factory/concurrency` с
  `{"epic_id":<N>,"concurrency":<M>}` (1..10).

### Наблюдатель core-view

Рядом с пультом — read-only наблюдатель ядра (только GET-проекции над той же
БД: snapshot/events/log-tail, никаких write-эндпоинтов; интервенции остаются в
`/admin`):

```bash
node core-view/server.mjs   # http://localhost:4323 (bind 127.0.0.1)
```

Порт по умолчанию **4323**, переопределяется `CORE_VIEW_PORT`. PID-файл
`core-view/.core-view.pid` не даёт поднять второй инстанс. Подробности —
`docs/design/FACTORY-CORE-VIEW.md`.

### Что делает кнопка

Кнопка выполняет один согласованный bootstrap:

1. Создаёт Project.
2. Регистрирует control repository и локальный checkout.
3. Инициализирует Git HEAD, если репозиторий пустой.
4. Создаёт Epic.
5. Фиксирует model route и concurrency.
6. Собирает immutable Product Delivery input из идеи и реального Git HEAD.
7. Создаёт durable LifecycleRun.
8. Запускает background orchestrator.

Успешный HTTP-ответ означает не просто spawn процесса, а подтверждение, что
LifecycleRun уже записан в БД.

### API-эквивалент

```bash
curl -X POST http://localhost:4321/api/factory/start \
  -H 'Content-Type: application/json' \
  -d '{"idea_url":"https://docs.example.com/sales-assistant-idea"}'
```

### Гонка первого claim

Оба стартовых пути (`factory.mjs start`, `POST /api/factory/start`) записывают
в `lifecycle_execution_controls` профиль по умолчанию (каталог z.ai —
единственный захардкоженный) и сразу спавнят движок. Первый claim может
заморозиться на этом профиле раньше, чем оператор переключит селектор на
нужную модель. Проверенное восстановление:

1. Убить воркера нецелевого профиля и процесс orchestrate-cli.
2. `node scripts/factory.mjs resume <db>` — **без флагов**: он адоптирует
   активный launch, supervision пометит потерянного воркера `lost`
   (`REAPED ... action=lost`), lifecycle возобновится, и тот же task
   перезаклеймится уже на целевой модели. (CLI-resume спавнит движок с
   `<db>/package-store` — см. оговорку о двойном package-store ниже; если
   остальные движки этой БД пущены панелью, resume лучше делать кнопкой
   Resume / `POST /api/factory/start`.)
3. `--recover-orphaned-launch` НЕ подходит сразу после kill: он требует уже
   детектированного `lost` + `repair_wait`; обычный resume сам доводит
   состояние до этого.

Для resume существующего заказа гонки нет: строка controls уже целевая.

### Двойной package-store root — почему движки пускать через панель

`scripts/factory.mjs` задаёт `SAGA_PACKAGE_STORE_DIR=<каталог-БД>/package-store`,
а спавн через панель (`/admin`, `POST /api/factory/start`, resume) не задаёт
его вовсе — движок использует дефолт `<repoRoot>/.saga/package-store`. Если на
одной БД запустить движок из CLI и из панели, они разъедутся по двум разным
package-store: установки задублируются, а resume одного и того же launch'а
увидит «чужие» package bytes. Поэтому рабочий режим — **все движки пускать
через панель** (один и тот же корень по умолчанию); `factory.mjs` оставлен как
аварийный/скриптовый путь и требует явного `SAGA_PACKAGE_STORE_DIR`,
совпадающего с остальными движками этой БД. Дополнительное отличие:
`factory.mjs` спавнит движок с наследуемым stdio (панель — detached с логом в
файл, см. §13), поэтому CLI-движок умирает вместе с терминалом.

## 5. CLI-путь: изолированные прогоны (factory.mjs)

`scripts/factory.mjs` — единственный публичный CLI. Удобен для изолированных
sandbox-прогонов, скриптов и аварий:

```bash
node scripts/factory.mjs start  <db-path> <idea-text> [--model <name>] [--sandbox <dir>]
node scripts/factory.mjs resume <db-path> [--requeue-paused|--recover-failed-gate]
node scripts/factory.mjs continue <db-path> --from-lifecycle <id> [options]
```

Никаких ручных launch-строк, SQL, HTTP. `factory.mjs` владеет state machine
запуска: `requested → claimed → running → completed|failed`, сам провижинит
Git-репо, проект, эпик, Factory Order и durable launch request.

Пример изолированного прогона:

```bash
export SAGA_REAL_CLAUDE_PATH="node D:/Development/saga-mcp/tools/agent-proxy/claude-shim.mjs"

node scripts/factory.mjs start .factory-sandboxes/my-run-db/factory.sqlite \
  'Build an accessible single-page counter with keyboard support and local persistence.' \
  --model glm-4.7 \
  --sandbox .factory-sandboxes/my-run
```

**Держать БД вне `--sandbox`-корня.** `factory.mjs start --sandbox` стирает
sandbox-каталог (`rmSync`) перед провижинированием; SQLite-файл (или любой
открытый хэндл — например, работающий tracker-view) внутри корня даёт EBUSY на
Windows. Схема:

```text
.factory-sandboxes/<run>-db/factory.sqlite   ← БД + чекпоинты (никогда не стирается)
.factory-sandboxes/<run>/                    ← sandbox root (стирается при каждом start)
```

Tracker-view, привязанный к БД, может жить сквозь провижинирование (WAL
допускает конкурентный доступ). Опциональные runtime-контролы:
`SAGA_FACTORY_CONCURRENCY` (параллельные development-воркеры; ставить перед
start И resume), `SAGA_FACTORY_CHECKPOINT_LOGS=1`. Для нового прогона на
существующем Project — опустить `--sandbox` и указать его БД.

## 6. Checkpoint'ы и восстановление

### Online-чекпойнты (во время прогона)

Включаются `SAGA_FACTORY_CHECKPOINT_STORE` (см. §4): backup БД +
content-addressing артефактов + manifest digest после каждого lifecycle cycle.
Обязательны для production reliability, но НЕ являются единственным механизмом
resume — resume работает из lifecycle-state в БД.

### Golden snapshot + restore (перезапустить только упавшую стадию)

Когда проект уже частично прогнан (например, Discovery + Formalization готовы,
Development упал), можно восстановиться из golden-снапшота и перезапустить
только упавшую стадию — 100% экономия токенов завершённых стадий.

```bash
# One-time: чекпоинт БД (влить WAL) и скопировать БД + product-репо в golden-каталог
node -e "
  const db = new (require('better-sqlite3'))('.factory-sandboxes/my-run-db/factory.sqlite');
  db.pragma('wal_checkpoint(TRUNCATE)'); db.close();
"
mkdir -p tests/golden-runs/my-run-$(date +%Y%m%d)
cp .factory-sandboxes/my-run-db/factory.sqlite tests/golden-runs/my-run-$(date +%Y%m%d)/golden.sqlite
cp -r .factory-sandboxes/my-run/product tests/golden-runs/my-run-$(date +%Y%m%d)/product-repo

# Restore: копия golden-БД, починка застрявших, сброс упавших ProcessRuns
node scripts/restore-from-checkpoint.mjs \
  tests/golden-runs/my-run-20260812/golden.sqlite \
  .factory-sandboxes/dev-run-002/factory.sqlite \
  --fix-stuck

# Product-репо (код + git-история + docs)
cp -r tests/golden-runs/my-run-20260812/product-repo .factory-sandboxes/dev-run-002/product

# Resume — завод продолжается на paused-стадии, завершённые пропускаются
node scripts/factory.mjs resume .factory-sandboxes/dev-run-002/factory.sqlite
```

| Стадия | Статус после restore | Токены LLM |
|-------|---------------------|------------|
| Discovery | `completed` (из снапшота) | **0** — артефакты в БД |
| Formalization | `completed` (из снапшота) | **0** — артефакты в БД |
| Development | `paused` → resumed | только оставшиеся задачи |

Опции `restore-from-checkpoint.mjs`: `--fix-stuck` — починить только
застрявшие workplaces (всё completed сохранить); `--reset-stage <stage>` —
сбросить стадию целиком (перепрогнать ВСЕ её задачи с нуля).

Когда использовать: завод упал посреди стадии (restore + fix-stuck + resume);
починен код, надо перепроверить (restore + reset-stage + resume);
регрессионные фикстуры (golden snapshot + product code); тот же проект,
другая модель (restore formalization, development на новой модели).

## 7. Кто чем владеет

### LifecycleRun

Владеет маршрутом между цехами:

```text
Discovery → Formalization → Development → Delivery
```

Только lifecycle routing решает, какой цех запускается следующим. Модуль не имеет права сам запускать соседний модуль.

### ProcessRun

Один запуск одного цеха. Цех обязан закончиться локальным outcome и, если outcome допускает передачу дальше, immutable product/certificate.

### Workplace

Стабильное рабочее место внутри ProcessRun. Оно владеет:

- карточкой на доске;
- desk/workspace;
- текущей ролью author/reviewer;
- loop state;
- CandidateSet и gate lineage.

Worker не владеет карточкой. Worker — одноразовый исполнитель, который приходит на Workplace по fenced reservation. При repair приходит новый worker на то же рабочее место.

### Task

`tasks` — человекочитаемая Kanban-проекция Workplace. Это не второй независимый автомат. Источник истины для внутреннего цикла — `v4_workplaces`; task status должен отражать его состояние.

## 8. Состояния карточки и Workplace

Легальные Kanban-статусы:

```text
todo  in_progress  review  review_in_progress  done  blocked  failed  cancelled
```

Внутренний loop state Workplace:

```text
idle  queued  leased  running  verifying  repair_wait  paused  terminal
```

Нормальный author/reviewer-проход:

```text
Workplace queued, next_role=author
  task: todo

worker claim
  Workplace: leased/running
  task: in_progress

worker seals author CandidateSet
  Workplace: verifying или queued, next_role=reviewer
  task: review

reviewer claim
  Workplace: leased/running
  task: review_in_progress

final gate accepted
  Workplace: terminal, terminal_reason=accepted
  task: done
```

Для code-changing task принятие качества и интеграция различаются:

```text
task.status = done
integration_state = pending
  → deterministic integration
integration_state = merged
  → зависимые задачи могут стать claimable
```

`done` без `merged` не открывает зависимую code task.

### Repair

```text
final/author gate: repair_required
  → создаётся RecoveryIssue
  → тот же Workplace сохраняется
  → та же карточка возвращается в todo
  → next_role указывает author или reviewer
  → приходит новый fenced worker
```

Нельзя создавать новую карточку только потому, что сменился worker. Иначе теряются desk, lineage и rejected CandidateSet.

### Исчерпание бюджета ремонта (ADR-075 — без человека в цикле качества)

В клетках качества `onExhausted='requeue'`: при исчерпании `maxAttempts`
бюджет **прокатывается в новую recovery-эпоху** — в immutable-таблицу
`factory_workplace_recovery_epochs` дописывается строка с базовой линией
счётчиков попыток, линия выдерживает экспоненциальный беккофф (1–15 мин) и
продолжает работу автономно. Линия никогда не паркуется «для человека».

Единственный не-человеческий предохранитель: суммарный потолок попыток
(`recovery.totalAttempts`, по умолчанию 30) — при его достижении линия честно
завершается `terminal failed` с диагнозом последнего отказа в логе
(`[recovery-budget] TOTAL-CAP …`). Продолжение — новый Factory Start /
continuation поверх принятого префикса.

### Human required (только Delivery и инфраструктура)

```text
gate: human_required
  → Workplace paused или blocked
  → карточка не claimable
  → создаётся durable human interaction/request
```

Человек требуется только там, где нужна физическая инфраструктура или внешняя авторизация: approval релиза в Delivery, заблокированные post-acceptance эффекты (например, git-integration), поломка спавна воркеров. Клетки качества человека не требуют (см. ADR-075). После решения человека завод возобновляет тот же Workplace, а не создаёт новый продуктовый поток.

### Failed и cancelled

`failed` и `cancelled` терминальны для конкретного рабочего места. Lifecycle может завершиться соответствующим terminal outcome либо остановиться на уровне текущего цеха. Нельзя превращать failure в `done` ручным SQL.

## 9. Переход между рабочими местами и цехами

Карточка не переезжает из Discovery в Formalization. Между цехами передаётся не task, а immutable handoff:

```text
StageRun A
  → local outcome
  → certificate/product ref + hash
  → atomic lifecycle transition
  → новый StageRun B
  → новые Workplace цеха B
```

Поэтому одновременно истинны два правила:

- внутри repair/review цикла сохраняется то же Workplace;
- при переходе в следующий цех создаются новые Workplace, связанные точными ProductRef/hash предыдущего цеха.

## 10. Что выпускает каждый цех

### Discovery

Вход: сырая идея, контекст, evidence и constraints. Продукт: discovery
certificate с outcome и точной lineage. Production-сценарий записывает силу
идеи и передаёт сертификат в Formalization. Formalization остаётся реальным
build gate. Строгий regulated-сценарий может останавливать маршрут раньше.

### Formalization

Внутри производит и согласует:

```text
PRD + FR/NFR/RULE
  → UC
  → AC
  → reconciliation
  → frozen acceptance baseline
  → SRS/decomposition
```

Продукт: immutable Solution Contract certificate. Только `formalized` передаётся в Development. Clarification, inconsistency и infeasibility завершают маршрут явным terminal status.

### Development

Внутри:

1. Planner предлагает task graph.
2. Kernel проверяет DAG, coverage, repositories и lineage.
3. Kernel материализует implementation/review/integration/verification workplaces.
4. Workers выполняют карточки через общую очередь.
5. Code-changing результаты проходят review и deterministic integration.
6. Verification evidence привязывается к неизменному frozen candidate.
7. Settlement выпускает verified integration bundle.

Критический инвариант:

```text
Development НЕ может settle как verified,
пока все спроецированные задачи не достигли terminal состояния,
все обязательные code changes не integrated,
а evidence не привязана к точному candidate hash.
```

Пока это не выполнено, ProcessRun остаётся paused/awaiting implementation. Conveyor продолжает разбирать доступные карточки и затем повторно запускает тот же settlement node.

### Delivery

Внутри:

```text
preflight
  → human approval, если требует policy
  → publish/deploy desired-state actions
  → authoritative observation
  → settlement
```

Продукт: release record и delivery certificate. Успешный `git push` или ответ deploy-команды сам по себе не считается release. Нужна authoritative observed state каждого обязательного destination.

### Терминальные состояния (ADR-045)

Под текущим lifecycle `product-build@1.1.0` завод терминируется после
Development:

| Стадия | Успешный исход | Терминальный статус |
|-------|----------------|---------------------|
| Discovery | `go` | (переход в Formalization) |
| Formalization | `formalized` | (переход в Development) |
| Development | `verified` | **`runnable-local`** |

`lifecycle_run.status=completed`, `terminal_status=runnable-local`. Delivery —
отдельный DevOps-запрос, не часть `product-build@1.1.0`: после успеха
Development использовать `continue` с `--local-release` или
release-специфичной композицией. Полная модель (§4 цеха Delivery) доводит
happy path до `terminal_status=released`.

## 11. Когда завод должен продолжать работу

Завод работает автоматически, пока выполняется хотя бы одно условие:

- текущий Flow имеет следующий node;
- существует claimable Workplace;
- Development ждёт незавершённые projected tasks;
- активен reviewer/repair loop;
- можно выполнить deterministic integration или verification;
- local outcome текущего цеха маршрутизируется в следующий цех.

Завод не должен завершать background loop только потому, что один worker вышел. Один worker обслуживает одну reservation; orchestrator обязан продолжить с очередью или с текущим ProcessRun.

Законный останов происходит только при:

- lifecycle terminal outcome;
- durable pause (Delivery approval / инфраструктурные границы — ADR-075 убрал человеческие паузы из цикла качества: исчерпание бюджета ремонта продолжается эпохами ретраев до честного terminal failed по потолку);
- human approval required (Delivery);
- exhausted recovery policy (суммарный потолок попыток — terminal failed);
- explicit operator stop/cancel;
- infrastructure failure, зафиксированном как failure, а не замаскированном под success.

## 12. Start, Stop и Resume

На странице проекта доступны: выбор модели, concurrency, кнопка Start, Stop,
Resume для существующего заказа по номеру Project. Для нового продукта
предпочителен `/admin` → «Идея на салфетке → запустить завод» (корректный
lifecycle input). Для paused LifecycleRun:

1. Не пересоздавать Project/Epic.
2. Не создавать новую стартовую task.
3. Нажать Resume или вызвать единую стартовую точку:

```bash
curl -X POST http://localhost:4321/api/factory/start \
  -H 'Content-Type: application/json' \
  -d '{"project_id": 1}'
```

Resume обязан использовать уже сохранённые lifecycle input, StageRun,
ProcessRun, Workplace и products.

### Операторский soft-stop (тормоз движка)

Штатная остановка — не `kill -9` и не закрытие терминала:

```bash
# из UI доски — кнопка Stop, или:
curl -X POST http://localhost:4321/api/factory/stop \
  -H 'Content-Type: application/json' -d '{"epic_id": 1}'

# CLI-эквивалент (тот же операторский протокол):
node scripts/factory.mjs stop <db-path> --project N [--dry-run] [--reason <текст>]
```

Протокол идемпотентный и многофазный (фазы durable в
`factory_worker_stops.phase`): план остановки → тормоз движка
(`brakeEnginesForProject` — убивает только pid, чья command line содержит
`orchestrate-cli.js`; чужой/переиспользованный pid никогда не трогается) →
fence и откат `leased/running` воркеров в точку до найма (карточка
возвращается в очередь, ни один WorkerExecution не теряется) → kill/reap при
необходимости → checkpoint. После soft-stop завод возобновляется обычным
Resume.

### Если остановилась панель

Движок спавнится detached (`child.unref()`) и живёт независимо от панели:
закрытие/рестарт панели НЕ останавливает завод, воркеры доигрывают. Обратная
сторона — вместе с панелью умирает engine supervisor (watchdog): пока панели
нет, замёрзший движок никто не лечит. Перезапустили панель — supervisor
подхватил launch'ы по durable-полям (`factory_launch_requests.
engine_log_path/engine_pid`) и продолжает наблюдение, включая бюджет
рестартов (`factory_engine_watchdog_events`, не память панели).

### Если остановился/умер движок

Воркеры — отдельные процессы; они доигрывают свой lease и сдают материал через
MCP-сервер, который пишет БД независимо от движка. Потерянные воркеры
(процесс убит, lease истёк) помечаются supervision как `lost` при следующем
resume/adoption и перезаклеймиваются. Recovery здесь — Resume, а не
пересоздание заказа.

### Watchdog: что делает supervisor сам

Пока панель работает, engine supervisor сам наблюдает и лечит движки: каждые
30 с проверяет каждый running launch; живой pid + heartbeat старше 120 с =
фриз главного потока → durable-события `freeze_detected`/`restart_attempted`
пишутся ДО остановки → soft-stop тормозом → рестарт штатным resume-кодом
панели; backoff 1→5→15 минут, бюджет 5 попыток за 2 часа. Мёртвый pid
помечается одной durable-записью `engine_dead`, дубли спавнов блокируются
(`sweepBeforeSpawn`). Отключить: `SAGA_ENGINE_SUPERVISOR=0`; тюнинг:
`SAGA_ENGINE_SUPERVISOR_INTERVAL_MS`, `SAGA_ENGINE_SUPERVISOR_STALE_MS`.

После исчерпания бюджета (5/2ч) supervisor не рестартует движок молча:
`engine_state='failed_watchdog'` + `last_error` — видно на доске и в
`GET /api/factory/status`. Дальше решение оператора: посмотреть лог движка и
phase-маркер (§13), починить окружение, нажать Resume.

### Флаги resume (узкие, evidence-based)

Для прерванного прогона — канонический `node scripts/factory.mjs resume $db`
(продолжает тот же LifecycleRun). `SAGA_FACTORY_CONCURRENCY` ставить перед
start И resume.

- `--requeue-paused` — только если triage доказал, что Workplace
  `blocked/paused` из-за исчерпания бюджета попыток submission-preflight
  rejections (явная one-attempt recovery директива).
- `--recover-failed-gate` — только если прогон упал после CandidateSet seal
  исключительно из-за различия версий pinned check plan и runtime provider.

Флаги взаимоисключающие; оба отказываются трогать уже завершённую/gated
работу. `--recover-orphaned-launch` — не стартовый инструмент: требует уже
детектированного `lost` + `repair_wait`; обычный resume сам доводит до этого
состояния.

Если workplace попал в human-pause (`blocked` + `loop_state=paused` после
повторных lost; движок логирует `N workplace(s) require explicit resume` и
простой resume останавливается): `--requeue-paused` подходит только узлам с
обязательным submission-валидатором. Платформенный примитив под обоими —
`ConveyorRuntime.resumeFromHuman({workplaceRef, taskId, role})`
(`src/application/conveyor-runtime.ts`): requeue того же Workplace с
revision+1 в одной транзакции. Сначала чинить причину — resume в сломанный
endpoint просто сжигает ещё одну попытку воркера.

### Continue после terminal failure

```bash
# Сначала проверка (без live-авторизации, на SQLite-бэкапе):
node scripts/factory.mjs continue $db --from-lifecycle 1 \
  --adopt-task 15 --scope index.html --scope js/app.js --scope css/styles.css \
  --check

# Verification-only continuation (после candidate freeze):
node scripts/factory.mjs continue $db \
  --from-lifecycle <latest-terminal-leaf> --verification-only --check
```

`--check` использует SQLite-бэкап и не расходует live-авторизацию. Реальная
команда идентична без `--check`.

## 13. Наблюдение и мониторинг

### Фронты

```text
http://localhost:4321/?project=<PROJECT_ID>   # пульт/борд (tasks, workers, controls)
http://localhost:4323                          # core-view (Пульс/Цепочка/Ячейка/Хроника)
http://localhost:4322                          # docs-graph — граф артефактов/доков эпика
http://localhost:4324                          # workshop-designer — визуальный редактор воркшопов
```

Два новых фронта (2026-08-22):

- **docs-graph** — `node tracker-view/docs-graph/server.mjs`; порт по умолчанию
  **4322**, переопределяется `DOCS_GRAPH_PORT`. Граф документации/артефактов
  эпика (PRD/FR/UC/AC/SRS и трассировки между ними) поверх той же БД.
- **workshop-designer** — `node workshop-designer/server.mjs`; порт по умолчанию
  **4324**, переопределяется `WORKSHOP_DESIGNER_PORT`. Визуальный редактор
  процесс-модулей воркшопов (граф ячеек, inspector контрактов, design-time
  conformance-проверки поверх реальной топологии Formalization).

Порядок подъёма при запуске завода: tracker (4321) → core-view (4323) →
docs-graph (4322) → workshop-designer (4324). Все — read-only наблюдатели над
одной БД прогона (WAL), движок не трогают.

Никогда не предполагать, что `localhost:4321` указывает на текущий прогон —
проверять идентичность БД на странице. Фронты переживают рестарты движка;
рестартить их только при переезде БД прогона. Порт 4325+ — если кто-то
занял порт, трекер тихо выходит («already in use»), core-view отказывается от
второго инстанса по pid-файлу: сначала проверить порт, потом винить фронт.

### Attach фронтов к уже идущему прогону (движок жив, БД найти и подключить)

Ситуация: завод уже запущен (известны pid движка и/или `launch-…`), фронты
надо поднять наблюдателями. Завод при этом не трогается — фронты работают
через read-only-подключения к той же БД (WAL это разрешает).

**Шаг 1 — найти активную БД.** launch-ref виден в command line движка;
БД подтверждается строкой в `factory_launch_requests` (state=running,
engine_pid совпадает):

```bash
# launch-ref живого движка:
powershell -NoProfile -Command "Get-CimInstance Win32_Process -Filter 'ProcessId=<PID>' |
  Select-Object -ExpandProperty CommandLine"
# → node …/orchestrate-cli.js --launch-ref=launch-96e8eb04-…

# свежие кандидаты (mmin -240 = изменённые за 4 часа):
find /d/Development/saga-mcp -maxdepth 4 -name factory.sqlite -mmin -240

# подтверждение (readonly, БД не трогаем на запись):
node -e "
const db = new (require('better-sqlite3'))('<db>', {readonly:true});
console.log(db.prepare('SELECT launch_ref, engine_pid, state, engine_log_path FROM factory_launch_requests ORDER BY rowid DESC LIMIT 3').all());
db.close();"
```

**Шаг 2 — проверить существующие фронты.** Занятые порты и БД каждого:

```bash
netstat -ano | grep LISTENING | grep -E ":432[0-9]"
curl -s http://localhost:4323/api/core/heartbeat        # → {"db":{"path":…}} — идентичность БД
curl -s 'http://localhost:4321/api/factory/status?epic_id=1'  # → running/pid/started_at
```

Если фронты указывают на чужую/мёртвую БД (heartbeat отстаёт от старта
прогона, `running:false`) — это «переезд БД прогона»: погасить старые
инстансы и поднять новые. В git-bash `taskkill /F` искажается — убивать
через PowerShell:

```bash
powershell -NoProfile -Command "Stop-Process -Id <pid1>,<pid2> -Force"
```

**Шаг 3 — поднять фронты на БД прогона** (порт трекера — env `PORT`,
дефолт 4321; порт core-view — `CORE_VIEW_PORT`, дефолт 4323; БД core-view —
`CORE_VIEW_DB`). `SAGA_PACKAGE_STORE_DIR` обязан совпадать с корнем движка
(§4, двойной package-store): если движок пущен CLI (`<db-dir>/package-store`
существует рядом с БД) — указать его явно, иначе supervisor-рестарт разъедется
по корням.

Логи воркеров прогон пишет в `<log-root>/board-<N>-<enginePid>-<ts>/task-*-worker-*.jsonl`
(корень = каталог `*-logs/` рядом с БД; точный путь — `worker_executions.log_path`).
Оба фронта читают их ТОЛЬКО из разрешённых корней — без env ниже карточка
«Терминал/logTail» в core-view и хвост воркера в пульте пустые («недоступно»):
трекеру корень задаёт `SAGA_ORCHESTRATION_LOG`, core-view — `CORE_VIEW_LOG_ROOT`.

### Логи и маркеры живости движка

Движок пишет весь лог ТОЛЬКО в `$SAGA_ENGINE_LOG` (stdout-пайпа не существует —
класс фризов stdout-backpressure устранён). Путь лога durability-привязан к
launch'у:

```sql
SELECT engine_log_path, engine_pid, engine_spawned_at
  FROM factory_launch_requests ORDER BY rowid DESC LIMIT 1;
```

Рядом с логом — маркеры живости:

```text
$SAGA_ENGINE_LOG.heartbeat   -- mtime обновляется каждые ≤5 с
$SAGA_ENGINE_LOG.phase       -- последняя фаза главного цикла движка
```

Живой pid + неменяющийся mtime heartbeat = фриз главного потока; лечением
занят supervisor/оператор после `failed_watchdog`. Durable-журнал watchdog:

```sql
SELECT * FROM factory_engine_watchdog_events ORDER BY rowid DESC LIMIT 20;
```

Ключевые строки в логе движка:

```text
[recovery-budget] ROLLOVER ...    -- бюджет ремонта прокатился в новую эпоху (ADR-075)
[recovery-budget] TOTAL-CAP ...   -- суммарный потолок попыток: честный terminal failed
[obligation-reconciler] sweep dispatched=... -- проход метлы обязательств
[obligation-reconciler] DEFER/FAIL ...       -- типизированное ожидание/отказ
[obligation-reconciler] defer-only streak=... -- серия чистых DEFER: лифт ждёт постусловий
```

При диагностике всегда различать: lifecycle status; current stage; ProcessRun
status; Workplace loop state; task Kanban projection; worker execution
liveness; integration state.

### Каденс мониторинга: опрос раз в 60 секунд

Не спать 3–5 минут между проверками — воркер может завершиться, gate упасть,
клетка запнуться в зазоре; ловить переход в минуту события. Каждый опрос читает
две вещи: последние ~15 строк лога orchestrate-cli (cycle/stage/dispatch
события) и статус задач/артефактов из живой БД:

```bash
node -e '
  const D = require("better-sqlite3");
  const db = new D(process.argv[1], {readonly:true});
  for (const t of db.prepare("SELECT id,status,workflow_stage,title FROM tasks ORDER BY id").all())
    console.log(`  #${t.id} [${t.status.padEnd(12)}] ${t.workflow_stage.padEnd(12)} ${t.title.slice(0,48)}`);
  const ac = db.prepare("SELECT status,count(*) n FROM artifacts GROUP BY status").all();
  console.log("  artifacts:", ac.map(a=>`${a.status}=x${a.n}`).join(" "));
  db.close();
' <путь к factory.sqlite>
```

### Формат отчёта — цепочка конвейера

Глифы `✅ done · 🔄 running · ⬚ idle · ✖ failed`, у активной стадии — активный
узел:

```
Discovery      ✅
Formalization  🔄  product-contract ✅ | use-cases 🔄
Planning       ⬚
Development    ⬚
Verification   ⬚
Delivery       ⬚
```

Правила: стадия `✅` только когда её terminal ProcessModule outcome запечатан
(все задачи `done`, артефакты `accepted`); одна `done` + одна `in_progress` =
всё ещё `🔄`; рядом со спиннером имя активного узла; на любой
`failed`/`repair_required`/краш — `✖` с точным кодом ошибки
(`FORMALIZATION_ACCEPTANCE_PRODUCT_REF_INVALID`, …), без пересказа. Коротко:
цепочка — заголовок, одна-две строки деталей, без прозы.

### Что такое здоровый прогресс

`LifecycleRun.status=paused` между циклами воркеров может быть durable-ожиданием,
а не остановкой. Проверять всё вместе:

- активный WorkerExecution имеет свежий heartbeat и progress timestamp;
- его lease валиден и `stuck_state=active`;
- текущий Workplace `in_progress/running` или `review_in_progress/running`;
- завершение author создаёт CandidateSet, затем оценивается GateDecision;
- работа reviewer — отдельный fenced execution;
- только финальный acceptance создаёт ReplayCapsule.

### Межстадийные инварианты

После Discovery убедиться, что вход следующего ProcessRun содержит точный
certificate ref и hash. После Formalization — точный Solution Contract и
замороженный acceptance baseline. Перед Development — repository base commit и
package installation pin. Продукты content-addressed: потребители используют
точные ProductRefs, не `latest` task output.

Replay-капсулы создаются только из финального принятого CellFinalAcceptance;
выход воркера или голый `accepted`-чек недостаточен. У review-клеток —
отдельные author/reviewer капсулы. Replay создаёт новые текущие CandidateSets
и gates; он никогда не восстанавливает старое состояние Workplace или
receipts внешних эффектов.

## 14. Если завод выглядит остановленным

Трактовать как инцидент, когда истинно всё сразу:

- LifecycleRun `paused` на том же node;
- Workplace `blocked/paused` или `repair_wait`;
- ни один WorkerExecution не имеет живого lease;
- у спроецированной задачи нет `current_execution_id`;
- новых CandidateSet/GateDecision нет несколько host-циклов подряд.

Сохранить БД, worker JSONL-логи, execution workspaces и последний checkpoint.
Не resumeить сразу: сначала идентифицировать последний отклонённый MCP-вызов и
проверить, созданы ли durable RecoveryIssue/RecoveryCase и feedback-файл. Если
единственная durable-ошибка — «exited without terminal worker_done», искать в
логе воркера более ранний отклонённый `worker_done`; иначе доменная валидация
могла схлопнуться в generic lost-worker state.

## 15. Безопасность оператора

Перед ручным вмешательством — snapshot БД.

Нельзя:

- удалять `saga.db`, если нужен прогресс;
- вручную менять accepted artifacts или hashes;
- переводить task в `done` SQL-командой;
- удалять ProcessRun/StageRun для «разблокировки»;
- удалять paused Project — paused lifecycle живой и resumable;
- повторно отправлять изменённый lifecycle input под тем же idempotency key;
- убивать worker и сразу назначать второго без истечения/release fence;
- молча править инструкции воркеров или сбрасывать БД во время активного прогона;
- трогать `~/.claude/settings.json` (трипвайр, §1).

Проблема решается через resume, recovery, cancel или новый lifecycle run с
новым idempotency key — не разрушением audit trail.

Для наблюдаемого прогона держать рядом с его изолированной БД evidence-файлы:
`FACTORY-RUN-REPORT.md` (исходы стадий и точные handoffs) и
`FACTORY-BUGS.md` (runtime/UI/документационные дефекты). Каждый запуск
фиксируется в `ЖУРНАЛ-ЗАПУСКОВ.md`.
