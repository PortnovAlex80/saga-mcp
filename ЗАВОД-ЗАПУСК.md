# Завод saga4 — чистый запуск с нуля

Пошаговая инструкция: от нулевой БД до работающего Product Delivery Lifecycle.
Проверено на saga4-рефакторинге (commit e209155, branch saga4).

---

## ⛔ ГЛАВНОЕ ПРАВИЛО: ВСЕГДА RESUME, НИКОГДА С НУЛЯ

Завод — это конвейер. Если pipeline остановился (paused), ответственный
(цех, артефакты, прогресс) СОХРАНЁН в БД. **Никогда не начинай с нуля если
уже есть артефакты.** Всегда resume.

### Как resume (ЕДИНСТВЕННЫЙ правильный путь)

```bash
# 1. Проверить — есть ли lifecycle run в paused?
node -e "const D=require('better-sqlite3'); const db=new D('C:/Users/user/.zcode/saga.db'); const r=db.prepare('SELECT id,status,current_stage_id,terminal_status FROM saga3_lifecycle_runs ORDER BY id DESC LIMIT 1').get(); console.log(r.status, r.current_stage_id, r.terminal_status);"

# 2. Если paused И terminal_status=NULL → подать create-from-idea СНОВА
#    (с тем же именем/идеей/путём). Это создаст НОВЫЙ lifecycle run,
#    но accepted артефакты (PRD, FR, NFR, AC) из предыдущего run'а ОСТАНУТСЯ.
#    Formalization/Development продолжит с того места где остановился.
curl -s -X POST http://localhost:4321/api/project/create-from-idea \
  -H "Content-Type: application/json" \
  -d '{"name":"<ТО_ЖЕ_ИМЯ>","idea":"<ТА_ЖЕ_ИДЕЯ>","local_path":"<ТОТ_ЖЕ_ПУТЬ>"}'

# 3. Если "Проект уже существует" — удалить проект через API:
curl -s -X POST http://localhost:4321/api/project/delete \
  -H "Content-Type: application/json" -d '{"project_id":<ID>}'
# И снова create-from-idea.
```

### ⛔ ЧЕГО ДЕЛАТЬ НЕЛЬЗЯ

1. **НЕ УДАЛЯЙ saga.db** если в нём есть accepted артефакты
2. **НЕ ДЕЛАЙ `DELETE FROM artifacts`** — immutable audit trail
3. **НЕ ДЕЛАЙ `DELETE FROM saga3_managed_artifact_productions`** — kernel gate
   упадёт: "ledger artifact does not match its canonical row"
4. **НЕ ИСПОЛЬЗУЙ `reset-saga-db.mjs`** — оно создаёт schema v1 без v4 таблиц
5. **НЕ ВЫПОЛНЯЙ `DELETE FROM` по всем таблицам** — это уничтожит прогресс
6. **НЕ УБИВАЙ процессы** между проверками прогресса — движок сам renewal'ит lease
7. **НЕ ПЕРЕСОЗДАВАЙ lifecycle-input JSON** — hash должен совпадать byte-identically

### Snapshot/Restore (защита прогресса)

**ВСЕГДА делай snapshot перед любым вмешательством в pipeline:**

```bash
# Способ 1: бинарная копия БД (полная)
cp "C:/Users/user/.zcode/saga.db" "C:/Users/user/.zcode/saga-snapshot-$(date +%Y%m%d-%H%M).db"

# Способ 2: JSON export (только project данные, портативный)
cd /d/Development/saga-mcp
node saga4-snapshot.mjs export --project=<ID> > "C:/Users/user/.zcode/saga-project<ID>-snapshot.json"

# Restore из JSON:
node saga4-snapshot.mjs import < "C:/Users/user/.zcode/saga-project<ID>-snapshot.json"
```

Snapshot сохраняет: projects, artifacts, traces, lifecycle_runs, stage_runs,
process_runs, node_runs, managed_productions, exact_acceptance_*, tasks,
worker_executions, command_receipts, work_intents, verification_evidence.

НЕ сохраняет: activity_log, board-runs JSONL, module_installations.

**Когда snapshot обязателен:**
- Перед любым `UPDATE`/`DELETE` в БД для починки stuck state
- Перед экспериментами с настройками
- Перед переключением модели (glm-4.7 → другое)
- Периодически (каждые ~30 мин активного pipeline)

Saga — governance-платформа. Её данные (artifacts, traces, node_runs,
managed_artifact_productions, recovery_cases) — **immutable audit-trail**.
Ручной `DELETE FROM ...` нарушает целостность и ломает lifecycle:

- `saga3_managed_artifact_productions` ссылается на artifact_id — если
  artifact удалён, kernel-gate падает: «one or more ledger artifacts no
  longer exist» → `domain.failed` → lifecycle терминально failed.
- `saga3_exact_candidate_acceptance_items` защищён ABORT-триггером (immutable).
- Triggers защищают другие таблицы.

### Механика pause / resume (ЕДИНСТВЕННЫЙ правильный путь)

Lifecycle имеет ровно два состояния для живого pipeline:
- **`running`** (или `paused`) — работа идёт / приостановлена
- **`terminal`** (completed/failed/released/...) — pipeline завершён

Если lifecycle `paused` (движок умер, lease протух) — **возобновить**, не удалять:

```bash
# 1. Старт того же engine — lifecycle продолжится с того же места:
DB_PATH=... SAGA_PRODUCT_LIFECYCLE_COMPOSITION=... \
nohup node dist/orchestrate-cli.js <proj> <epic> --concurrency=N --resume \
  > /c/Users/user/.zcode/engine.log 2>&1 &
```

Если lifecycle **`terminal: failed`** (не откатить) — создать **новый lifecycle run**
для того же epic (новый idempotency-key). Discovery replay'нется, но accepted
PRD/SRS/UC/AC из предыдущего run'а **останутся** и могут быть переиспользованы.

### Когда reset БД оправдан

Только при старте **нового продукта с нуля** (delete old projects before fresh
start). Никогда — для «починить застрявший pipeline». Для застрявшего — resume.

## TL;DR — быстрый старт (3 команды)

```bash
cd /d/Development/saga-mcp

# 1. Полный сброс (убить процессы, удалить БД — fresh schema v2 с v4 таблицами)
powershell -Command "Get-CimInstance Win32_Process -Filter \"name='node.exe' OR name='claude.exe'\" | Where-Object { \$_.CommandLine -like '*orchestrate*' -or \$_.CommandLine -like '*tracker-view*' -or \$_.CommandLine -like '*claude-board*' } | ForEach-Object { Stop-Process -Id \$_.ProcessId -Force -ErrorAction SilentlyContinue }"
sleep 2; rm -f "C:/Users/user/.zcode/saga.db" "C:/Users/user/.zcode/saga.db-shm" "C:/Users/user/.zcode/saga.db-wal"; rm -rf ~/.zcode/cli/board-runs/board-*

# 2. Пульт (ДВИЖОК НЕ ТРОГАТЬ — он стартует сам через create-from-idea)
DB_PATH='C:/Users/user/.zcode/saga.db' SAGA_PRODUCT_LIFECYCLE_COMPOSITION='D:/Development/saga-mcp/tracker-view/product-delivery-composition.mjs' node tracker-view/tracker-view.mjs > /tmp/tracker-view.log 2>&1 &
sleep 5 && curl -s http://localhost:4321/api/heartbeat

# 3. Заказ (это создаст project+repo+epic, materializе lifecycle input, spawn движок)
curl -s -X POST http://localhost:4321/api/project/create-from-idea -H "Content-Type: application/json" -d '{"name":"habit-tracker","idea":"<твоя идея одной фразой>","local_path":"D:/Development/habit-tracker"}'
```

⚠️ Критические правила (v4 clean-slate):
1. `SAGA_PRODUCT_LIFECYCLE_COMPOSITION` — задаётся при старте tracker-view, БЕЗ него движок падает
2. Движок стартует ТОЛЬКО через `/api/project/create-from-idea` (которое делает spawn({detached:true}))
3. **НЕ используй `/api/engine/start` для resume** — оно не передаёт lifecycle input → `PRODUCT_LIFECYCLE_INPUT_REQUIRED`. Для restart — новый `create-from-idea` (accepted артефакты сохранятся, Discovery replay'нется)
4. **НЕ используй `reset-saga-db.mjs`** — оно пересоздаёт старую schema v1 без v4 таблиц. Просто удали файл `saga.db` — getDb() создаст fresh schema v2 (7 v4 таблиц + 4 immutability triggers + workplace_ref)
5. Канбан: http://localhost:4321/?project=1

### Resume (если движок умер, но pipeline ещё не terminal)
```bash
# 1. Проверить — жив ли tracker-view
curl -s http://localhost:4321/api/heartbeat

# 2. Если alive — просто повторно подай create-from-idea (старые артефакты сохранятся):
curl -s -X POST http://localhost:4321/api/project/create-from-idea -H "Content-Type: application/json" -d '{"name":"<то же имя>","idea":"<та же идея>","local_path":"<тот же путь>"}'
# Это создаст НОВЫЙ lifecycle run (старый failed/paused), но accepted PRD/FR/NFR/AC
# из предыдущего run'а остаются — Formalization продолжит с того места где остановился.
```

## Что происходит на доске

Открыть http://localhost:4321/?project=1 :

- **Движок: ▶/⏸** — кнопка старта/остановки (но заказ УЖЕ подан в шаге 3)
- **Lifecycle** — карточка Product Delivery, показывает текущий цех
- **Задачи** — двигаются todo → in_progress → review → done
- **Вкладка «Артефакты»** — PRD/SRS/UC/AC
- **Вкладка «Покрытие»** — какие AC закрыты

### 4 цеха (последовательно)

```
1. Discovery (product-discovery@3.0.2)
   LM-ноды: produce-proposal → normalize-semantic → assess-readiness → settle
   Итог: certificate {go | clarify | reject | ...}

2. Formalization (solution-formalization@1.0.0)
   LM-ноды: PRD → SRS → UC → AC → reconciliation
   Итог: frozen Solution Contract

3. Development (solution-development@1.0.0)
   dev-задачи → ревью → мерж в integration-branch
   Итог: verified integration bundle

4. Delivery (delivery-release@1.0.0)
   preflight → approval → release
   В режиме local-dry-run: завершается approval-required (fail-closed)
```

### Что нормально видеть на канбан (НЕ дубли!)

По мере прохождения цехов завод **создаёт задачи** — это Kanban-история, не дубли.
Каждая задача = одна LM-нода или один dev-step. Пример реального прогона:

```
Цех Discovery:
  Task "Product Discovery: <idea>"          → done   (produce-proposal)
  Task "Discovery: Assess readiness..."     → done   (assess-readiness)

Цех Formalization (после discovery=go):
  Task "Solution Formalization: Create PRD..." → in_progress → done
  Task "...Create SRS..."                      → ...
  Task "...Create UC..."                       → ...
  Task "...Create AC..."                       → ...
  Task "...Reconciliation..."                  → ...

Цех Development (после formalized):
  Task "Implement <feature>"                   → dev → review → done → merged
  Task "AC-verify <AC-N>"                      → verify
  ... и т.д.
```

**«Product Delivery» (родитель) + «Initial Discovery» (стадия) = ОДИН pipeline**,
не две задачи. Стадия внутри родителя меняется по мере продвижения:
`initial-discovery` → `solution-formalization` → `solution-development`
→ `delivery-release`.

Когда видите «задачи поехали» — это значит завод перешёл к следующему цеху и
создал новые задачи для него. **Старые (done) задачи остаются** как audit-trail.

### Прогресс по цехам (SOURCE OF TRUTH = БД, не HTTP-статус)

Один запрос показывает на каком цехе завод и с каким исходом:

```bash
node -e "
const D=require('better-sqlite3');
const db=new D('C:/Users/user/.zcode/saga.db');
console.log('LIFECYCLE:', db.prepare('SELECT id,status,current_stage_id,terminal_status,error FROM saga3_lifecycle_runs').all());
console.log('PROCESS:  ', db.prepare('SELECT id,status,projected_stage,local_outcome FROM saga3_process_runs').all());
console.log('TASKS:    ', db.prepare('SELECT id,status,title FROM tasks').all());
"
```

Как читать вывод:
- `lifecycle.status=running` + `current_stage_id=initial-discovery` → на цехе 1
- `process.local_outcome=go` → Discovery прошёл успешно, завод идёт дальше
- `current_stage_id=solution-formalization` → на цехе 2 (PRD/SRS/UC/AC)
- `current_stage_id=solution-development` → на цехе 3 (код, сборка фронта)
- `terminal_status=released|failed|approval-required` → pipeline завершён

## 🌳 Отчёт прогресса — формат дерева (КАК РИСОВАТЬ)

Когда просят «отчёт прогресса» / «что сейчас» / «где рабочий» — рисуем **дерево
прогресса завода**. Это канонический формат: один взгляд показывает весь завод,
все активные заказы, текущий цех и за каким столом стоит рабочий.

### Команды для сбора данных

```bash
# 1. Проекты, lifecycle-цеха, process-подцеха, задачи
node -e "
const D=require('better-sqlite3');
const db=new D('C:/Users/user/.zcode/saga.db');
console.log('=== PROJECTS ===');
db.prepare('SELECT id,name,status FROM projects').all().forEach(p=>console.log('  ['+p.id+'] '+p.name+' ('+p.status+')'));
console.log('=== LIFECYCLE RUNS ===');
db.prepare('SELECT id,project_id,status,current_stage_id,terminal_status FROM saga3_lifecycle_runs ORDER BY id').all().forEach(r=>console.log('  Run #'+r.id+' (P'+r.project_id+'): '+r.status+' | '+r.current_stage_id+(r.terminal_status?' → '+r.terminal_status:'')));
console.log('=== PROCESS RUNS ===');
db.prepare('SELECT id,project_id,status,projected_stage,local_outcome FROM saga3_process_runs ORDER BY id').all().forEach(r=>console.log('  #'+r.id+' (P'+r.project_id+'): '+r.status+' | '+r.projected_stage+(r.local_outcome?' → '+r.local_outcome:'')));
console.log('=== TASKS ===');
db.prepare('SELECT id,epic_id,status,title,assigned_to FROM tasks ORDER BY id').all().forEach(t=>console.log('  #'+t.id+' [E'+t.epic_id+'] '+t.status+(t.assigned_to?' → '+t.assigned_to:'')+' | '+t.title.slice(0,58)));
"
# 2. Живые процессы движка + воркеров
powershell -Command "Get-CimInstance Win32_Process -Filter \"name='node.exe'\" | Where-Object { \$_.CommandLine -like '*orchestrate-cli*' } | Select-Object ProcessId"
powershell -Command "Get-CimInstance Win32_Process -Filter \"name='claude.exe'\" | Select-Object ProcessId"
```

### Движок упал молча? (диагностический рецепт)

Если `LIFECYCLE_START_CHILD_EXITED_BEFORE_RECEIPT: code=1` и непонятно почему —
`stdio:'ignore'` в спавне прячет stderr. Временный diag-патч покажет причину:

1. В `src/infrastructure/engine/legacy-engine-administration.ts`, метод `start()`,
   заменить блок `spawnProcess(...)`:
   ```ts
   // было:
   stdio: 'ignore',
   // стало (временно):
   const diagLog = path.join(os.tmpdir(), `saga-engine-child-${Date.now()}.log`);
   const diagStream = createWriteStream(diagLog, { flags: 'a' });
   // ... spawnProcess('node', cliArgs, { detached:true, stdio:['ignore','pipe','pipe'], env:{...} })
   child.stdout?.pipe(diagStream);
   child.stderr?.pipe(diagStream);
   ```
   (нужны `import os from 'node:os'` и `import { createWriteStream } from 'node:fs'`)

2. `npx tsc` и перезапустить tracker-view

3. Дёрнуть старт, потом прочитать лог:
   ```bash
   cat "$(ls -t /tmp/saga-engine-child-*.log | head -1)"
   ```

4. **После диагноза откатить патч обратно** к `stdio:'ignore'` (не коммитить diag).

Этот рецепт нашёл оба бага текущего прогона (MODULE_NOT_FOUND и ENOENT).

## Известные подводные камни

### 1. `SAGA_PRODUCT_LIFECYCLE_COMPOSITION` обязателен

Без него движок падает с `code=1`, а `stdio:'ignore'` прячет stderr → видно только
`CHILD_EXITED_BEFORE_RECEIPT`. **Задавать при старте tracker-view**, движок
наследует окружение родителя.

### 2. ⚠️ BUG (исправлен): path к orchestrate-cli.js

В `src/app/product-lifecycle-run-starter.ts` и `legacy-engine-administration.ts`
был баг: `path.join(here, '..', '..', 'orchestrate-cli.js')` давал путь в корень
репо (`saga-mcp/orchestrate-cli.js`), но файл реально в `dist/orchestrate-cli.js`.

**Фикс:** spawn-starter теперь использует `path.join(here, '..', 'orchestrate-cli.js')`
(один `..`). legacy-engine-administration — в `dist/infrastructure/engine/`, ему
нужны `..`, `..` → `dist/orchestrate-cli.js` (два `..` корректны для него).
Проверяй: файл должен резолвиться в `<repo>/dist/orchestrate-cli.js`.

### 3. ⚠️ КРИТИЧНО: lifecycle-input путь должен быть ASCII

Windows engine-child получает `--lifecycle-input=<path>` и читает файл через
`readFileSync`. Если путь содержит **кириллицу** (`D:\Разработка\...`), Windows
ANSI codepage ломает её в `??????????` → `ENOENT: no such file or directory`.

**Правило:** клади lifecycle-input **только в ASCII-путь**:
```bash
# ПРАВИЛЬНО:
C:/Users/user/.zcode/blink-input.json
C:/temp/blink-input.json

# НЕПРАВИЛЬНО (кириллица ломает engine):
D:/Разработка/saga-mcp/blink-input.json
```

### 4. `/api/engine/status` врёт на Windows

`alive:false` не значит «движок мёртв» — PowerShell CIM-проверка иногда не находит
процесс в первые секунды. **Источник правды — БД** (`saga3_lifecycle_runs.status`).

### 5. Дубли lifecycle runs

Возникают если запускать несколько раз с разными idempotency-key. Чистый старт =
reset БД. Если нужно удалить один мусорный run, см. SQL-каскад ниже.

### 6. Один lifecycle = одна карточка на доске

«Product Delivery» (родитель) и «Initial Discovery» (вложенная стадия) — это
НЕ две задачи, это один pipeline на двух уровнях детализации.

### 7. НЕ запускай движок через `node ... &` в Bash-tool

Harness убивает child-процессы по завершении tool-call → движок orphan'ится через
пару минут, lease висит. **Запускай только через tracker-view's
`/api/engine/start`** (или веб-форму), который делает настоящий
`child_process.spawn({detached:true})` на уровне ОС — он переживает turn'ы.

## Удаление мусорного lifecycle run (если что-то пошло не так)

```bash
RUN_ID=<id мусорного run'а>  # например 40
node -e "
const D=require('better-sqlite3');
const db=new D('C:/Users/user/.zcode/saga.db');
db.pragma('foreign_keys=OFF');
db.prepare('DELETE FROM saga3_protocol_step_runs WHERE protocol_run_id IN (SELECT id FROM saga3_protocol_runs)').run();
db.prepare('DELETE FROM saga3_protocol_runs').run();
db.prepare('DELETE FROM saga3_process_transitions WHERE lifecycle_run_id=$RUN_ID').run();
db.prepare('DELETE FROM saga3_stage_runs WHERE lifecycle_run_id=$RUN_ID').run();
db.prepare('DELETE FROM saga3_node_runs WHERE process_run_id IN (SELECT id FROM saga3_process_runs WHERE id IN (SELECT process_run_id FROM saga3_stage_runs WHERE lifecycle_run_id=$RUN_ID))').run();
db.prepare('DELETE FROM saga3_stage_runs WHERE lifecycle_run_id=$RUN_ID').run();
db.prepare('DELETE FROM saga3_lifecycle_runs WHERE id=$RUN_ID').run();
db.pragma('foreign_keys=ON');
console.log('run $RUN_ID removed, remaining:', db.prepare('SELECT id,status FROM saga3_lifecycle_runs').all());
"
```

⚠️ Никогда не удаляй run со статусом `running` — это активный pipeline.

## ports и финальный результат

- **Канбан (пульт завода):** http://localhost:4321 — всегда доступен пока жив tracker-view
- **Продукт (Vite dev server):** http://localhost:5173 — поднимется на стадии Development,
  когда dev-воркер соберёт фронт. Не существует до цеха 3.

### Как понять что продукт готов

1. `lifecycle.terminal_status` ∈ `{released, approval-required}` → pipeline завершён
2. В репо продукта появился код (Vite-проект, собранный dev-воркером)
3. Vite dev server отвечает на http://localhost:5173

В режиме `local-dry-run` (composition по умолчанию) Delivery завершается
`approval-required` — это **не ошибка**, а fail-closed: публикация не настроена,
поэтому завод честно говорит «нужна авторизация для релиза». Продукт уже собран
и работает локально, только не опубликован.

### Если нужно перезапустить остановленный движок

```bash
# Остановить
curl -X POST http://localhost:4321/api/engine/stop -H "Content-Type: application/json" -d '{"epic_id":1}'

# Снова запустить (тот же lifecycle продолжится, если не terminal)
curl -X POST http://localhost:4321/api/engine/start \
  -H "Content-Type: application/json" \
  -d '{"epic_id":1,"concurrency":2,"lifecycle_input_path":"C:/Users/user/.zcode/blink-input.json"}'
```

⚠️ Если lifecycle в `terminal_status` (failed/released/...), повторный старт с тем же
idempotency-key вернёт тот же терминальный run. Для нового прогона — новый
idempotency-key или reset БД.
