# arch-incident-forensics — трёхкомандный форензик инцидентов и архитектурных дефектов

## 1. Назначение и критерии запуска

Скилл кодирует процесс глубокого разбора инцидента: послойный форензик с
доказательствами → три независимые команды (архитектор, инженер, красная
команда) → сведение, реализация, тесты, QA-гейт, коммит.

**Запуск обязателен, когда:**

- отказ одного класса повторяется после одного-двух точечных фиксов;
- телеметрия вводит в заблуждение: статус в БД/трекере не соответствует
  физике (статусы «lost»/«failed» у фактически завершившихся воркеров);
- дефект кросс-слойный: симптом виден в одном слое, причина — в другом
  (контракт дрейфует между исполнением, авторингом и гейтами);
- серия ночных `fix(...)` не ослабляет симптом — признак одного системного
  дефекта, а не независимых багов.

**Не для этого скилла** (соседние, не дублировать):

- одиночная runtime-ошибка с понятным кодом → `saga-factory-diagnostician`;
- застрявший воркер одной задачи (MAX_ATTEMPTS) → `saga-diagnostician`;
- баг в коде продукта под эпизодом → `saga-bug-diagnostician`;
- лечение stage-gate провалов и плохих состояний артефактов
  (Cynefin-триаж + MCDA) → `autonomous-recovery` — он ЛЕЧИТ, этот скилл
  РАССЛЕДУЕТ.

## 2. Доктрина качества — «разбирать как инженер, а не как студент»

### 2.1 Послойный разбор

Каждый инцидент разбирается по четырём слоям. Для каждого слоя ответить на
два вопроса: что механически произошло и почему.

```text
Слой 1 — физика исполнения: процессы и PID, lease/heartbeat, гонки
         наблюдателей (reaper / poller / close-callback / boot-sweep),
         транзакционность переходов, атомарность освобождения.
Слой 2 — контент/авторинг LLM: какой пинированный контракт, шаблон,
         чеклист и набор инструментов воркер реально получил и что
         реально произвёл (байты, не пересказ).
Слой 3 — гейты клеток: парсер/канонизатор, CheckPlan, валидатор,
         CandidateSet → GateRun → GateDecision — кто и по какому правилу
         принял/отклонил материал.
Слой 4 — kernel/инварианты: владение authority, модель переходов,
         событийная модель, инварианты CONVEYOR — какой инвариант
         нарушен или отсутствует.
```

Запрещено останавливаться на слое, где удобно найти объяснение: у дефекта,
дожившего до этого скилла, симптом почти всегда живёт не в своём слое.

### 2.2 Каждое утверждение — с доказательством

- Факт = `file:line` из кода ИЛИ read-only SQL по БД завода с приведённым
  запросом и числом строк.
- Всё недоказанное явно помечается `ГИПОТЕЗА` и получает план фальсификации
  (какой запрос/эксперимент её убьёт). Ни одна гипотеза не попадает в вывод
  фазы 3 как факт.
- Запрещены недоказанные отсылки. «Те самые потерянные воркеры» — мусор:
  каждое «те самые» раскрывается механически — какие именно строки таблицы,
  какие события, какой коммит это создал.

### 2.3 Двойной регистр отчёта

- (а) Технический: послойно, с file:line и SQL-доказательствами.
- (б) Аналогия для оператора: завод-цех-рабочий-ОТК-табельщик — что
  сломалось на языке табеля и смен, без жаргона. Оба регистра обязательны:
  оператор принимает решение о приоритете по регистру (б), проверяет по (а).

### 2.4 Цена дефекта по БД

До предложений фикса посчитать по БД (readonly): сколько строк/событий
попадает под класс дефекта, сколько холостых циклов и ретраев он уже сжёг
(сожжённый бюджет клеток, лишние запуски, потерянные часы). Цена
приоритизирует фикс и отделяет крупный класс от единичного случая.

### 2.5 Семя отказа vs шум исполнения

- Семя — нарушенный инвариант: при воспроизведении условий убивает всегда,
  само не сходится. Фиксится.
- Шум — случайные пересечения таймингов, опоздавшие наблюдения, ретраи
  сетевых сбоев: сходится сам, не требует структурного фикса.
- Отделять явно: «фиксить семя, мониторить шум». Фикс шума — раздутие
  скоупа; игнор семени — повторение инцидента.

## 3. Фаза 1 — соло-форензик

### 3.1 Обязательное чтение (целиком, не выдержки)

```text
docs/architecture/decisions/053-workplace-production-revision-as-accepted-material-authority.md
docs/architecture/CONVEYOR-MENTAL-MODEL.md
docs/architecture/CONVEYOR-TRANSITION-DIAGNOSTICS.md
docs/architecture/CONVEYOR-TRANSITION-CHECKLIST.md
```

ADR-053 — системный диагноз перекодирования границ (Workplace как владелец
работы против WorkerExecution как владельца материала): большинство
«разных» ночных багов — его проявления. CONVEYOR-* — грамматика переходов
`FactoryOrder → LifecycleRun → StageRun → ProcessRun → NodeRun → Workplace →
WorkerExecution → CandidateSet → GateRun → Decision` и три слоя authority.

### 3.2 Каналы данных (читать одним проходом, БД — только readonly)

БД завода определить по запуску (трекер/лог драйвера; тестовый полигон —
`.factory-testbed/factory.sqlite`). Открытие строго
`sqlite3 "file:<db>?mode=ro"`.

```text
worker_executions        state, phase, pid, lease_expires_at, heartbeat_at
lifecycle_events         журнал команд/событий (event_kind, task_id)
factory_lifecycle_runs / factory_stage_runs / factory_node_runs / factory_process_runs
factory_workplaces       kanban_phase, loop_state, active_reservation_ref, terminal_reason
factory_gate_runs + factory_gate_decisions     кто и почему принял/отклонил
factory_orders           last_error, state
artifacts / factory_managed_artifact_productions   произведённый материал
tasks                    обратная проекция (status, workplace_ref)
логи драйвера            stdout/stderr воркеров и трекера запуска
```

### 3.3 Порядок

1. Зафиксировать симптом и scope: порядок/ран/воркплейс, коды ошибок.
2. Построить timeline рассинхрона: какое событие в каком канале произошло,
   а в каком — не произошло; где каналы противоречат друг другу.
3. Пройти все четыре слоя (§2.1), по каждому — механика + доказательство.
4. Посчитать цену класса по БД (§2.4).
5. Выделить кандидатов в семя vs шум (§2.5).
6. Выход фазы 1: черновик причинной цепочки с доказательствами, список
   открытых вопросов — они становятся входом брифов фазы 2.

## 4. Фаза 2 — три параллельных субагента с самодостаточными брифами

Запустить три субагента ПАРАЛЛЕЛЬНО. Бриф самодостаточен: субагент не видит
сессию лида, поэтому каждый бриф содержит контекст инцидента (факты фазы 1
с file:line/SQL), пути доков, путь к БД (readonly), запрет коммитов и
формат деливерабла. Субагенты — только на разрешённом репо бэкенде
(opencode; claude CLI backend запрещён — CLAUDE.md/AGENTS.md, коммит
aa104969). Независимость ролей обязательна: архитектор не видит патч
инженера, красная команда атакует вслепую — это снижает самоподтверждение.

### 4.1 Бриф АРХИТЕКТОР (шаблон)

```text
РОЛЬ: архитектор конвейера saga4.
КОНТЕКСТ: <5-10 фактов фазы 1 с file:line / SQL; симптомы и цена класса>.
ОБЯЗАТЕЛЬНО ПРОЧИТАТЬ ЦЕЛИКОМ: docs/architecture/decisions/053-*.md,
docs/architecture/CONVEYOR-MENTAL-MODEL.md, CONVEYOR-TRANSITION-DIAGNOSTICS.md,
CONVEYOR-TRANSITION-CHECKLIST.md.
ЗАДАЧА: целевые инварианты (дано ⇒ всегда) по затронутой границы;
протокол консистентности между каналами authority; событийная модель
целевого состояния; привязка каждого предложения к конкретному ADR/разделу
CONVEYOR; риски миграции. Не писать код.
ВЫХОД: документ-предложение <путь в docs/architecture/proposals/>.
ЗАПРЕЩЕНО: коммиты, запись в БД (readonly SQL можно).
```

### 4.2 Бриф ИНЖЕНЕР (шаблон)

```text
РОЛЬ: инженер по коду завода.
КОНТЕКСТ: <те же факты фазы 1>.
ЗАДАЧА: карта кода — по каждому затронутому состоянию/таблице перечислить
ВСЕХ writer'ов с file:line (кто-что-пишет); минимальный патч-сет ТЕКСТОМ
(unified diff), решающий семя, не шум; список регрессионных тестов —
какие существующие тесты закрывают класс и какие новые нужны.
ВЫХОД: карта writer'ов, патч-сет текстом, тест-план.
ЗАПРЕЩЕНО: коммит/применение патча, запись в БД.
```

### 4.3 Бриф КРАСНАЯ КОМАНДА (шаблон)

```text
РОЛЬ: красная команда. Твоя работа — сломать, а не согласиться.
КОНТЕКСТ: <те же факты фазы 1 + предложение архитектора, если готово;
для слепой атаки — без него>.
ЗАДАЧА: таблица атак по слоям 1-4: сценарий ⇒ где в коде (file:line) ⇒
последствие ⇒ какая защита должна существовать; квантификация шума по БД
(readonly): сколько наблюдаемых событий класса — шум, сходящийся сам;
список инвариантов «дано ⇒ всегда», которые система обязана гарантировать;
вердикт по предложению: ПРИНЯТЬ / ТРЕБУЕТ ИЗМЕНЕНИЙ (список обязательных
поправок) / ОТВЕРГНУТЬ.
ВЫХОД: таблица атак + вердикт с обоснованием.
ЗАПРЕЩЕНО: коммиты, запись в БД.
```

## 5. Фаза 3 — сведение, реализация, тесты, QA, коммит

1. Сверка трёх отчётов: таблица расхождений «архитектор vs инженер vs
   красная команда». Спорные вопросы решаются в пользу МИНИМАЛЬНОГО
   решения — меняющего наименьшее число слоёв и таблиц.
2. Обязательные поправки красной команды — в скоуп. Не опциональны;
   невключение каждой обосновывается отдельно и явно.
3. Реализация патч-сета + целевые тесты (из тест-плана инженера).
   Ловушка: существующие golden-тесты могут фиксировать ДЕФЕКТ как эталон.
   Каждый упавший golden разбирается: эталон или закодированный дефект?
   Если дефект — тест обновляется, в коммите указано почему.
4. QA-гейт: любое изменение Factory runtime / entrypoints / воркшопов /
   клеток / Workplace / WorkerExecution — прогнать скилл
   `saga-factory-qa` (fail-closed; PASS_TO_COMMIT обязателен).
5. Протокол коммита:
   - зафиксировать `git status` ДО работы; в коммит идут ТОЛЬКО
     намеренные файлы (явный `git add <список>`); чужие незакоммиченные
     изменения не трогать;
   - `git fetch origin && git rebase origin/saga4` (удалёнка живая);
   - коммит-месседж: что и почему, цена дефекта по БД, ссылки на ADR;
   - `git push origin saga4`.

## 6. Связанные методики

- **Blameless postmortem** (Google SRE): системные способствующие причины
  вместо поиска виноватого; таймлайн объективных данных — основа фазы 1.
  https://sre.google/sre-book/postmortem-culture/
- **Swiss Cheese Model** (Wiegmann 2022): отказ — это выровнявшиеся дыры
  нескольких слоёв защиты, а не «один root cause»; поэтому разбор послойный.
  https://pmc.ncbi.nlm.nih.gov/articles/PMC8514562/
  Критика модели (Larouzee 2020): сама модель не даёт механики — механику
  даёт код и БД, модель лишь рамка. https://www.sciencedirect.com/science/article/pii/S0925753520300576
- **Ограничения 5 Whys**: линейность и остановка на первом удобном ответе;
  здесь заменено четырёхслойной механикой с доказательствами (§2.1-2.2).
- **Red teaming** (IBM; систематический обзор arXiv 2602.21267):
  структурированная адверсариальная симуляция для вскрытия уязвимостей —
  основа роли красной команды в фазе 2.
  https://www.ibm.com/think/topics/red-teaming
- **Multi-agent debate** (Du et al., MIT/Google): несколько независимых
  экземпляров модели с разными ролями уменьшают самоподтверждение и
  повышают фактичность — обоснование трёх независимых брифов фазы 2.
  https://composable-models.github.io/llm_debate/
- **Cynefin** (Snowden): триаж доменов (clear/complicated/complex/chaotic)
  определяет стратегию ответа; соседний скилл `autonomous-recovery`
  применяет его для ЛЕЧЕНИЯ stage-gate провалов — этот скилл не дублирует
  его, а расследует инцидент трёхкомандным форензиком.
  https://thecynefin.co/about-us/about-cynefin-framework/

## 7. Референс-пример: инцидент false-lost (фикс d09ad0e6)

Образец требуемой глубины, 12 строк:

```text
Симптом (регистр оператора): табельщик списывает в пропавших рабочих,
  которые смену сдали (20-проектный полигон).
Слой 1 (физика): reaper классифицировал мёртвый процесс по одной физике
  (pid мёртв), не проверяя receipt; гонка close-callback vs poller теряла
  exit_code. src/lifecycle/atomic-release.ts — все writer'ы терминализации.
Слой 2: непричастен — контент воркеров был корректен.
Слой 3: непричастен — гейты пропускали материал.
Слой 4 (инвариант): принятый worker_done receipt — durable
  semantic-completion authority, коммитится ДО смерти процесса ⇒
  терминал «lost» при живом receipt невозможен. Инвариант нарушен.
ЦЕНА по БД (readonly SQL): 111 строк false-lost (76% всех lost);
  4 из 5 «terminated» — живые receipt-backed финишеры, убитые на 30-сек
  границе фазы; холостые ретраи жгли бюджет клеток как фантомные попытки.
Семя: классификация терминала по физике без перепроверки receipt.
Шум: опоздавшие наблюдения exit (бэкфилл, не ретраи).
Фикс (d09ad0e6): единая точка releaseExecutionAtomically — каждый writer
  (reaper, guard, lease expiry, kill, boot sweep) фуннелится через неё,
  receipt перепроверяется в транзакции, lost/terminated сходятся к «exited».
Уроки: «те самые потерянные» раскрыты в 111 конкретных строк; счёт по БД
  приоритизировал фикс; расходившиеся writer'ы лечатся не правкой одного,
  а единой транзакционной точкой схождения.
```
