## 0. Резюме (одним абзацем)

Задача «восстановить документацию по коду» не требует нового терминального конвейера и не должна копировать цех формализации. Правильный ход — **инверсия**: фан параллельных цехов-восстановителей (инфраструктура, данные, домен, тесты, бизнес-синтез) производит не документацию, а **структурированное сырьё** — Reconstruction Brief, — который стыкуется во вход штатного цеха 2. Формализация остаётся единственной печатью контракта: те же артефакты (PRD, FR/NFR/RULE, UC, AC, SRS), те же гейты, тот же reconciliation. Методология Wiegers/BABOK разлагается на три слоя внедрения: чек-листы → детерминированные check-провайдеры существующих гейтов; секции → role cards рабочих мест цеха 2; AUDIT-режим → ядро самого восстановления (аудит кода-свидетеля, Health Summary как реестр пробелов, классификатор уровня как фильтр стыковки). Провенанс-маркировка `evidenced / inferred / hypothesis` превращает отсутствие документации из источника галлюцинаций в честный реестр открытых вопросов.

## 1. Проблема

У проектов бывает код без документации. Универсальный цех формализации читает такой материал неподготовленным: один воркер с одним профилем чтения должен одновременно быть инженером инфраструктуры, аналитиком домена, тест-инженером и бизнес-аналитиком. Результат (подтверждено прогоном GDesign и мысленным экспериментом «код-only»): формализация выходит честной, но суше — доменный вес, который несли доки (эталоны, нормативные оговорки, история), теряется, если он не вшит в код/фикстуры.

Корневая асимметрия: **код — свидетель поведения, но не замысла.** Значит, восстановление обязано различать «доказано кодом», «выведено из паттерна» и «правдоподобная гипотеза» — иначе получится правдоподобная выдумка.

## 2. Ключевая инверсия

Фан восстановления **не производит формальных артефактов** и не имеет гейтов формальной приёмки — только детерминированные проверки свидетельств (тест запускается, приложение поднимается). Вся формальность (author/reviewer, CandidateSet, GateDecision, reconciliation) остаётся в цехе 2. Это и есть «не копировать цех формализации»: ни одного своего formal-artifact-типа, ни одного своего гейта качества.

```text
код + тесты + git-история (замороженный ProductRef)
  → ФАН ВОССТАНОВЛЕНИЯ (параллельно):
       инвентаризация   → карта кода: модули, точки входа, зависимости, тест-карта
       инфраструктура   → Infra Evidence Pack    (сборка/запуск/окружение/deps)
       данные           → Data Evidence Pack     (форматы, схемы, потоки)
       домен            → Domain Evidence Pack   (сущности, инварианты, эталоны, глоссарий)
       тесты            → Test Evidence Pack     (тест → AC-кандидат с оракулом)
       бизнес-синтез    → актёры, потоки ценности (максимум инференции — поэтому последний)
  → СТЫКОВОЧНЫЙ АДАПТЕР: Reconstruction Brief
  → Discovery (штатный) → сертификат go
  → ЦЕХ 2 (штатный, не тронут) → тот же выход: PRD+FR/NFR/RULE → UC → AC → SRS
```

Порядок фан-аута: сначала цехи с низкой инференцией и высоким свидетельством (инфра, данные, домен, тесты), бизнес-синтез последним — он строит замысел из выходов остальных.

## 3. Стыковочный адаптер: Reconstruction Brief

Бриф организован **не по цехам фан-а, а по узлам приёмника** — каждый узел цеха 2 читает ровно свою секцию. Структура секций наследует обязательную структуру документа методологии (Wiegers: секции 1–18) и таксономию артефактов цеха 2.

| Секция брифа (по узлу цеха 2) | Что кладут цехи фан-а | Целевые артефакты |
|---|---|---|
| `business-context` (секции 4–7: контекст, RACI, границы, допущения) | бизнес-синтез | BR, SR, CONSTRAINT, ASSUMPTION |
| `use-cases` (секция 10: BUC/SUC/User Stories) | бизнес-синтез + глоссарий домена | UC |
| `acceptance-contract` | **тест-пак: тест → AC-кандидат с оракулом** | AC |
| `architecture-contract` (deployment view, data model, декомпозиция) | инвентаризация + инфра + данные + домен | SRS |
| поперёк всех | домен: инварианты и эталоны (условие → тип Blocking/Soft → последствие) | RULE; кандидатуры FR/NFR с провенансом |

Единица брифа: `{утверждение, слой, провенанс, источники (файл:строка), целевой тип из таксономии BR..NFR}`.

## 4. Провенанс-маркировка и реестр пробелов

Эволюция анти-галлюцинационных правил прогона GDesign («нет источника — не включается») в систему трёх градаций:

- `evidenced` — факт с источником `файл:строка/функция`;
- `inferred` — вывод из паттерна (паттерн назван);
- `hypothesis` — правдоподобно, требует человека.

**Реестр пробелов (Open Questions) — первоклассный побочный продукт фан-а**: не входит в таксономию цеха 2, кладётся рядом; каждому пробелу — место в коде, где ответ был бы виден, если бы существовал. Восстановление без доков законно возвращает «суше, но честнее» — дыры видимы, а не залиты выдумкой.

## 5. Методологическая база: три слоя внедрения

Методология (Wiegers/BABOK, полная версия) разбирается не на «промпт», а на детали конвейера. В репо уже есть её прототип — скилл `senior-analyst` (дистилляция BABOK v3 + Wiegers, Complexity Gate оркестратора); полная версия добавляет классификатор уровня, чек-листы качества формулировок/AC, INVEST-таблицу, FURPS+ и AUDIT-режим.

### 5.1 Слой 1: чек-листы → check-провайдеры существующих гейтов

Граница автоматики (что можно проверить без LLM):

| Проверка | Источник в методологии | Механика |
|---|---|---|
| Бан расплывчатых слов без метрик («быстрый», «корректный», «удобный», «надёжный», «оптимальный») | Formulation Checklist §3 | словарь-фильтр |
| NFR квантифицирован: число + единица + условие | NFR Checklist | паттерн |
| Утечка дизайна в FR/AC: endpoint, HTTP-код, JSON-поля, формула, флаг, протокол | DOWN-тест (Step 4) | регулярки |
| Полнота трассировки цепочки BR→SR→BUC→SUC→FR/RULE→NFR→тест; сироты и бездетные родители | Traceability | графовый чек по БД |
| У каждого FR есть AC; AC бинарны; у AC — тест-кейс | AC Checklist | структурный чек |
| AC-мультиусловия «Given <условие> → Then <вердикт>» → извлечь в RULE | RULE vs FR тест (Step 5) | шаблон |

Кандидат: `factory.requirement-hygiene.v1` — усиливает гейты цеха 2 **без единого нового цеха**.

Семантика (remove-technology тест, ценность BR, выбор BUC/SUC, рекомендация модели state/BPMN/sequence) остаётся в author/reviewer-циклах.

### 5.2 Слой 2: role cards рабочих мест цеха 2

| Рабочее место | Роль из методологии | Артефакты |
|---|---|---|
| `business-context` (новое) | секции 4–7; BR с измеримой метрикой успеха; SR называет стейкхолдера | BR, SR, CONSTRAINT, ASSUMPTION |
| `use-case-modeling` | дисциплина BUC↔SUC; нарратив + рекомендуемая модель + таблица переходов; User Story по INVEST | BUC, SUC, User Story |
| `solution-requirements` | FR/NFR/RULE по DOWN-тесту; механизм — в приложение 18 как ALGORITHM/SPEC с родителем | FR, NFR, RULE |
| `acceptance-contract` (есть) | AC: Given/When/Then, бинарность, негативные/граничные, без механизма | AC |
| `traceability-reconciliation` (есть, усилить) | полная матрица + FURPS+ покрытие + сироты | матрица трассировки |
| `architecture-contract` (есть) | SRS по фактическим модулям кода | SRS |

PRE-OUTPUT GATE методологии («не отдавать, пока не пройдено») — спецификация финального гейта цеха 2.

### 5.3 Слой 3: AUDIT-режим как ядро восстановления

«У пользователя уже есть требования/документы — не переписывать, сначала аудит» в doc-recovery обращается в: **«уже есть код»** — восстановленные кандидатуры проходят аудит против кода-свидетеля.

- **Health Summary** (ID | заявленный тип | вычисленный уровень | вердикт OK/ISSUES/CRITICAL | главная проблема) — формат реестра пробелов.
- **LEVEL CLASSIFIER** (вычисленный уровень ≠ метка → FAIL) — фильтр стыковки: бриф не пропускает кандидатуру неподтверждённого уровня.
- `hypothesis` без родителя → Open Question с владельцем.

## 6. Реализация: два уровня

- **v0 — без кода завода (эксперимент сегодня):** фан выполняет внешний агент (ZCode), собирая паки по замороженному коду, и собирает бриф. Дальше штатный вход: бриф как материал идеи (заморозка по хэшу) → обычный запуск → штатные Discovery + цех 2. A/B против прогона GDesign 2026-08-20 покажет прирост от специализированного чтения (сравнение наборов FR/NFR/RULE/AC, полнота трассировки, размер и качество Open Questions).
- **v1 — профиль lifecycle:** узлы фан-а как специализированный Discovery-модуль (параллельные pack-узлы + адаптер-свертка в бриф), далее штатный маршрут. Эпик на сам завод — собирается самим заводом (догфудинг).
