## Исследование: как стартовать с того места

### Проблема
Каждый новый idempotency-key создаёт НОВЫЙ lifecycle run → discovery стартует с нуля.
Это трата: discovery уже дал `go` 5 раз, PRD/UC/AC уже созданы.

### Варианты resume

#### Вариант A: --resume с тем же idempotency-key (ПРАВИЛЬНЫЙ)
```bash
node dist/orchestrate-cli.js 1 1 --concurrency=2 --resume \
  --idempotency-key='product-delivery:epic:1:blink-v4-epicfix'
```
- Если lifecycle #52 в paused: продолжит с того же node
- Если lifecycle #52 terminal (failed/completed): вернёт terminal, не создаст новый
- **Ограничение:** нельзя resume terminal lifecycle (нужен новый key → новый run → discovery заново)

#### Вариант B: создать lifecycle НО пропустить discovery через accepted certificate
Discovery certificate уже есть (immutable, process_run 117/119/121).
Новый formalization process-run мог бы начать с discovery-certificate-ref,
не пере-выполняя discovery. Но lifecycle всегда начинает с entryStageId=initial-discovery.

#### Вариант C: fast-track discovery (готовая фича saga-kickstart)
Если discovery уже дал go для этого epic — пропустить к formalization.
Но это в skill-логике (saga-kickstart), не в lifecycle-engine.

#### Вариант D: direct formalization process-run (минуя lifecycle)
Запустить solution-formalization module напрямую через process_run_start,
передав discovery certificate из #50. Но это обходит lifecycle orchestration.

### Рекомендация
- Для PAUSED lifecycle: --resume с тем же key (Вариант A)
- Для FAILED lifecycle: проверить — можно ли «возобновить» failed run
  (изменить status failed→paused в БД — это status change, не destruction,
  разрешено CGAD P2). Потом --resume.

## Вывод по исследованию resume

**Главная трата токенов:** discovery повторяется каждый новый lifecycle run.
Это structural — lifecycle engine всегда начинает с entryStageId=initial-discovery.
Даже с `--resume` того же key, если lifecycle terminal:failed, нужен новый key →
новый run → discovery заново.

**Ближайшая цель:** formalization должен пройти с фиксами F+F'. Если пройдёт —
Vite будет готов. Если нет — следующий шаг: resume failed lifecycle через
status change (CGAD P2: «status change, not destruction»), а не новый run.

**Долгосрочное решение (tech-debt):** lifecycle engine должен поддерживать
«skip completed stages» — если discovery certificate уже accepted для этого
epic, новый lifecycle run может пропустить discovery и начать с formalization.
Это аналог fast-track в saga-kickstart, но на уровне lifecycle-engine.

## Incident 2026-08-06 — `AUTHORITY_BINDING_INVALID`

- **Run:** `order-fd0f5b6b`
- **Результат запуска:** `start_failed`
- **Ошибка:** `AUTHORITY_BINDING_INVALID: WorkIntent 1 status 'concluded' is not claimable (task status='todo')`
- **Слой:** архитектурный authority-binding split brain.

### Фактическая последовательность

1. Discovery worker закоммитил durable raw submission / Proposal.
2. Worker process был потерян в post-submit/pre-close окне.
3. `resolve-proposal-submission` нашёл durable product и законно завершил
   WorkIntent как `concluded`.
4. Workplace остался `in_progress/verifying`, а task projection вернулась или
   осталась `todo`.
5. Resume снова выбрал карточку, после чего claim был отвергнут: закрытый intent
   не может дать authority новому worker.

### Корневая причина

`factory_work_intents.status`, `factory_workplaces` и `tasks.status` изменялись
разными writer-путями без общей транзакции. Кроме того, resume-код допускал
неправильную компенсацию `concluded -> open` на основании `tasks.status=todo`,
то есть проекция могла переопределить authority state.

### Исправление

ADR-028 вводит обязательный cross-channel invariant:

```text
WorkIntent -> concluded
  + Workplace -> terminal(accepted|failed)
  + task reverse projection -> done
```

Все три изменения выполняются в одной SQLite-транзакции. При открытии БД
выполняется одноразовая reconciliation уже накопленных
`concluded + verifying/todo` строк. `concluded` не становится claimable и не
переоткрывается из-за stale task projection.

### Нарушенные правила, которые теперь защищены кодом

- crash/lease expiry не возвращает начатую работу в `todo`;
- `verifying` обязан завершиться terminal decision, а не зависнуть при наличии
  принятого durable product;
- `tasks.status` является reverse projection и не управляет WorkIntent;
- новый worker не получает authority по уже `concluded` intent.

### Остаточная граница миграции

Текущий bridge использует легитимное решение module resolver и не фабрикует
CandidateSet, CheckReceipt или GateDecision. Полный universal GateRun остаётся
отдельным этапом Production Cell cutover. До него ADR-028 гарантирует
атомарность существующего resolver-пути и отсутствие повторного найма после
crash-after-submit.
